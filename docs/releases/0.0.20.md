# Wukong Code 0.0.20

0.0.20 lets Loop reuse qualitative verification rules from existing local
Skills while keeping commands, secrets, and final PASS under Wukong's frozen
Gate.

## What's changed

- `/loop` discovers strict `verification/criteria.v1.json` sidecars from
  personal, project, monorepo package, explicitly trusted local, and read-only
  built-in reference sources. Markdown Skill bodies remain documentation and
  cannot add commands, tools, permissions, hooks, MCP, or network access.
- Deterministic suggestions stay visibly unselected. Users choose exact
  source + locator + full provenance digest identities and may order multiple
  standalone recipes in one flat selection. Same-name sources no longer use
  silent first-wins behavior.
- Headless dry-run reports the contract schema, catalog digest, exact
  selection CAS, criteria, provider destination, review-subject policy,
  exclusions, and estimated reviewer cost without starting a model call or
  creating local run state.
- Every new V2/V3 reviewer receives only attempt-scoped broker tools. It cannot
  use arbitrary Read, Glob, Grep, Bash, Skills, MCP, or Web. Changed, explicitly
  untracked, scope-matched, and deterministic Gate evidence inputs remain
  bounded and secret-filtered.
- Workspace broker trust is separate from project-check shell trust. Each run
  also requires a non-remembered confirmation for the exact BYOK provider
  endpoint and allowed input origins. Auto, YOLO, and `--yes` cannot replace
  either decision. Fresh-reviewer requests lock the transport to that exact
  origin and disable redirects; transports that cannot prove this boundary
  fail before the Gate attempt opens a provider connection.
- Selected Skill, input manifest, evidence, provider, policy, or workspace
  drift fails closed. A single isolated fresh reviewer must cover every
  criterion and carried blocker; deterministic failures still have higher
  priority than model output.
- Gate attempt, check, scan, subject manifest, reviewer verdict, proof
  aggregate, evidence snapshot, completion, terminal, and continuation records
  now use durable exact joins for both V2 and V3 Loops.
- Four read-only reference recipes ship with the CLI: API compatibility,
  migration safety, log security, and frontend design. They are optional,
  transparent, and never selected automatically.
- The installer downloads from the public `wukong-code` release, maps Windows
  to the published `win32-x64` / `win32-arm64` assets, and verifies SHA-256
  with either `sha256sum` or `shasum`. It does not create an install identity
  or send install telemetry.

## Product boundary

Wukong Code remains free, local-first, and BYOK. Catalogs, selections, trust
grants, contracts, manifests, and Gate records stay on the user's machine.
Only content explicitly admitted by the bounded broker is sent to the exact
BYOK provider confirmed for that run; it is not uploaded to Wukong Web or D1.

This release does not create or edit Skills, execute Skill commands, add a
command-recipe runtime, provide a complete process sandbox, chain recipes,
upload sessions or evidence, add hosted models, quotas, payments, PR Gate,
Team policy, cloud sync, or a telemetry metrics backend.

## Try it

Inside the TUI:

```text
/loop update the public API without breaking existing clients
```

Open **Review verification**, inspect source/trust/full digest/criteria/input
policy/cost, explicitly select any applicable recipes, then confirm local broker
trust and the exact BYOK destination.

For a headless proposal:

```sh
wukong loop "update the public API" \
  --dry-run \
  --output-format stream-json
```

Use the returned catalog digest, exact `selection-id@provenance-digest`, short
broker challenge, Gate approvals, and provider-consent acknowledgement when
starting the real Loop. None of these can be replaced with a short Skill name
or a broad `--yes`.
