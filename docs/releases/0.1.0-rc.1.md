# Wukong Code 0.1.0-rc.1

`0.1.0-rc.1` is a prerelease candidate for the Trusted Local Loop. It remains
Free, local-first, and BYOK. It is not the stable `latest` release and is meant
for explicit opt-in validation on real repositories.

## What's changed

- One editable Preflight now consolidates the Goal, Done when, Must not rules,
  exact checks or a versioned no-check decision, provider destination, input
  boundary, permission mode, dirty workspace, iteration limit, provider-call
  ceilings, and optional token budget.
- Local read, provider transmission, permission, and project-check execution
  remain separate approvals. Cancelling Preflight creates no run and makes no
  provider request.
- Gate completion now requires complete, fresh evidence from the same attempt.
  Partial, inconclusive, stale, conflicting, stopped, interrupted, or corrupt
  evidence cannot become `PASS`.
- Terminal output separates `PASS`, `NEEDS_WORK`, and `ERROR` Gate verdicts from
  `PAUSED` and `STOPPED_BY_USER`, and shows decisive evidence, file attribution,
  checks, usage, blocker, recovery, and next action.
- Provider-call and token ceilings are enforced at runtime. Exhaustion is a
  resumable `NEEDS_WORK` result, while an unknown provider outcome blocks blind
  retry and exposes the request identity needed for reconciliation.
- Compatibility and recovery cover direct upgrade from `0.0.22`, legacy
  `0.0.21` records, crash/restart, duplicate or late terminal records, and
  concurrent continuation attempts.
- Codex, Claude Code, Cursor, Kimi Code, and Grok imports remain read-only
  context that produces an editable Goal without importing trust, checks,
  permissions, or provider consent.
- The public prerelease was built once from one exact source/catalog identity.
  Checksums, provenance, attestations, pinned fresh installs, `0.0.22` upgrades,
  state recovery, and smoke tests passed for all six platform targets without
  replacing stable `latest`. The canonical installer verifies the published
  SHA-256 automatically and stops before replacement when it does not match.

## Install the pinned prerelease

Do not use the default installer until `0.1.0` becomes stable. macOS and Linux
testers can pin this public candidate:

```sh
curl -fsSL https://wukong.today/install.sh | WUKONG_VERSION=v0.1.0-rc.1 sh
wukong --version
```

The installer downloads the adjacent SHA-256 file and stops without replacing
the installed binary if verification fails.

Windows testers should download the matching ZIP and checksum from the
[v0.1.0-rc.1 prerelease](https://github.com/mutnpc/wukong-code/releases/tag/v0.1.0-rc.1),
verify the SHA-256 file, extract `wukong.exe`, and keep the previous binary until
the candidate has started successfully against the same Wukong home directory.

## Candidate boundaries

- Stable `latest` remains `v0.0.22` throughout RC validation.
- A blocking candidate defect requires a new prerelease identity; published
  assets and provenance must not be rewritten in place.
- Six-platform public install/upgrade smoke, a Windows real-repository Loop,
  five real Resume-source flows, first-user comprehension, the opt-in cohort,
  and the full 14-day stability window remain release evidence for `0.1.0`.
- Full direct-shell content/PATH attestation, a multi-layer coverage schema,
  provider pricing, hosted execution, payment, quota, Team, and managed models
  are not part of this candidate.
