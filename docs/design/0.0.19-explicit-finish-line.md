# 0.0.19 Explicit Finish Line

> 状态：核心实现已完成，发布验收进行中。
> 目标版本：0.0.19。
> 最后更新：2026-07-25。
> 前置版本：0.0.18 Loop-First Simplification。
> 产品边界：继续 Free、local-first、BYOK；不增加顶层命令，不提供 Wukong 托管模型或推理，不引入支付、quota、Hosted Terminal、云同步、PR Gate、Verification Skill runtime 或 telemetry 指标后端。

## 一句话定义

0.0.18 已把普通用户路径收敛为 `Resume → Loop → Gate`。0.0.19 只解决同一条路径里的一个核心问题：

> **在 Loop 开始前确认“做什么、怎样算完成、哪些事情不能发生、必须跑哪些检查”；启动后冻结这条完成线，任何 Agent 都不能静默降低它。**

版本名 `Explicit Finish Line` 指的是一次 Loop 可见、可确认、可恢复、不可静默弱化的验收合同，不是增加新的计划命令、工作流 DSL、Skill 平台或云端执行层。

## 研究依据与产品校正

本设计吸收以下官方一手资料中的有效原则：

- [Loop engineering: Getting started with loops](https://claude.com/blog/getting-started-with-loops)
- [Building verification loops in Claude Code with skills](https://claude.com/blog/building-verification-loops-in-claude-code-with-skills)
- [Claude Code Goal 文档](https://code.claude.com/docs/en/goal)
- [Claude Code Skills 文档](https://code.claude.com/docs/en/skills)

结论不是照搬 Claude 的命令，而是明确 Wukong 的产品边界：

1. Claude 的 `/goal` 是目标驱动循环，`/loop` 是时间间隔循环；Wukong 的 `/loop` 明确是 **goal-driven, iterate-until-verified delivery loop**，不是 interval scheduler。
2. 自然语言条件和 Verification Skill 可以描述项目特有规则，但不能替代真实 test、lint、typecheck、build 和退出码。
3. Skill 是可复用的验证 recipe，不是不可绕过的最终 Gate；0.0.19 不把 Skill 接入 PASS 决策。
4. Wukong 的差异化不是“也有 `/loop`”，而是 Cross-Agent Resume、本地 BYOK、冻结验收合同、仓库级真实 evidence、fresh reviewer 和可追溯 continuation。
5. `/schedule`、proactive routines、dynamic workflows、PR-wide verification 和托管 grader 均不进入本版本。

## 用户问题

当前 Loop 已能修改、运行 Proof、调用 fresh reviewer 并继续修复，但仍有以下可信度缺口：

1. 用户只输入 objective 时，完成标准可能仍由模型临场解释。
2. `Done when`、必须避免的行为和真实 checks 没有统一出现在启动前确认面板。
3. Gate 只记住 `pnpm test` 之类的命令名时，Agent 可以改写 `package.json` 的 script 正文，让同一命令失去原来的验证意义。
4. 未确认的项目命令可能在 Headless 模式里被直接 shell 执行。
5. Gate 失败和 run 真正结束都可能被表示为 `NEEDS_WORK`，用户无法判断当前是在继续修复，还是已经需要手动 Continue。
6. 终态后的恢复若原地复活旧 run，会改写历史、预算和 blocker 解释。
7. Resume transcript 可能含命令或“完成条件”，但这些外部文本不应自动获得执行权或验收权。
8. 多次 continuation 后，用户看不到任务累计轮次、时间和 token/成本。

## 版本目标

1. `/loop <objective>` 启动前展示简洁、可编辑、可取消的 Finish Line。
2. Finish Line 至少能表达 objective、可选 `Done when`、可选 `Must not` constraints 和必跑 checks。
3. Acceptance Contract 与模型、权限、轮次等 Run Settings 分离。
4. `LoopContractV2` 是对现有 v1 的无损增量升级，不能删除 reviewer 已依赖的验收字段。
5. Gate Plan 冻结精确命令、来源定位和来源定义摘要，而不只冻结显示名称。
6. 所有项目命令在 spawn 前完成 workspace trust、风险分类和 permission 检查。
7. 每次代码、测试、配置或 check 定义变化后，旧 PASS evidence 失效并重新运行完整 Gate Plan。
8. 中间 Gate attempt 与 run terminal result 使用不同的 durable record。
9. `NEEDS_WORK` 终态后的 Continue 创建幂等、可追溯的新 run，不修改旧 run。
10. TUI、Headless、Resume、restart 和 continuation 使用同一合同与 Gate 语义。
11. 0.0.18 遗留的 Kimi/Grok 真实 smoke 和 CLI/Web Feedback contract fixture 作为跨版本发布债务单列，不扩大 0.0.19 核心产品范围。

## 明确非目标

0.0.19 不负责：

- 创建、导入、自动选择、执行或串联 Verification Skill；
- 自动修改 Role、Skill、review policy、`.wukong/checks.json` 或 active contract；
- 时间间隔型 `/loop`、`/schedule`、proactive routine 或 workflow engine；
- GitHub Actions、GitHub App、PR Gate、Team rules 或托管 grader；
- 托管模型、支付、credits、Guest/Free 月度 quota 或 entitlement；
- Hosted Terminal、Hosted Report、session/evidence 云同步或 D1 telemetry；
- 新的顶层 `/contract`、`/criteria`、`/checks`、`/continue` 命令。

可复用 Skill criteria 归 [0.0.20 Reusable Verification Criteria](0.0.20-reusable-verification-skills.md)。

## 核心定义

### Goal

用户要完成的工作。一个 Goal 可以跨多个 run，但不能跨多个 Acceptance Contract。同合同 continuation 复用 `goalId`；Revised Loop 必须创建新的 `goalId`，并通过 lineage 字段关联被替代的 Goal。

### Acceptance Contract

用户最终确认的完成线，包括：

- objective；
- 可选 `Done when`；
- 可选 `Must not` constraints；
- acceptance criteria 与稳定 criterion IDs；
- verification plan；
- frozen Gate Plan；
- 创建来源、版本和 lineage。

合同对 active run 及其同合同 continuation 不可变。

### Run Settings

执行方式，不属于完成标准：

- writer model；
- reviewer model；
- permission mode；
- `maxIterations`；
- `--every` 轮间最小间隔；
- 本 run 的 token/time safety limit。

调整 Run Settings 不能修改合同，也不能把已经失败的 Gate 变成 PASS。

### Run

在一份冻结合同下的一次有界执行。每个 run 有独立 `runId`、预算、开始时间和 terminal result。

### Gate attempt

Loop 内部的一次验证尝试。它可以返回 `NEEDS_WORK` 并把 blocker 注入下一轮，但这不等于 run 已终止。

### Terminal result

run 真正结束时唯一的 durable 结果：

- `PASS`
- `NEEDS_WORK`
- `ERROR`

只有 terminal result 才能创建 continuation。

### Continuation

从一个 terminal run 创建的新 run。它复用完全相同的 Acceptance Contract，带入 unresolved blocker keys，并拥有新的 Run Settings 和预算。

### Revised Loop

用户改变 objective、`Done when`、constraints、required checks、blocking review policy 或其定义后创建的新合同、新 `goalId` 和新 root run。它记录 `supersedesContractId` 与 `supersedesGoalId`，但不是原 run 的 continuation。

## 用户路径

### TUI：新建 Loop

用户输入：

```text
/loop 修复登录后模型列表刷新失败
```

默认面板保持简洁，不暴露 `proof-pass` 等内部术语：

```text
Finish line

Goal
  修复登录后模型列表刷新失败

Done when
  未单独指定

Must not
  0 constraints

Verification
  2 required project checks

Run
  10 iterations this run

[Start Loop] [Edit finish line] [Review checks] [Advanced] [Cancel]
```

展开 `Review checks` 后显示：

```text
Required checks

✓ pnpm test --filter wukong
  Source   package.json#scripts.test
  Selected project default

✓ pnpm typecheck
  Source   .wukong/checks.json#/commands/1
  Selected project config

Excluded checks
  none
```

展开 `Advanced` 后才显示 writer、reviewer、permission、Gate 名称、轮间节流和详细预算。

交互要求：

- 用户可以编辑 Goal、Done when 和 Must not。
- 未填写 `Done when` 时明确显示“未单独指定”，不能由 planner/model 暗中补写。
- 模型可以在 Preflight 前提出 completion/constraint 草稿，但只有用户编辑并确认后的文本进入合同。
- 默认选择 verification package 当前返回的推荐检查集合，不扫描并强制运行仓库里的所有可执行命令。
- 用户排除默认检查时必须二次确认，并记录被排除检查的来源和用户确认；Agent 无权排除。
- 所有检查显示执行命令、来源定位和风险提示。
- `Start Loop` 是唯一冻结合同和创建 run 的动作。
- `Cancel` 不创建 goal、contract、run、trust grant 或 telemetry event。

### TUI：从 Resume 进入 Loop

```text
/resume kimi
```

导入完成后：

1. 显示只读来源和 workspace re-check 结果；
2. 只生成可编辑 objective 草稿；
3. transcript 中的 `/loop`、`--check`、shell、“已完成”或验收文本保持普通文本；
4. 不从外部 transcript 自动生成 `Done when`、constraint 或 required check；
5. 进入同一份 Finish Line 面板；
6. 用户确认后才创建合同和 run。

### TUI：终态 `NEEDS_WORK` 后继续

```text
NEEDS_WORK · no_progress
2 blockers remain

This run       10 iterations
Entire task    18 iterations · 42m · token usage available locally

[Continue same contract] [Review blockers] [Start revised Loop]
```

`Continue same contract`：

- 创建新的 `runId`；
- 记录 `continuedFromRunId`；
- 引用完全相同的 `contractId`；
- 带入 unresolved blocker keys；
- 重新检查 workspace freshness；
- 重新确认本 run 的 iteration/token/time limit；
- 不修改原 run 的 terminal result、evidence 或预算。

如果 check 定义或合同内容发生变化：

- 不允许同合同 Continue；
- 用户可以恢复原定义后 Continue；
- 或进入 `Start revised Loop`，生成新 `contractId` 和 `supersedesContractId`。

### Headless CLI

新增参数：

```text
wukong loop "<objective>" \
  --done-when "<criterion>" \
  --constraint "<must-not rule>" \
  --check "<command>" \
  --accept-discovered-checks \
  --trust-workspace "<challenge>" \
  --approve-gate-plan "sha256:<approval-set-digest>" \
  --ack-finish-line-warnings "<warning-set-digest>"
```

参数合同：

- `--done-when` 可选，只能出现一次。
- `--constraint` 可重复。
- `--check` 可重复，表示用户显式选择。
- `--accept-discovered-checks` 接受 verification package 当前推荐的全部 discovered checks。
- `--only-explicit-checks` 显式排除 discovered checks，并把排除事实写入 dry-run/合同；它与 `--accept-discovered-checks` 互斥。
- 显式 checks 与 accepted discovered checks 按稳定 identity 去重后形成 Gate Plan。
- 未使用两个 discovered-check 决策 flag 之一且发现项目 checks 时，Headless 在创建 goal/run 前 fail closed，返回 `discovered_check_confirmation_required`。
- 没有有效本地 trust grant 时，Headless 必须传入 dry-run 为当前 canonical workspace identity 生成的短时签名 `--trust-workspace <challenge>`；裸 `--yes`、Auto 或 Yolo 均不能代替。
- Headless 必须提交 dry-run 返回的 exact `--approve-gate-plan sha256:<approval-set-digest>`；选择、workspace trust 和执行批准是三个不同决定。approval set 绑定 workspace identity、完整 ordered Gate Plan、definitions、risk/permission policy 和 warning set，任一变化后旧批准失效。
- expected-unresolved placeholder 不可批准或执行；它只阻止 PASS，直到用户通过 Revised Loop 预览并冻结真实定义。
- Finish Line 有 warning 时，Headless 必须传入 dry-run 返回的精确 `warningSetDigest`；编辑 objective、criterion、constraint 或 checks 后旧确认立即失效。
- `--until` 只兼容 `proof-pass`，不重新开放旧多 Gate 语义。
- 非交互模式缺少 objective 继续返回参数错误，不能进入模型。

`--dry-run` 输出完整的 proposed contract、selected/excluded checks、来源、风险和 Run Settings，但不得：

- 写 goal/contract/run record；
- 创建 trust grant；
- 执行 check；
- 调用模型；
- 发送 feedback 或 telemetry。

机器输出统一使用现有 `--output-format text|stream-json` 机制，不新增 `--output json` 或其他冲突 flag。

### 输入限制

为防止持久化、终端渲染和 shell 参数失控：

- objective：1–8,000 个 Unicode 字符；
- `Done when`：最多 4,000 个字符；
- constraint：单条最多 1,000 个字符，最多 16 条；
- explicit check：单条最多 2,000 个字符，合并后最多 24 条；
- contract 序列化后最多 64 KiB；
- check 禁止 NUL、CR、LF 和其他不可见控制字符；
- 所有超限或非法输入必须在任何持久化和执行前失败。

命令中的真实 secret 禁止以内联值进入合同。显式命令、项目配置或 package script 命中已知 credential/token 模式时，在 trust、持久化和执行前返回 `inline_secret_rejected`。用户必须改用不包含 secret 值的环境变量引用或项目 secret 机制；环境变量是否可读取仍受现有 permission ceiling 和用户 OS 权限约束，0.0.19 不承诺完整 process-tree sandbox。

## 数据模型

### 无损 `LoopContractV2`

V2 必须保留现有 v1 reviewer 和 finding 已依赖的字段：

```ts
type LoopContract = LoopContractV1 | LoopContractV2;

interface LoopContractV2 {
  readonly schemaVersion: 2;
  readonly contractId: string;
  readonly supersedesContractId?: string;
  readonly supersedesGoalId?: string;
  readonly goalId: string;
  readonly objective: string;
  readonly completionCriterion?: string;
  readonly constraints: readonly LoopConstraint[];
  readonly finishLineReview: FinishLineReviewV1;
  readonly workspaceTrust?: WorkspaceTrustBindingV1;
  readonly gateApproval: GateApprovalBindingV1;
  readonly acceptanceCriteria: readonly LoopAcceptanceCriterionV2[];
  readonly verificationPlan: readonly LoopVerificationStep[];
  readonly gatePlan: GatePlan;
  readonly reviewPolicy: ReviewPolicyBindingV1;
  readonly source: 'user' | 'planner' | 'fallback';
  readonly createdAt: number;
}

interface LoopConstraint {
  readonly id: string;
  readonly text: string;
}

interface WorkspaceTrustBindingV1 {
  readonly workspaceIdentityDigest: string;
  readonly scope: 'loop-project-checks';
}

interface FinishLineReviewV1 {
  readonly schemaVersion: 1;
  readonly warningPolicyVersion: string;
  readonly finishLineDigest: string;
  readonly warnings: readonly FinishLineWarningV1[];
  readonly warningSetDigest: string;
  readonly acknowledgedWarningIds: readonly string[];
  readonly acknowledgedAt?: number;
}

interface FinishLineWarningV1 {
  readonly id: string;
  readonly code: 'missing_done_when' | 'broad_criterion' | 'conflicting_finish_line' | 'no_resolved_checks';
  readonly field: 'objective' | 'completion_criterion' | 'constraint' | 'gate_plan';
  readonly message: string;
}

interface GateApprovalBindingBaseV1 {
  readonly schemaVersion: 1;
  readonly gatePlanDigest: string;
  readonly warningSetDigest: string;
  readonly guardPolicyVersion: string;
  readonly orderedChecks: readonly {
    readonly checkId: string;
    readonly resolution: RequiredGateCheck['resolution'];
    readonly commandDigest: string;
    readonly definitionDigest?: string;
    readonly sourceLocator?: string;
    readonly riskDigest: string;
    readonly permissionRequestDigest: string;
  }[];
  readonly approvalSetDigest: string;
}

interface ExecutableGateApprovalBindingV1 extends GateApprovalBindingBaseV1 {
  readonly hasExecutableChecks: true;
  readonly workspaceIdentityDigest: string;
}

interface NonExecutableGateApprovalBindingV1 extends GateApprovalBindingBaseV1 {
  readonly hasExecutableChecks: false;
  readonly workspaceIdentityDigest?: never;
}

type GateApprovalBindingV1 =
  | ExecutableGateApprovalBindingV1
  | NonExecutableGateApprovalBindingV1;

type ReviewPolicyBindingV1 =
  | {
      readonly mode: 'blocking-frozen';
      readonly sourceLocator: '.wukong/review-policy.md';
      readonly definitionDigest: string;
    }
  | {
      readonly mode: 'advisory-live';
    };

interface LoopAcceptanceCriterionV2 {
  readonly id: string;
  readonly text: string;
  readonly source:
    | 'objective'
    | 'completion_criterion'
    | 'constraint'
    | 'derived';
}
```

实现约束：

- 新建 0.0.19 合同时，blocking `derived` criterion 必须由用户确认；不能由模型暗中生成。
- `acceptanceCriteria` 是 objective、completion criterion 和 constraints 的稳定投影，reviewer 继续按 criterion ID 返回 finding。
- `verificationPlan` 与现有 reviewer 协议保持兼容。
- `contractId` 使用随机 UUID，不从 objective、路径或用户内容推导，避免跨项目关联。
- criterion/check ID 只要求在合同内稳定，不需要成为全局内容指纹。
- `finishLineDigest` 使用 `wukong/finish-line/v1\0` + objective、nullable completion criterion、ordered constraints 与 proposed Gate Plan digest 的 RFC 8785 canonical JSON/full SHA-256。
- warning IDs 由 versioned canonical warning rules 生成；`warningSetDigest` 使用独立 domain 绑定 warning policy version、`finishLineDigest` 和完整 warning set。TUI 必须逐项显示并由用户确认，Headless 必须确认精确 digest；任何 Finish Line 或 checks 编辑都会使旧 acknowledgement 失效，即使 warning codes 没变化。
- `riskDigest` 绑定 risk policy version、classification、matched rule IDs 与 residual-risk summary；`permissionRequestDigest` 绑定 check 请求的 filesystem/network/environment 能力。两者使用各自 domain separator 的 versioned canonical JSON + full SHA-256。
- `approvalSetDigest` 使用 `wukong/gate-approval/v1\0` domain、RFC 8785 canonical JSON 和 full SHA-256，并排除自身字段；它绑定 workspace identity、Gate Plan digest、ordered check snapshots、source/definition、risk/permission digests、guard policy version 和 warning set。合同持久化前与每次 spawn 前都必须 compare-and-set。
- Gate Plan 含可执行项目 check 时 `workspaceTrust` 必填；只有 expected-unresolved placeholder 或没有项目 check 时可以省略，且不得据此获得未来 check 的执行权。
- 只要存在任一 `resolution: resolved` check，Gate approval 必须使用 `hasExecutableChecks: true` 且包含与 `workspaceTrust` 完全相同的 identity digest；只有全部为 expected-unresolved 或没有 checks 时才允许 non-executable variant。schema/restore 不满足该不变量时 fail closed。
- `supersedesContractId` 与 `supersedesGoalId` 只用于 Revised Loop lineage；新合同必须使用新 `goalId`，不能把新合同伪装成旧 Goal 的 continuation。
- `.wukong/review-policy.md` 若能产生 blocking finding，必须以 `blocking-frozen` 模式冻结 locator 与 definition digest；运行中漂移时先 BLOCK，恢复原定义后可同合同继续，确需采用新定义时才创建 Revised Loop。未冻结的 live policy 只能是 `advisory-live`，只能生成 important/note，不能阻止或授予 PASS。

### V1 identity assignment 与 Goal lineage

旧 V1 合同可能没有 `contractId`，恢复时不能从 objective、路径或 transcript 内容推导 ID。

- 第一次由 0.0.19 恢复时，为原始 `goal.contract.create` record 生成随机 UUID，并 append 一次 `goal.contract.identity.assign`。
- identity assignment 以原始 contract record 的 durable record identity 作为幂等键；崩溃重放只能得到同一个已持久化 ID，不能生成第二个身份。
- 兼容 assignment 不把 V1 改写成 V2，也不伪造 constraints、Gate Plan、warning acknowledgement 或历史 evidence。
- 同合同 continuation 复用原 `goalId` 与兼容 `contractId`。
- Revised Loop 创建新 `goalId`、新 `contractId` 和新 root run，并 append `goal.lineage.create { goalId, supersedesGoalId, contractId, supersedesContractId }`。
- lineage 只表达“后一个任务替代前一个任务”，不允许跨合同合并 iteration budget、terminal result 或 blocker disposition。

### Gate Plan

```ts
interface GatePlan {
  readonly schemaVersion: 1;
  readonly stopCondition: 'proof-pass';
  readonly requiredChecks: readonly RequiredGateCheck[];
  readonly excludedChecks: readonly ExcludedGateCheck[];
  readonly builtinRiskScanPolicyVersion: string;
  readonly planDigest: string;
}

interface RequiredGateCheckBase {
  readonly id: string;
  readonly source:
    | 'explicit'
    | 'package-script'
    | 'workspace-script'
    | 'project-config'
    | 'project-inferred';
  readonly sourceLocator?: string;
  readonly selectedBy: 'user' | 'project-default';
}

interface ResolvedRequiredGateCheck extends RequiredGateCheckBase {
  readonly resolution: 'resolved';
  readonly executionCommand: string;
  readonly displayCommand: string;
  readonly commandDigest: string;
  readonly definitionDigest: string;
}

interface ExpectedUnresolvedGateCheck extends RequiredGateCheckBase {
  readonly resolution: 'expected-unresolved';
  readonly executionCommand: string;
  readonly displayCommand: string;
  readonly commandDigest: string;
  readonly expectedSourceLocator?: string;
}

type RequiredGateCheck = ResolvedRequiredGateCheck | ExpectedUnresolvedGateCheck;

interface ExcludedGateCheck {
  readonly displayCommand: string;
  readonly commandDigest: string;
  readonly source: RequiredGateCheck['source'];
  readonly sourceLocator?: string;
  readonly excludedBy: 'user';
  readonly reason: 'only-explicit' | 'tui-confirmed';
}
```

规则：

- `sourceLocator` 必须是 workspace-relative locator，例如 `package.json#scripts.test`，不能保存绝对路径。
- `definitionDigest` 哈希的是实际赋予命令语义的最小来源定义，例如 package script 正文或 `.wukong/checks.json` 对应条目。
- `executionCommand` 是 restart 所需的精确本地执行值，只能在通过 inline-secret 拒绝后写入本地 durable contract；`displayCommand` 是单向脱敏展示值，日志、UI、错误和导出只能使用它；`commandDigest` 始终基于 execution value，不能基于脱敏文本。
- expected-unresolved check 只是用户确认的未来 finish-line placeholder，不拥有可执行定义，也不能 PASS。运行中出现新 source/definition 时必须返回 `contract_update_required` 并创建 Revised Loop；同合同不得仅凭相同命令字符串接受新定义，更不能接受新出现的 `exit 0`。
- 不直接冻结整个现有 `configDigest`；lockfile、review policy 等无关变化不能制造伪 blocker。
- `planDigest` 使用 `wukong/gate-plan/v1\0` + stop condition、canonical required/excluded check snapshots 和 `builtinRiskScanPolicyVersion` 的 RFC 8785 canonical JSON/full SHA-256；scan policy 变化与 check definition 变化一样必须恢复原定义或创建 Revised Loop，不能在 active contract 中热升级/降级。
- required checks 是有序列表；顺序来自显式参数顺序或 verification package 的稳定选择顺序，并在合同中冻结。
- 展示值可以脱敏，但执行值、display value 和 digest 输入必须有明确转换规则，不能因脱敏后碰撞。

durable 规则：

- `goal.contract.create`、`goal.contract.identity.assign`、`goal.lineage.create`、`loop.run.create`、`loop.gate-attempt.create`、`loop.gate-check-result.create`、`loop.builtin-risk-scan-result.create`、`loop.reviewer-result.create`、`loop.proof-aggregate.create`、`loop.evidence-snapshot.create`、`loop.gate-attempt.complete`、`loop.run.terminal` 和 `loop.continuation.create` 为 append-only。
- `attemptId` 是随机 UUID；`sequence` 只用于同 run 展示排序，不能作为 durable join key。
- contract 只冻结 workspace identity 与 trust scope；每次 attempt 的 evidence 记录实际使用的本地 `workspaceTrustGrantId`。session grant 过期或 remembered grant 被 revoke 后可以为同一 identity 重新授权，不需要修改合同，但不得复用旧 grant。
- append 顺序固定为 `GateAttemptCreatedV1 → ordered GateCheckResultRecordedV1 → BuiltinRiskScanResultRecordedV1 → ReviewerResultRecordedV1 → ProofAggregateRecordedV1 → LoopEvidenceSnapshotCreated → GateAttemptCompleted`。evidence snapshot 必须先于 completion 落盘；全链的 `attemptId`、`runId`、`contractId`、`planDigest`、approval/blocker/input/result digests 必须完全一致。
- `orderedCheckResults` 必须按冻结 Gate Plan 顺序恰好覆盖全部 required checks，不能缺失、重复或插入未知 ID；expected-unresolved 使用 `unresolved` result，绝不能伪装成 executed/pass。每个完整 attempt 还必须恰有一个同 attempt/plan/workspace 的 builtin scan、reviewer result 与 Proof aggregate。
- 所有下面列出的 digest 都使用 UTF-8、RFC 8785 canonical JSON、full SHA-256，排除自己的 digest 字段，并以给定 domain separator 开头：
  - `checkResultDigest`：`wukong/gate-check-result/v1\0` + 完整 `GateCheckResultRecordedV1`；`stdoutDigest`/`stderrDigest` 分别对 versioned、bounded、已脱敏的输出 bytes 计算，raw secret-bearing output 不进入 record。
  - `scanResultDigest`：`wukong/builtin-risk-scan-result/v1\0` + 完整 `BuiltinRiskScanResultRecordedV1`，包括 policy version、workspace fingerprint、status 和 ordered finding refs/digests/severity；finding ref 指向 immutable local payload，payload 正文按现有 privacy/redaction policy 处理。
  - `reviewerInputDigest`：`wukong/reviewer-input/v1\0` + `{ attemptId, contractId, planDigest, workspaceFingerprint, orderedCheckResultDigests, scanResultDigest, carriedBlockerSetDigest, reviewPolicyBinding }`。
  - `reviewerPayloadDigest`：`wukong/reviewer-payload/v1\0` + 现有 versioned `ReviewResult` canonical payload；`INCONCLUSIVE` 使用 versioned normalized error payload，不能存任意原始模型文本。
  - `reviewerResultDigest`：`wukong/reviewer-result-record/v1\0` + 完整 `ReviewerResultRecordedV1`。
  - `proofAggregateDigest`：`wukong/proof-aggregate/v1\0` + 完整 `ProofAggregateRecordedV1`，必须绑定 ordered checks、builtin scan、reviewer、prior blockers、status 和 reason code。
  - `evidenceDigest`：`wukong/loop-evidence-snapshot/v1\0` + 完整 `LoopEvidenceSnapshotCreated`，必须绑定 approval、workspace、ordered checks、builtin scan、reviewer 和 aggregate refs/digests。
  - `resultDigest`：`wukong/gate-attempt-result/v1\0` + 完整 `GateAttemptCompleted`。
- builtin scan 只有 `status: clean` 才能参与 PASS；`blocking` 或 `error` 必须阻止 PASS。缺失、重复、policy/workspace drift 或 digest 不一致一律 `record_corrupt`。
- scan `clean` 时不得含 blocking finding，`blocking` 时必须至少含一个 blocking finding；status/finding severity 矛盾按 `record_corrupt` 处理。
- `ProofAggregateRecordedV1.status: PASS` 只允许全部 required checks 为 `passed`、builtin scan 为 `clean`、reviewer result 精确为 `PASS`、carried blockers 全部有有效解决 disposition，且所有 refs/digests fresh；`NEEDS_WORK`/`INCONCLUSIVE` reviewer 或任一 blocker 不能被 aggregate 改成 PASS。
- PASS terminal 必须携带 `terminalAttemptId` 和 `attemptResultDigest`，且引用 attempt 的 `runId`/`contractId`/status/result digest 必须完全一致；该 attempt 必须覆盖完整 Gate evidence、没有 unresolved/non-pass check，拥有同 workspace/policy 的唯一 clean builtin scan，以及有效 reviewer/aggregate。任何缺失、孤儿、错状态或 digest 不一致均返回 `record_corrupt`，不得恢复为 PASS。
- 非 PASS terminal 只有在确实完成 Gate attempt 时才同时填写 `terminalAttemptId` 与 `attemptResultDigest`；因 preflight、取消或环境错误提前结束时两者必须同时省略。只填一个、状态/digest 不一致或将无 attempt terminal 映射为 PASS 均为 `record_corrupt`。
- `terminalDigest` 使用 `wukong/loop-terminal/v1\0` + terminal 中除自身外全部字段的 RFC 8785 canonical JSON/full SHA-256。
- 崩溃留下的孤儿 evidence 可以在 replay 后安全清理或忽略，但不能被另一 attempt 认领。
- 中间 Gate `NEEDS_WORK` 只写 attempt record，不产生 terminal record。
- continuation 只能基于 terminal record 创建。
- TUI、Headless 和恢复逻辑只能读取 terminal record 中唯一的 `continuationPolicy`；不得再根据 status、reason code、`retryable` 或 `requiresRevisedContract` 各自推导不同结论。
- 同一 terminal run + idempotency key 只能创建一个 continuation run。
- 双击、并发请求或任一写入点崩溃后，replay 不能产生两个 active run、孤儿 parent link 或被覆盖的旧结果。
- 现有可覆盖写的 loop-run JSON 只能作为可重建索引，不能继续作为 authoritative history。

## 合同创建与冻结

创建顺序固定为：

1. 取得 objective；
2. 取得可选 `Done when`；
3. 取得可选 constraints；
4. 运行只读 verification discovery；
5. 合并显式 checks；
6. 解析 canonical workspace identity，检查现有 trust，并完成风险分类和 permission preflight；
7. 展示 selected/excluded checks、Finish Line warnings、trust 状态和剩余 shell 风险；
8. 用户确认 Finish Line、warning、workspace trust intent 与每个 check；
9. 原子或可恢复地写入所需 trust grant，并 append contract + initial run records；
10. 启动 writer。

第 8 步前的内容是 proposal，不是合同，trust 选择也只是待提交 intent；Cancel 不得留下 grant。第 9 步后，以下主体均无权修改 active contract：

- writer；
- reviewer；
- strategist；
- resume importer；
- compaction；
- 自动恢复逻辑；
- project Skill、Role 或 plugin。

用户改变 objective、`Done when`、constraint、required check 或 Gate 定义时，必须创建 Revised Loop。0.0.19 不支持 active contract revision。

## Workspace trust 合同

选择一个 check 不等于信任整个仓库；workspace trust、Gate selection 和 command permission 是三个独立决定。

```ts
interface WorkspaceTrustGrantV1 {
  readonly schemaVersion: 1;
  readonly trustGrantId: string;
  readonly canonicalRealpath: string;
  readonly workspaceIdentityDigest: string;
  readonly scope: 'loop-project-checks';
  readonly persistence: 'session' | 'remembered-local';
  readonly createdAt: number;
  readonly revokedAt?: number;
}
```

identity 规则：

- 启动 Preflight 时先 `realpath` workspace；不存在、不可读、root 自身 symlink 解析失败或 selected locator 逃逸 canonical root 时 fail closed。
- `workspaceIdentityDigest` 绑定 canonical realpath、可取得时的 filesystem identity，以及 Git workspace 的 common-dir identity；只用 remote URL、显示路径或当前 branch 不足以建立 trust。
- canonical identity 在确认与 spawn 之间变化时，旧 grant/challenge 失效并返回 `workspace_trust_mismatch`。
- remembered grant 只保存在本机权限受限的 trust store，绝不进入合同、导出、feedback、telemetry 或 crash payload；合同只冻结 identity digest 与 scope，本地 evidence 可记录实际 grant 的随机 ID 供审计。
- trust 只允许进入项目 check permission preflight，不批准具体命令、网络、secret、workspace 外写入或未来新增 check。

TUI 首次进入未知 workspace 时显示：

```text
Trust this workspace before running project checks?

Canonical path   /real/path/to/project
Identity         2f9c…81a0
Selected checks  2
Risk summary     shell commands; network denied

[Trust once] [Remember locally] [Cancel]
```

- `Trust once` 只在当前 session 有效；session 结束自动失效。
- `Remember locally` 写入本地 grant；用户可在 `/settings → Security → Trusted workspaces` 查看并 revoke。
- revoke 立即使后续 Gate 和 continuation fail closed；已经运行的历史 evidence 保持不可变，但不能作为 revoke 后的新 PASS。
- `Cancel` 不创建 trust grant、合同、run 或 telemetry event。

Headless：

- dry-run 的 `stream-json` 输出 canonical identity、风险摘要、短时签名 trust challenge，以及完整 `approvalSetDigest`。
- challenge 是不落盘的 tamper-evident envelope，绑定 canonical identity、`approvalSetDigest`、warning digest、签发时间和最多 10 分钟 expiry；无有效 remembered grant 时必须原样提交。
- challenge 在有效期内只能批准完全相同的 proposed contract；复用它不能批准任何新命令、定义或风险等级。0.0.19 不声称 stateless challenge 具备跨进程单次消费语义。
- 必须通过 `--approve-gate-plan sha256:<approval-set-digest>` 批准完整 ordered snapshot；`--accept-discovered-checks` 只表示选择，不等于执行批准。
- cwd/realpath/identity、selected checks、definition digest 或风险等级变化都会使 challenge 和 check approvals 失效。
- Headless 不提供隐式 remember；revoke remembered grant 通过 TUI Settings 或删除 trust store 中精确匹配的 grant 完成，不能用宽目录 glob。

## Checks 选择与适用性

### 初始发现

0.0.19 复用现有 verification package 和 `.wukong/checks.json`，不发明第二套项目配置。

可用来源：

- `explicit`
- `project-config`
- `package-script`
- `workspace-script`
- `project-inferred`

“发现”不等于“仓库里的所有工具都必须运行”。初始默认集合只来自 verification package 当前的稳定选择策略，并遵循现有 docs-only/source-change Proof policy。

TUI 用户可以排除默认检查，但必须看见影响并确认。Headless 用户必须通过明确 flag 选择接受 discovered checks 或只使用 explicit checks。

### 运行中新发现的检查

active contract 不动态扩展：

- 新发现 check 可以显示为 suggestion。
- writer 可以在普通工具权限下自行运行它，但结果只是辅助 evidence。
- 新 check 不自动获得 required 或 PASS 决策权。
- 若用户希望它成为 required check，必须创建 Revised Loop。
- “为项目补测试”的目标可以在 Preflight 中由用户显式填入预期最终命令，但只能冻结为 `expected-unresolved` placeholder。它在新定义出现前始终阻止 PASS；新定义出现后返回 `contract_update_required`，用户必须在 Revised Loop 中预览并确认实际定义摘要。

这避免 TUI 等待中途确认，也避免 Headless 挂起、偷偷执行或隐式改合同。

## Trust、权限与 shell 安全

required check 是可信仓库中的真实 shell 命令，不是普通文本。0.0.19 在 spawn 前完成 workspace trust、精确 source preview、per-check selection、现有 permission ceiling 和 best-effort 静态风险分类；它不新增完整跨平台 sandbox，也不能证明任意 package script 的隐藏行为安全。

### 权限不变量

- project/discovered check 在 workspace trust 前不得执行。
- 用户显式 `--check` 或接受 discovered check 表示选择该精确命令和来源，不表示绕过全局 deny/guard。
- permission profile 是执行上限，合同不能扩权。
- best-effort guard 能识别的 destructive、网络外传、credential/env 读取和 workspace 外写入风险，必须在 spawn 前 BLOCK 或进入现有显式 permission 流程。
- Headless 必须同时具备有效 workspace trust 与完整 `approvalSetDigest`；缺少任一项都 fail closed，Auto/Yolo/`--yes` 不能补齐。
- 通过确认后，可信仓库的 package/script 仍按用户当前 OS 权限运行。脚本内部动态导入、间接联网、子进程和隐藏写入无法靠字符串 guard 静态证明；Preflight 必须明确披露这一剩余风险，文档不得宣传“任意 shell 已隔离”。
- 真正的 filesystem/network/environment process-tree sandbox 与 command recipe 后置到 0.0.21+ 候选；0.0.20 只复用 qualitative criteria，不能反向把普通 0.0.19 shell check 标记为 sandboxed safe subset。
- reviewer、strategist 和未来 Verification Skill 无权给 check 提权。
- Headless 不得因为无人交互而默认批准。

### 负向保证

对于 guard 可识别并已拒绝的 fixture，自动化必须证明：

- 子进程从未 spawn；
- 目标文件仍存在；
- sentinel HTTP server 收到 0 个请求；
- secret sentinel 未进入 stdout/stderr、record、feedback、telemetry 或 crash payload；
- reason code 稳定且结果不是 PASS。

以上零 spawn/sentinel 保证只覆盖 guard 已识别或 permission 已拒绝的命令，不构成对任意可信仓库脚本内部行为的静态安全证明。

## Gate Plan 与 anti-weakening

### 什么可以修改

Agent 可以正常修改：

- 产品实现代码；
- 测试代码；
- 文档；
- 与目标有关的普通配置。

Agent 不能在同合同 active run 中静默修改：

- selected package script 的定义；
- `.wukong/checks.json` 中 selected 条目；
- selected workspace script 的来源定义；
- required command 或 provenance locator；
- active contract、Gate Plan 或 frozen blocking review policy。

若目标本身就是修改这些 Gate 定义，当前 run 应返回 `contract_update_required`，用户以新定义启动 Revised Loop。`advisory-live` policy 可以变化，但只能生成 important/note，既不能阻止也不能授予 PASS。

### 执行前比较

每次 Gate 前：

1. 重新解析 selected check 的 source locator；
2. 重算 `definitionDigest`；
3. 解析并比较冻结的 builtin risk-scan policy version；
4. 比较冻结 `planDigest`；
5. 比较 blocking review policy binding；
6. 完成 trust、Gate approval-set CAS、permission 和 best-effort guard；
7. 只有全部一致才允许执行。

| 情况 | 行为 |
|---|---|
| required definition 完全一致 | 允许执行 |
| required source 消失 | `frozen_check_missing`，不得 spawn |
| command 或 source definition 变化 | `gate_plan_changed`，不得执行新定义 |
| project config 删除或选中条目变化 | `gate_plan_changed` |
| expected-unresolved 尚无定义 | `check_definition_unresolved`，不得 PASS |
| expected-unresolved 出现任何新定义 | `contract_update_required`，不得执行；进入 Revised Loop 预览并冻结 |
| frozen blocking review policy 变化 | `review_policy_changed`，不得进入 reviewer；恢复原定义或 Revised Loop |
| builtin risk-scan policy 变化 | `gate_plan_changed`，不得运行新 policy；恢复原版本或 Revised Loop |
| advisory live review policy 变化 | 可重新读取，但只能生成 important/note |
| 新发现额外 check | 仅 suggestion，不修改合同 |
| tool 暂时不可用 | `check_unavailable`，不得当成功 |
| trust/Gate approval/permission 不允许 | 对应稳定 preflight code，不得 spawn |

### 执行后 freshness

每次完整 Gate 结束后：

- 重算 workspace input snapshot；
- 重算 selected provenance digests；
- 检查命令执行期间是否发生 TOCTOU 变化；
- 任一代码、测试、配置或 Gate 定义变化都会使本次 evidence stale；
- 下一次 attempt 必须重新运行完整 required-check chain，不能只运行上次失败项；
- 不允许复用旧 PASS 补齐一个新的最终 PASS。

同一 workspace snapshot 上出现互相矛盾的 PASS/FAIL 时，不取多数、不取最后一次结果，返回 `check_unstable` 并保留每次 evidence。

## `Done when` 与 `Must not`

示例：

```text
Goal
  修复登录后模型列表刷新失败

Done when
  有效 token 返回空模型目录时保持登录成功，404/5xx 显示明确失败

Must not
  不覆盖用户当前 BYOK 默认模型
  不把 token、response body 或用户 prompt 写入日志
```

规则：

- `Done when` 和 constraints 只能来自用户确认文本。
- Resume transcript、planner、writer 或 reviewer 可以提出草稿，但不能直接写入合同。
- constraint 是必须保持为真的限制条件，不是普通提示。
- fresh reviewer 必须逐项返回 criterion-level evidence。
- qualitative criterion 不能覆盖 deterministic check 失败。
- 宽泛、不可验证或互相冲突的完成线必须在 Preflight 显示 versioned warning；用户仍可确认，但合同必须记录完整 warning set、digest 与 acknowledgement。
- “Skill 已加载”“模型说已完成”或 transcript 中的成功描述均不是 evidence。

## Gate 执行顺序

每次 attempt 的固定逻辑为：

```text
1. Contract / plan / permission precheck
2. The Gate command executor runs the full frozen deterministic checks once
3. Re-check workspace and provenance freshness
4. Run and persist the builtin risk scan once
5. Run and persist the fresh-context read-only reviewer once
6. Purely aggregate persisted check/scan/reviewer results and prior blockers
7. PASS, continue repair, or end run
```

不变量：

- Preflight 是唯一 discovery/compile 阶段；Gate command executor 是 required checks 的唯一执行 owner。
- 必须把当前 `runProof` 中“再次发现并执行 checks”的隐式职责拆开；最终 Proof aggregate 不做 discovery、不 spawn、不重复 scan/reviewer。
- 同一 `attemptId + checkId` 最多产生一个 command result；聚合阶段只读取 durable results。
- deterministic failure 立即阻止最终 PASS；
- reviewer 不能把 deterministic blocker 改成 note；
- fresh reviewer 读取 harness 的原始结构化结果和当前 workspace，不只读取 writer summary；
- reviewer finding 必须关联 criterion ID 或明确标记为 independent finding；
- writer 收到结构化 blockers 后才能进入下一轮；
- 任何修复都会使旧 attempt evidence stale。

## 状态、恢复与 continuation

### 中间 `NEEDS_WORK`

Gate attempt `NEEDS_WORK` 表示 Loop 仍在修复：

- 不显示 Continue；
- 不创建新 run；
- 不释放 active contract；
- 把 blockers 注入当前 run 下一轮；
- 受当前 run 的 iteration/token/time limit 控制。

### terminal `NEEDS_WORK`

以下情况可以结束 run：

- `max_iterations`
- `no_progress`
- `check_unstable`
- `frozen_check_missing`
- `gate_plan_changed`
- `review_policy_changed`
- `contract_update_required`
- 用户明确停止且现有 lifecycle 映射为 NEEDS_WORK

只有 terminal record 出现后，TUI 才能显示 Continue 或 Revised Loop。

### restart

未终态 run 重启后：

- 恢复同一 `runId`、contract、Gate Plan、prior blockers 和 Run Settings；
- 未完成、过期或无法证明原子完成的 attempt 必须重新执行；
- 重新检查 workspace、input、provenance 和 plan freshness；
- 不重新询问未变化的合同；
- 不复用 stale PASS。

### continuation

terminal record 中持久化的 `continuationPolicy.mode` 是 TUI、Headless 和 restart 的唯一决策来源：

- `same-contract`：允许用户手动 Continue；创建新 run 前仍须完整重做 trust、permission、workspace、Gate Plan 和 review-policy preflight。
- `restore-or-revise`：只有用户把冻结的 check/review 定义原样恢复并通过 preflight，才允许同合同 Continue；否则只能创建 Revised Loop。
- `revised-loop`：当前合同不能继续；必须以新 `goalId`、新合同和 lineage 启动 Revised Loop。
- `blocked`：不提供 Continue；包括 PASS、用户取消、permission/security denial、未知 ERROR、record corruption 或无法证明 parent terminal。

所有模式的 `automaticRetry` 都是 `false`。UI 不得从 status/reason code 猜测按钮，也不得保留旧的 `retryable`、`requiresRevisedContract` 分支；reason code 到 policy 的映射只在写 terminal record 时由一个共享函数完成。

continuation 使用相同合同，但显示：

- 本 run 新预算；
- chain 累计 iterations；
- chain 累计时间；
- 可取得时的累计 token/模型成本；
- carried blocker 数量。

## 稳定 reason codes

### Preflight / 参数阶段

| reason code | 行为 |
|---|---|
| `discovered_check_confirmation_required` | Headless 未决定如何处理 discovered checks；零副作用退出 |
| `workspace_trust_required` | 没有有效本地 grant 或本次精确 challenge；不得创建合同或 spawn |
| `workspace_trust_mismatch` | canonical workspace identity、selected checks 或风险摘要与 grant/challenge 不一致 |
| `gate_approval_required` | 完整 approval-set digest 缺失；不得 spawn |
| `gate_approval_mismatch` | workspace/plan/definition/order/risk/permission/warning 与 approved snapshot 不一致；不得持久化或 spawn |
| `check_permission_required` | check 未获执行权限；不得 spawn |
| `finish_line_warning_ack_required` | warning set 未逐项确认，或 Headless digest 缺失/过期 |
| `inline_secret_rejected` | execution command 含疑似内联 credential/token；不得持久化或 spawn |
| `invalid_finish_line` | 输入为空、超限、含非法控制字符或合同总大小超限 |

### Gate attempt / terminal

| reason code | 状态 | persisted continuation policy | 行为 |
|---|---|---|---|
| `passed` | PASS terminal | `blocked` | 已完成，不可 Continue |
| `check_failed` | NEEDS_WORK attempt | 无 | active run 内继续修复 |
| `tests_missing` | NEEDS_WORK attempt | 无 | active run 内继续修复 |
| `check_definition_unresolved` | NEEDS_WORK attempt | 无 | placeholder 仍未实现，不能 PASS |
| `no_progress` | NEEDS_WORK terminal | `same-contract` | 用户可手动增加本 run 预算后 Continue |
| `max_iterations` | NEEDS_WORK terminal | `same-contract` | 用户可手动增加本 run 预算后 Continue |
| `check_unstable` | NEEDS_WORK terminal | `same-contract` | 用户稳定环境后手动 Continue |
| `frozen_check_missing` | NEEDS_WORK terminal | `restore-or-revise` | 恢复原定义，或 Revised Loop |
| `gate_plan_changed` | NEEDS_WORK terminal | `restore-or-revise` | 恢复原定义，或 Revised Loop |
| `review_policy_changed` | NEEDS_WORK terminal | `restore-or-revise` | 恢复冻结 policy，或 Revised Loop |
| `contract_update_required` | NEEDS_WORK terminal | `revised-loop` | 新定义必须重新预览并冻结 |
| `check_unavailable` | ERROR terminal | `same-contract` | 环境修复后由用户手动 Continue |
| `reviewer_unavailable` | ERROR terminal | `same-contract` | reviewer 恢复后由用户手动 Continue |
| `workspace_changed` | ERROR terminal | `same-contract` | workspace 稳定并通过 preflight 后手动 Continue |
| `verification_error` | ERROR terminal | allowlist 内为 `same-contract`，否则 `blocked` | 映射必须由共享 allowlist 固定 |
| `permission_denied` | ERROR terminal | `blocked` | 不允许 Continue |
| `record_corrupt` | ERROR terminal | `blocked` | 不允许恢复为成功或 Continue |

未知 ERROR 一律持久化 `blocked`。用户显式取消也持久化 `blocked`，不能通过换 UI 或重启变成可续跑。

`continuation_created` 是事件类型，不是 reason code。

## Privacy 与数据边界

新增本地字段包括 objective、completion criterion、constraints、contract/run IDs、blocker keys、evidence metadata，以及恢复冻结 Gate 所需的精确 `executionCommand`。

边界：

- 这些字段只可按 durable recovery 需要保存在用户本机；`executionCommand` 只有通过 inline-secret 拒绝后才可进入本地 contract。
- 不发送到 Wukong Web、D1、feedback、telemetry 或 crash payload。
- BYOK 模型调用仍按用户选择的 provider 工作；“不发送到 Wukong”不能误写成“完全不出网”。
- UI、日志、错误、导出和诊断只使用单向脱敏的 `displayCommand`，不得回显或导出 `executionCommand`；durable contract 是唯一允许保存精确执行值的 record。
- stdout/stderr 必须有界保存并经过 secret redaction；启发式 redaction 是 defense-in-depth，不能替代对已知 inline secret 的 pre-persistence 拒绝。
- evidence 默认保存摘要、exit code、duration、file:line 和 digest，不保存无限 stdout/stderr。
- `contractId` 使用随机 UUID，不能由内容生成。
- canonical path、filesystem/Git identity 和 remembered trust grant 只存在本机权限受限 trust store；合同仅保留 identity digest 与 scope，本地 evidence 只引用随机 grant ID。
- 共享隐私 fixture 使用唯一 sentinel 覆盖所有 outbound payload。

- 同合同 continuation 复用 `goalId`；Revised Loop 创建新 `goalId`/`contractId` 并持久化双向可查的 supersedes lineage。

### P0：Gate anti-weakening

- 冻结 `pnpm test` 后把 script 从真实测试改为 `exit 0`，必须在 spawn 前 `gate_plan_changed`。
- `.wukong/checks.json` 删除、改写、重排 selected entry 均不得 PASS。
- selected workspace script rename/symlink escape 必须 fail closed。
- 只改变无关 lockfile 或 `advisory-live` policy 不应制造 Gate 定义 drift；frozen blocking review policy 变化必须返回 `review_policy_changed`。
- expected-unresolved check 在定义不存在时不能 PASS；同合同中新出现的真实定义（包括 `exit 0`）必须零 spawn 返回 `contract_update_required`，只能由 Revised Loop 预览并冻结。
- digest 检查后、命令结束前发生 TOCTOU 修改时，本次 evidence 作废。
- 修复代码后重新运行完整 required plan。
- 同一 attempt 的每个 required check 只执行一次；Proof aggregate 不重新 discovery 或 spawn。
- 同一 attempt 的 builtin risk scan 恰好运行并持久化一次；Proof aggregate 不重复 scan，scan 缺失/重复/policy drift 均不能 PASS。
- 同一 snapshot 上矛盾 PASS/FAIL 返回 `check_unstable`。
- deterministic blocker 不能被 reviewer 覆盖。

### P0：Workspace trust、权限与隐私

- canonical realpath、filesystem/Git identity、root symlink 解析失败和 locator escape 均有 fixture；identity 变化使 remembered grant 与 Headless challenge 失效。
- resolved check + missing/mismatched approval workspace identity 在 schema/restore/spawn 前 fail closed；non-executable approval 只允许空 plan 或纯 expected-unresolved plan。
- `Trust once` 在 session 结束后失效；`Remember locally` 可列出并精确 revoke；revoke 后 future Gate/continuation fail closed，历史 evidence 不变。
- TUI Cancel 与 Headless dry-run 不创建 trust grant、contract 或 run；Headless 缺少精确 workspace challenge 或 Gate approval-set digest 时 fail closed。
- 对 guard 可识别的 destructive/network fixture，spawn 计数为 0、目标文件保持存在、sentinel server 收到 0 请求；测试名称和文档不得把该保证扩大到任意 package script。
- 可信脚本的隐藏 dynamic import/network/write 不宣称可静态证明安全；Preflight 必须显示其按当前 OS 权限执行的剩余风险。
- provider secret、源码 sentinel 不进入 record、feedback、telemetry 或 crash payload。
- 含内联 credential/token 的 explicit/project/package command 在 trust、持久化和 spawn 前返回 `inline_secret_rejected`。
- Headless 未确认 discovered check 时 fail closed。
- Headless 缺少、过期或 digest 不匹配的 exact approval set 时零 spawn；同 execution command 但 definition/source/risk/workspace/order 不同的 fixture 必须得到不同 digest。`--accept-discovered-checks`、Auto、Yolo 和 `--yes` 均不能代替。
- permission deny 优先于 explicit check selection。
- 本地 contract 可恢复精确 `executionCommand`，但 UI/log/error/export 只出现 `displayCommand`；bounded stdout/stderr 与所有 outbound payload 使用同一 redaction sentinel。

### P0：Gate attempt、恢复与 continuation

- 中间 `NEEDS_WORK` 继续当前 run，不显示 Continue。
- terminal `NEEDS_WORK` 才允许创建 continuation。
- evidence/attempt 以随机 `attemptId` 和 digest join；sequence 不作主键，缺失/错配/孤儿 evidence 或无效 `terminalAttemptId` 返回 `record_corrupt`，绝不恢复为 PASS。
- PASS terminal 强制引用同 run/contract/plan 且 status/result digest 一致的完整 attempt；缺 check、unresolved check、缺/重复/非 clean scan、缺 reviewer/aggregate/snapshot 或引用 NEEDS_WORK attempt 均 fail closed。
- check/scan/reviewer/aggregate/snapshot/completion 每种 canonical digest 都有 RFC 8785/domain separator/self-field exclusion golden fixture 与跨实现 replay fixture。
- Continue 双击、并发和重试使用 idempotency key，只创建一个新 run。
- contract append、run create、continuation link 每个写入点 fault injection 后均可 replay。
- 原 run terminal/evidence/预算不可变。
- restart 恢复同一 active run，未完成 attempt 重新执行。
- carried blockers 逐项 `resolved` / `still-open` / `replaced-by`。
- 所有入口只读取 persisted `continuationPolicy`：`same-contract`、`restore-or-revise`、`revised-loop`、`blocked` 的按钮与行为一致，且永不自动 retry。
- Revised Loop 使用新 Goal/contract/root run 和 lineage，不伪装 continuation、不合并预算或 terminal result。
- ERROR allowlist 映射为用户手动 `same-contract`，未知错误、permission denial 和 corruption 持久化 `blocked`。

### P1：真实项目与重复稳定性

- Node、Python、Rust、Go 与 monorepo 的 source locator/digest 行为。
- docs-only 无 checks 继续遵循现有 Proof policy。
- source-code change 无可信 checks 不得宣称已验证 PASS。
- fresh process/session 不复用旧 evidence。
- 同一 fresh fixture 连续至少 3 次产生相同 check 顺序、终态和 reason code。
- macOS、Linux、Windows 覆盖引号、空格、`$`、`&&`、反斜杠、Unicode、timeout、cancel 和 process-tree kill。

### P1：Resume、Feedback 与发布债务

- Codex、Claude Code、Cursor、Kimi Code、Grok 只生成 editable objective draft。
- Kimi/Grok 真实本机会话完成 Resume → Finish Line → Loop smoke。
- CLI/Web Feedback 正向与隐私负向 fixture 一致。
- production feedback 使用固定 synthetic marker 并精确清理。
