# 0.1.0 Trusted Local Loop

> **状态：PARTIALLY IMPLEMENTED / 未达 RC / 未发布。**
> 目标版本：0.1.0。
> 最后更新：2026-08-06。
> 已发布基线：[0.0.22](../releases/0.0.22.md)；兼容验证继续覆盖 0.0.21 records。
> 产品边界：Free、local-first、BYOK；不增加付费、quota、托管执行或新的默认命令。

当前开发分支已具备部分 durable terminal、provider outcome unknown guard 和结果摘要，
consolidated Preflight 汇总已经部分实现；稳定 phase event、完整 usage/call attribution、无 check 显式
确认以及本文件的全部跨平台 Gate 尚未验收。任何已实现条目都不表示
`0.1.0-rc.1` 已发布。

## 一句话定义

> **0.1.0 是第一版可以向普通开发者稳定推荐的 Wukong Code：从明确的完成线开始，在用户当前 workspace 中持续写、检查、审查和修复，直到一个完整且新鲜的 Gate attempt 得出可信结论。**

0.1.0 是稳定化里程碑，不是功能堆叠版本。它不引入新的 Loop 执行架构，
而是冻结并打磨 0.0.14–0.0.22 已发布的 Resume、Finish Line、durable
lifecycle、Verification Criteria、evidence broker 和 Gate。

计划发布顺序是：

```text
0.0.22
  → 0.1.0-rc.1
  → RC 真实项目与外部用户验证
  → 0.1.0
```

0.0.22 已作为 provider catalog resilience 与 CLI clarity 维护版本发布，不改变
0.1.0 的功能范围。若 0.1.0 前再出现生产 P0，只能另行决定是否发布紧急补丁，
不能借补丁版本加入本设计之外的新功能。

## 1. 版本决策

1. **稳定现有单 Loop。** `/loop` 继续复用现有 Goal engine，在用户确认的
   当前 workspace 中执行。
2. **冻结公开合同。** 0.1.0 发布后，Goal、Acceptance Contract、Gate
   attempt、terminal result、continuation 和 reason code 构成稳定兼容面。
3. **不重新引入已取消架构。** isolated worktree、Candidate Gate、Safe
   Promote、target Final Gate、lease/fencing 和 Windows FFI 不属于 0.1.0。
4. **不扩张默认命令面。** 普通入口仍是 editable Goal 或 optional Resume → Loop → Gate；高级命令
   保留实现和直接调用能力，但默认隐藏。
5. **不收费。** 本地 BYOK Loop 不需要 Wukong 登录，不按 Loop、轮次或
   用户自己的 token 设置额度。
6. **先证明可重复使用。** 只有安装、恢复、跨平台、真实项目和外部重复使用
   门槛通过，才发布正式 0.1.0。

## 3. 用户承诺

0.1.0 的完整用户路径必须是：

```text
Install or Upgrade
  → Configure and smoke-test an exact BYOK provider/model
  → Start from an editable Goal or Resume draft
  → Review one consolidated Preflight
      - Goal / Done when / Must not
      - required checks or explicit no-executable-check acknowledgement
      - current workspace and pre-existing dirty changes
      - exact provider/model and outbound input summary
      - iteration, provider-call and optional token limits
  → Confirm and run
  → Write → Check → Review → Fix
  → Gate verdict: PASS / NEEDS_WORK / ERROR
     or lifecycle result: STOPPED_BY_USER
  → Review changed files, checks, provider usage, blockers and next action
  → Resume, Continue, Revise or End
```

用户不需要理解内部 schema、digest 或 record 才能完成流程。每个终态都必须
回答三个问题：

1. 发生了什么；
2. 哪一项 evidence 或运行条件决定了结果；
3. 用户下一步可以安全地做什么。

这是 0.1.0 的目标合同：Goal、workspace trust 和 provider consent 集中在一个可编辑
Preflight 中；高级合同字段默认折叠。当前开发 TUI 已先给出一份共享语义的最终汇总，
覆盖 exact Finish Line/checks、dirty paths、Provider、权限、出站边界、审批顺序与结果
处理；本地 broker read、provider transmission、permission 和 workspace check trust 仍按
安全边界顺序单独授权，且尚未实现独立 provider-call/token enforcement，因此完整目标
仍未完成。`/resume` 来源不可用或格式变化时，用户仍可直接编辑或输入 Goal，不得阻断
`/loop`。

## 4. P0 功能范围

### 4.1 稳定 Acceptance Contract 与兼容

- Goal 原文、可选 `Done when`、`Must not`、required checks 和用户选择的
  Verification Criteria 必须无损保存。
- 0.0.22 当前配置与 0.0.21 已支持的 V1/V2/V3 记录必须有明确的读取、恢复和
  迁移矩阵。
- 兼容升级不能静默增加 criterion、删除 required check、扩大 workspace
  trust、改变 BYOK provider origin 或覆盖用户原始 objective。
- 旧记录无法满足当前安全不变量时，必须明确要求 Revised Loop；不得伪造
  PASS、自动授予 consent 或破坏旧记录。
- V2 与 V3 都必须引用完整 durable PASS terminal 才能进入 completed；
  直接 SDK 调用、恢复重放或内部状态入口不能绕过该保护。
- objective、criterion、constraint 或 required check 改变时创建新的
  contract lineage，不原地改写已冻结合同。
- TUI 与 headless 必须使用同一合同、Gate Plan、terminal 和 continuation
  语义。

### 4.2 Durable lifecycle 与恢复

- crash、终端关闭、进程被杀或系统重启后，可以恢复 active Loop 和最后一个
  已持久化阶段。
- 恢复不得重复已确认的 provider request、check result、reviewer result、
  terminal result 或 continuation。
- provider request 已发送但响应是否成功无法证明时，写入 durable
  `provider_outcome_unknown`（旧内部记录名如 `request_outcome_unknown` 必须兼容读取）；
  不得静默重发。用户显式 Retry 前必须提示该请求
  可能已经产生调用和费用；provider 支持 idempotency key 时优先复用同一 key。
- append-only records 缺失、损坏、跨 run 引用或 digest 不一致时 fail
  closed，并提供可操作的恢复说明。
- 同一 terminal `NEEDS_WORK` 的重复 Continue 只能创建一个新 active run。
- Cancel、permission denial、provider failure 和 verification runtime error
  必须保留可解释状态，不能显示成成功，也不能吞掉已确认的合同。
- 清理只处理 Wukong 能证明由当前 run 创建并拥有的临时状态；不自动
  stash、commit、reset、checkout、push 或删除用户文件。

### 4.3 清晰且稳定的 Loop 结果

Gate verdict 固定为：

| 终态 | 含义 | 默认下一步 |
|---|---|---|
| `PASS` | 完整且新鲜的 Gate attempt 满足所有冻结条件 | 查看摘要或结束 |
| `NEEDS_WORK` | 代码、检查或 reviewer 仍有可修复 blocker，或达到显式迭代上限 | 修复后继续，或创建 Revised Loop |
| `ERROR` | provider、权限、运行环境、合同完整性或 verification runtime 无法完成 Gate | 解决运行条件后重试；provider outcome unknown 时先核对 provider logs/billing，禁止盲目重试 |

- `BLOCKED` 可以作为界面阶段提示，但不能替代 durable terminal status。
- run lifecycle 与 Gate verdict 分离：`active | paused | cancelled | terminal`。
  TUI Ctrl-C 或 `/loop pause` 进入 `paused`，保留同一 contract 并允许 resume，不产生
  terminal result。`/loop stop` 或 headless process interruption 才显示
  `STOPPED_BY_USER`，不能伪造 Gate verdict；前者丢弃 contract，后者只有在 provider
  outcome 已知时才可提供 resume。
- preflight cancel 不创建 run。preflight permission refusal 也不产生 terminal；活动
  Loop 内的 Auto permission guard 以 `NEEDS_WORK/permission_required` 结束当前 run，
  verification runtime permission failure 则按稳定 reason 映射为 `ERROR`。
- model/provider/runtime 错误不能被显示成普通 delivery failure，也不能让用户
  误以为代码检查失败。
- 每个稳定 reason code 必须只映射到一个 terminal 类别、一个 continuation
  policy 和一组用户下一步。
- `max_iterations` 等允许 same-contract continuation 的结果，界面不能错误
  提示用户必须启动全新的 Loop。
- TUI footer、终态卡片、`/loop status` 与 headless structured output 必须
  使用同一结果来源，不各自推断状态。
- 终态摘要至少显示可证明的 outcome/lifecycle、reason、迭代数、pre-existing dirty
  files、Wukong touched/added/deleted files、执行过的 checks、provider
  calls/tokens（provider 可提供时）、未解决 blockers 和下一步；默认不要求
  用户展开内部日志。无法从 durable record 归因的字段必须显示 `unavailable` 或
  `unknown`，不得推断成功值。
- Cancel 只停止后续动作，不自动 rollback、reset 或删除当前改动；摘要必须
  说明停止阶段、仍保留的改动、已执行 checks 和是否存在 outcome unknown 的
  provider request。

### 4.4 Gate 与 evidence 完整性

- 每个 Gate attempt 按冻结计划执行 required checks、builtin risk scan 和
  唯一 fresh-context reviewer。
- deterministic check failure 或 risk failure 不能被 reviewer 覆盖。
- reviewer 只能读取 bounded、去密、attempt-scoped 的 review subject 和
  Gate evidence，不能获得任意文件系统、Bash、Skill command、MCP 或写入能力。
- 同一 risk kind 的不同文件、行和 evidence occurrence 必须全部保留；完全
  相同的重复输入才允许去重。
- `PASS` 必须引用同一 run、contract、Gate Plan、workspace snapshot 和
  provider consent 下的完整 fresh attempt。
- check definition、review policy、selected criteria、workspace 或 provider
  origin drift 后，旧 PASS 立即 stale；必须重新确认、恢复或创建 Revised
  Loop。
- Verification Skill 继续只贡献 strict qualitative criteria；不执行
  command，不单独授予 PASS。
- 当前 workspace 中的完整 attempt 是唯一 PASS 来源；不存在 Candidate
  Workspace、Promote 或另一个 target Final Gate。
- required checks 分为三种冻结结果：
  1. 有适用 checks 时必须完整执行，缺失、漂移或删除均不得 PASS；
  2. 只有版本化 discovery/policy 确认该任务类型没有适用 executable checks
     时，用户才能在 Preflight 显式确认 `No executable checks apply`；该确认
     进入 Acceptance Contract 和 coverage，仍执行 builtin risk scan、fresh
     reviewer 和任务类型适用的静态 evidence，摘要醒目标注“本次没有执行项目
     命令”。source change 缺少本应存在的项目检查时返回
     `NEEDS_WORK/checks_missing`，不能用 acknowledgement 弱化完成线；
  3. 本应存在的 check 因 tool、permission 或 runtime 不可用时返回 `ERROR`；
     check 已运行但失败返回 `NEEDS_WORK`。
- 删除或弱化已冻结 check、或新增任务所需 verifier，都必须创建 Revised
  Loop；不能在当前合同中静默改变完成线。

### 4.5 Workspace trust、BYOK consent 与隐私

- Wukong 在用户当前 workspace 中按当前操作系统账号权限运行；0.1.0 不宣传
  完整 filesystem、network、environment 或 process sandbox。
- 执行项目命令前必须拥有对应 workspace trust 和 Gate approval；Resume
  文本、模型输出、Skill 文本和外部 transcript 不能自行获得执行权。
- workspace read trust 与“发送给 exact BYOK provider”的 run-scoped
  consent 保持分离。
- 首次写入前记录 workspace baseline：workspace/repo identity、tracked
  modified、staged、untracked、deleted paths，以及 Loop 首次触碰文件时的
  pre-edit digest。Preflight 显示 workspace 是否 clean 和现有 dirty paths。
- pre-existing changes 不能被记为 Wukong 创建，也不能被 cleanup 撤销。
  外部进程在运行期间修改同一路径时，停止对应写入并要求重新确认，不能静默
  覆盖。
- secret、credential、session、日志、绝对路径和未经确认的 raw evidence
  不得进入 provider-visible broker input、Feedback 或普通日志。
- Wukong Web 不接收源码或本地 Gate evidence；`/feedback` 只提交用户预览并
  确认的受控文本字段。
- `/login` 只连接可选 Wukong 账号。模型目录为空仍是成功状态，不改变 BYOK
  默认 provider，也不阻止本地 Loop。

### 4.6 Loop-first UX 与命令兼容

- Welcome、默认 help 和 autocomplete 继续只突出 `/resume`、`/loop`、
  `/model`/`/provider` 以及必要账号入口。
- `/goal`、高级 verify/scan/proof/judge 和其他兼容入口继续默认隐藏但保留
  实现；0.1.0 不以删除底层能力换取界面简洁。
- `/loop status|pause|resume|stop` 的可见行为、TUI footer 和后台状态必须
  与真实 Goal lifecycle 一致。
- `WRITE` / `CHECK` / `REVIEW` 必须来自稳定、共享的 phase event。当前基于 active
  tool name 的 TUI 标签和 headless 的 writer iteration / running tool 输出不满足这一
  合同；在 phase event 实现前，对外只能把这些标签描述为 activity hints。
- V2/V3 Goal panel 都必须显示 Finish Line、当前 run、chain usage、
  continuation policy、阻断原因和下一步，不能因为 schema 版本漏掉信息。
- Preflight 在写入或执行前清楚展示 Goal、完成线、必跑 checks 或明确的
  no-check acknowledgement、workspace trust、pre-existing dirty paths、
  exact provider/model、将发送的输入类别、最大 iterations、writer/reviewer
  call ceiling 和可选 token budget。
- 无检查、检查漂移、provider 不可用、consent 缺失、权限拒绝和用户取消都
  必须有不同且可操作的说明。
- 0.1.0 不新增 `/worktree`、`/candidate`、`/promote`、`/parallel`、
  `/agents`、`/supervisor` 或 `/ship`。

### 4.7 Cross-Agent Resume

- Codex、Claude Code、Cursor、Kimi Code 和 Grok 都只读取当前 workspace
  下受支持的本地会话格式。
- 导入结果只能成为可编辑 Goal 草稿，不能自动冻结 Done when、required
  checks、permission、trust 或 provider consent。
- auth、system prompt、terminal log、memtrace、隐藏状态和 workspace 外路径
  保持排除。
- picker、handoff、格式损坏、symlink escape、workspace mismatch 和空结果
  必须在五个来源上使用一致行为。

### 4.8 安装、升级与跨平台

- 支持 macOS、Linux、Windows 的 x64/arm64 六个平台，用户可完成同一主路径；
  平台机制可以不同，但不能隐藏降级或把未实现能力写成一致。
- 六平台 fresh install、`wukong --version`、首启、provider 配置、Resume、
  Loop、恢复和卸载说明必须真实可复现。
- macOS/Linux 的 0.0.22 → 0.1.0 native upgrade 使用下载、校验、同目录
  staging 和 atomic rename。Windows 不在仍运行的进程内覆盖 executable；
  `wukong upgrade` 明确要求退出后重新运行已校验 installer。0.1.0 不为此
  引入 Windows FFI 或隐藏 helper。
- 六平台 upgrade 验收的共同结果是 config、session 和 active Loop 数据保持
  可恢复；不要求 Windows 复制 macOS/Linux 的 in-process 替换机制。
- 公开 ZIP 与 SHA-256、installer、manifest、package version、tag 和
  GitHub Release 必须来自同一 release identity。
- 覆盖 quoting、Unicode、timeout、cancel、signal/process-tree cleanup 和
  contract restore；不得用平台专用隐藏降级绕过验收。
- Gate runner 与 Bash runtime 在 Windows 上都必须终止完整子进程树；恢复
  Windows 实机 CI，不能只依赖跨平台构建成功。
- 0.1.0 RC 期间只接受 P0/P1 修复、兼容、性能、测试、文档和发布工程变更。

### 4.9 Codex Security 借鉴的基础合同

0.1.0 只借鉴 Codex Security 的 evidence completeness、direct-launcher
和 release integrity 原则，不直接依赖 `@openai/codex-security`，也不导入其
Workbench、完整扫描 CLI、Skills/MCP、模型 finding matcher 或运行时容器。
这些合同是 Wukong 自己的内部版本化记录，不新增用户命令或外部 evidence
入口。

#### GateCoverageRecordV1

每个 Gate attempt 在 aggregate 和 terminal 之前必须持久化一个 coverage
record，至少包含：

- `attemptId`、`contractId`、`gatePlanDigest` 和 coverage policy version；
- 从 frozen Gate Plan 确定的 expected producers：required checks 或明确的
  no-executable-check acknowledgement、builtin risk scan、selected
  criteria/fresh reviewer 和 final freshness；
- 每个 producer 的 expected identity/version、实际 record/digest、状态和
  缺失原因；
- `complete | partial | inconclusive` coverage status；
- domain-separated canonical `coverageDigest`。

规则：

1. expected producers 只能来自冻结合同和版本化 policy，不能由 writer 或
   reviewer 临时增删；
2. 缺失、未知、跨 attempt、digest 不一致、stale 或无法验证的 producer 使
   coverage 进入 `partial` 或 `inconclusive`；相同 producer identity、
   canonical payload digest、attempt 和 idempotency key 的精确重复
   canonicalize 为
   同一记录，只有 conflicting duplicate 才是 coverage failure；
3. 只有 `complete` 才允许进入 root PASS 判定；coverage record 本身不能授予
   PASS，外部 evidence 也不能单独产生 root PASS；
4. resume 必须重新读取并校验 producer record、payload/digest 和 coverage
   record，不能只检查文件或 record 是否存在；
5. terminal 持久化后拒绝 late producer/coverage write；budget exhaustion、
   cancel 或 signal interruption 必须形成 durable 非 PASS 结果。

所有 0.1.0 producer schema 必须持久化稳定的 `producerIdentity`、
`producerIdempotencyKey` 和排除随机 ref/createdAt 的 canonical
`payloadDigest`；coverage 使用这三个字段做 replay join，不能比较包含随机值的
record digest。

coverage status 与恢复规则冻结为：

- `complete`：所有 expected producer 都有可验证记录；完整执行后存在代码/
  reviewer blocker 时仍可为 `complete`，Gate verdict 为 `NEEDS_WORK`；
  producer/runtime failure 被完整记录时也可为 `complete`，Gate verdict 为
  `ERROR`；
- `partial`：已知 expected producer 尚未完成或缺失，在 attempt 未 terminal
  时可恢复同一 attempt 补齐；一旦 stopped/interrupted terminal 已写入，后续
  重试创建新 attempt；
- `inconclusive`：digest conflict、跨 attempt、corruption 或 provenance
  无法证明；当前 attempt 永远不能 PASS，必须新 attempt，合同本身变化时必须
  Revised Loop。

`FinalFreshnessRecordedV1` 是 coverage 的真实 durable producer，至少绑定
attempt/run/contract/plan、workspace before/after fingerprint、Gate Plan、
check definitions、criteria 与 provider consent freshness、稳定 status/reason
和 record digest。正常路径在 checks、scan、reviewer 完成后生成
status=`complete`；提前停止、signal 或 crash recovery 仍生成
`incomplete|stopped|interrupted` freshness record，记录当时可证明的 workspace
与 producer 状态，并使 coverage 只能为 `partial|inconclusive`。reviewer
期间 workspace drift 也使 coverage 非 `complete`。

一旦 `GateAttemptCreated` 已持久化，所有正常、check/reviewer error、budget
exhaustion、cancel、signal 和 crash-recovery 路径都由唯一幂等 finalizer
收口。finalizer 先写 final freshness 和 coverage，再写 attempt disposition；
只有 disposition=`verdict` 时才写 aggregate/snapshot 和 Gate verdict。
preflight 在 attempt create 前失败时不伪造 coverage；已创建 attempt 无法证明
producer 完整时，只能完成为 `partial|inconclusive` 的非 PASS disposition。
terminal 后拒绝 late write，同 attempt 重放只能得到同一 disposition/verdict。

GateCoverageRecordV1 是 additive durable record，不要求把 Acceptance
Contract 升级到 V4，但不能作为旁路记录：

- `ProofAggregateRecordedV3` 必须绑定 `coverageRef/coverageDigest`，只有同一
  attempt coverage=`complete` 才能写入 `PASS`；
- `LoopEvidenceSnapshotCreatedV3` 绑定同一 coverage ref/digest；
- `GateAttemptCompletedV2` 绑定 coverage 和
  `verdict | stopped_by_user | interrupted` disposition；只有 `verdict`
  携带并引用同 attempt 的 V3 aggregate/snapshot 与
  `PASS|NEEDS_WORK|ERROR`，用户取消或 signal interruption 的 `gateVerdict`
  必须为空；
- 旧 aggregate/snapshot/terminal schema 只读兼容，不能产生新的 0.1.0 PASS。

#### DirectShellBindingV1

每个 frozen executable check 必须绑定 Wukong 实际 exec 的 direct shell，
而不是声称已经验证 shell 内解析出的全部程序。binding 至少包含：

- platform、shell resolution source、canonical realpath、content digest、size
  和平台可稳定获得的 metadata；
- cwd/workspace identity、解析时 PATH digest、execution/display command
  digest、approval digest 和 Gate Plan identity；
- 允许的 workspace/toolchain/system source 与 protected-root policy
  version。

执行前和执行后都重新验证 binding。PATH shadow、symlink/realpath drift、
shell replacement、content drift、从 Wukong state/output 目录执行未知 shell
或 approval mismatch 必须在 spawn 前拒绝，或使 attempt 进入稳定的非 PASS
终态。合法 toolchain drift 进入可操作的重新确认路径，不能只给笼统错误。

该合同只观察 Wukong 直接启动的 shell。shell 内解析的 `npm`、`pnpm`、
pipeline、function、shebang、脚本和 descendants 不在 binding 范围；pre/post
校验用于阻止错误 PASS，不能消除 executable replacement TOCTOU，也不构成
sandbox 或完整 runtime attestation。Windows 不强制 POSIX inode/uid/gid；
最低一致合同使用 canonical path、content digest、size 和可稳定 metadata。

#### ReleaseProvenanceV1

ReleaseProvenanceV1 是 release engineering record，不进入 Loop contract 或
本地用户 session。0.1.0 的公开发行使用 stage-verify-publish-exact：

1. manifest 分开记录 `sourceRepository/sourceTag/sourceCommitSha/
   sourceMainAncestryVerified` 与 `distributionRepository/
   distributionReleaseTag/distributionReleaseUrl`；distribution tag 通过
   manifest 绑定 source tag、完整 SHA、package version 和 RC approval，
   不要求两个仓库的 tag 指向同一 Git object；
2. 每个最终发布 asset 对应唯一记录的 build output；失败 candidate 可以重跑，
   但 publish 阶段不得重新构建；
3. release manifest 记录每个 asset 的 target、name、size、SHA-256、source
   commit、build job/run 和 toolchain identity；
4. GitHub Actions 使用 full commit SHA 固定第三方 action，
   `persist-credentials: false` 和最小权限；
5. 为公开 artifact 生成 GitHub OIDC provenance/attestation，并从公开下载
   URL 重新校验 manifest、SHA 和 provenance；attestation 必须记录真实 source
   repository/issuer，不能把 distribution repo 写成构建来源；
6. 六平台先 build/package，再从 ZIP 解压 smoke exact packaged bytes，随后
   上传 workflow staging artifacts、生成 manifest/attestation 并回读验证；
7. 只在 staging 全部通过后创建 draft release，一次性上传 exact bytes，禁止
   `--clobber`；核对 12 assets、SHA、provenance 和 notes 后才 publish；
8. source/distribution identity、version、artifact/manifest 或 attestation
   不一致时发布
   fail closed；matrix 失败不能改变 public `latest` 或留下部分公开 release，
   也不能通过手工重传未记录来源的文件绕过。

如果某个平台暂时无法生成或验证 provenance，该平台的 0.1.0 正式发布保持
阻断，不能把 attestation 静默降级为可选项。

OIDC provenance 证明 CI 来源，不替代 macOS notarization 或 Windows
Authenticode。若 0.1.0 继续发布 unsigned binaries，安装文档与 native smoke
必须验收真实 Gatekeeper/SmartScreen 路径；OS signing 另列 release decision，
不隐含在 ReleaseProvenanceV1 中。

## 5. P1 稳定化范围

### 5.1 真实项目与 Criteria 质量

- Node、Python、Rust、Go 与 monorepo 各完成至少一条 blocker → fix → full
  rerun → PASS。
- 真实任务矩阵同时覆盖小型 bug、失败测试修复、多文件 feature、refactor、
  docs/config 无 executable checks、pre-existing dirty workspace 和依赖工具
  缺失；语言覆盖不能代替任务覆盖。
- API compatibility、migration/log security、frontend/design 和 monorepo
  package 四类 reference criteria 完成固定 eval。
- with/without criteria 配对不得增加 seeded blocker false PASS；blocking
  finding 必须包含 provenance、evidence 和可执行 next action。
- adversarial fixture 覆盖恶意 Skill 文本、workspace source、stdout/stderr、
  Gate evidence、secret 和 prompt injection。

### 5.2 可理解性与性能

- 首次用户不阅读内部文档也能理解 Finish Line、workspace shell 权限、
  provider-visible input、Gate verdict 与 `STOPPED_BY_USER`。
- 从 fresh install 到可执行 Preflight 的 onboarding 时间单独测量，不把真实
  项目 checks 耗时算入；provider setup、Preflight 和首次 terminal 的退出阶段
  必须可归因。
- Preflight 显示 exact provider/model、最大 iterations、writer/reviewer call
  ceiling 和可选 token budget。终态显示 calls、input/output tokens、retries
  和 budget remaining；只有存在可靠 pricing source/version 时才显示费用估算，
  不伪造金额。
- 避免在一次 attempt 中重复执行同一 check、scan 或 reviewer。
- 将日常开发验证与六平台 release 验收分层；减少重复运行时间，但不删除
  P0 合同、安全、恢复和发布覆盖。
- 终态和恢复路径的关键交互提供稳定的 TUI/headless regression fixture。

### 5.3 Public truth

- README、docs、官网、Download、Today、Changelog 和 Release Notes 只描述
  已经通过 0.1.0 验收的能力。
- 使用经过脱敏且用户授权的真实本地 Loop 输出作为演示，不恢复 Hosted
  Report，也不使用虚构 dashboard 数据。
- 登录、空模型目录、Feedback、BYOK 和无 quota 的文案在 CLI 与 Web 一致。
- 0.1.0 不新增 telemetry event 或 Web/D1 product metrics backend，也不使用
  CLI telemetry、账号表或下载量证明 release cohort。现有 optional CLI
  telemetry 只作为兼容行为保留；RC 前必须审计并公开 exact fields、endpoint、
  retention 和 opt-out，不能把它写成 0.1.0 新功能或验收来源。

## 8. 四类发布门槛

### 8.1 Contract / Security

- Acceptance、checks、criteria、consent、attempt、evidence、aggregate、
  coverage、terminal 和 continuation lineage 可完整校验。
- deterministic failure、stale evidence、record corruption、secret input、
  origin drift 和权限缺失全部 fail closed。
- root PASS 必须引用 `complete` GateCoverageRecordV1；partial、inconclusive、
  budget exhaustion、cancel 和 signal interruption 永远不能 PASS。
- frozen executable checks 的 actual direct shell 必须拥有新鲜且匹配的
  DirectShellBindingV1；不得把它宣传成 package-manager/descendant
  attestation。
- Resume、restart、continuation 和 legacy migration 不扩大权限或 provider
  可见范围。
- 已取消架构不存在于运行路径、默认命令、公开文案和 release notes。

### 8.2 Automated Quality

- targeted unit/integration/E2E、typecheck、lint、docs build、installer
  validator 和 clean checkout build 通过。
- macOS、Linux、Windows 覆盖 quoting、Unicode、timeout、cancel、
  process-tree cleanup 和 restore。
- 同一 fresh fixture 连续至少三次保持 check 顺序、terminal 和 reason code
  一致。
- fault injection 覆盖 provider failure、invalid reviewer output、check
  runtime failure、request outcome unknown、crash、cancel、workspace drift、
  consent revoke 和 corrupt record。
- coverage producer 缺失/conflicting duplicate/跨 attempt/late write、
  exact duplicate replay、PATH shadow、shell replacement、content drift 和
  protected-root 执行负向测试通过。
- provider setup 覆盖有效配置以及 invalid key、model not found、rate limit、
  timeout；no-check acknowledgement、pre-existing dirty change、外部同路径写入
  和 `STOPPED_BY_USER` 形成稳定 regression。
- 六平台 native bundle 启动、`--version`、基本 Loop smoke 和 SHA 校验通过。

### 8.3 Real User Flow

- 五个 Resume 来源各完成 picker → editable Goal → Preflight → Loop →
  terminal/recovery smoke。
- Node、Python、Rust、Go、monorepo 和至少一个真实 Windows repo 完成真实
  流程。
- 至少 25 名不同、明确 opt-in 的外部测试者进入 cohort，所有人都进入分母。
- 至少 20 名完成 fresh install/upgrade、provider smoke 和第一个可执行
  Preflight，且不需要维护者实时指导。
- 至少 15 名不同测试者完成第一个真实 Goal + Gate PASS。
- 15 名首次 PASS 用户都必须获得完整的 14 天观察窗口；其中至少 7 名在首次
  PASS 后第 1–14 天内主动完成第二个真实且不同的 Goal PASS。验收人员指定的
  第二个演示任务不计入。
- 至少 80% 完成者无需内部文档即可正确说明终态、决定结果的 evidence、
  workspace 中保留的改动和下一步。
- 在参与者已准备可用 API Key 的前提下，fresh install 到可执行 Preflight 的
  中位数不超过 5 分钟，P90 不超过 15 分钟；真实项目 checks 时间另记。
- 未解决 false PASS、pre-existing state loss、workspace 外越界写入、隐私/
  consent violation、静默重复 provider request 和不可恢复状态均为 0。
- 所有 P0 与明确标记为 release-blocking 的 P1 为 0；其他 P1 必须记录影响、
  owner、workaround 和目标版本。

以上数字使用显式 opt-in cohort 验收协议，不通过账号表、D1 行为数据、安装
标识或匿名 telemetry 推断：

1. release owner 维护私有验收 ledger；代码仓库和公开文档只记录聚合结果；
2. 每名参与者使用自愿提供的稳定 participant ID 去重，不创建设备指纹；
3. 最小字段只包含 consent 日期、平台、项目类型、onboarding started/completed、
   first Preflight/PASS 时间、exit stage/reason、第二个不同 Goal PASS、
   terminal comprehension、willing-to-use-again、provider cost/latency 是否
   可接受、反馈/复现引用和可选案例授权状态；
4. 不记录源码、repo 名称/路径、Goal 原文、prompt、transcript、evidence、
   API key 或 provider credential；
5. PASS 必须由参与者确认的真实终态摘要或共同复现实验支持，started、演示
   fixture、内部账号和模型自评不计入；
6. 未完成用户必须保留非敏感退出分类：install/upgrade、provider setup、
   Preflight 理解/拒绝、Loop execution、Gate/runtime、用户主动停止、产品缺陷
   或外部环境不支持，不能从分母删除；
7. 非案例的 participant-level 记录在正式版发布 90 天后删除或只保留不可
   反向识别的聚合数；授权案例按单独书面授权处理。

至少 3 个经过授权、可复现且不泄露源码的案例属于正式宣传/launch gate，
可以在 RC 阶段准备，但不作为 binary correctness 的发布阻断条件。

### 8.4 Release / Public truth

- `0.1.0-rc.1` 后只接收本设计允许的稳定化变更。
- RC 连续稳定至少 14 天；只有 false PASS、pre-existing state loss 或越界
  写入、privacy/consent violation、不可恢复 durable state 或公开 artifact/
  provenance mismatch 重新计算稳定期。普通文案、非阻塞性能或兼容修复不自动
  重置 14 天。
- package、tag、12 个 release assets、SHA、manifest、installer、README、
  docs、Web、Today、Changelog 和 What's Changed 完全一致。
- ReleaseProvenanceV1 证明 tag/version/full source SHA、RC、每个平台已验证
  artifact 和公开下载完全对应；第三方 Actions full-SHA 固定，checkout
  不持久化 credential，并完成 OIDC attestation 验证。
- 从公开 URL 验证 fresh install 与 0.0.22 → 0.1.0 直接 upgrade，并覆盖
  0.0.21 records 的向后兼容恢复；不以本地构建结果代替。
- GitHub Release、官网 health/version、installer 和关键页面完成生产验收，
  且保留经过演练的发布回撤步骤。

## 10. 完成定义

只有同时满足以下条件，0.1.0 binary release 才算完成：

1. 本文件所有 P0 已实现，P1 发布项已关闭或明确证明不阻塞；
2. 0.0.22 的配置、会话和 Loop records 完成直接升级验证，0.0.21 records
   完成向后兼容与恢复验证；
3. PASS 只来自同一当前 workspace 上完整且新鲜、coverage 为 `complete` 的
   Gate attempt；
4. 所有 executable checks 使用新鲜 DirectShellBindingV1，且不把 direct
   shell observation 宣传成 package-manager/descendant attestation；
5. 公开资产全部满足 ReleaseProvenanceV1 和 stage-verify-publish-exact；
6. PASS、NEEDS_WORK、ERROR Gate verdict 与 STOPPED_BY_USER lifecycle result
   的边界、reason/next action 在 TUI/headless 一致；
7. 六平台、真实项目、五来源 Resume、fresh install 和 upgrade 验收通过；
8. opt-in 用户、首次无协助成功、主动重复使用和 14 天 RC 门槛有可审计证据；
9. 所有 P0、release-blocking P1、false PASS、pre-existing state loss、越界
   写入、静默重复 provider request 和隐私冲突为 0；其他 P1 有明确处置；
10. Free、local-first、BYOK、无 quota、无付费的产品与公开口径一致；
11. 已取消或后续能力没有进入实现、默认命令面或发布说明。

正式宣传或 Product Hunt launch 另要求至少 3 个授权、可复现且不泄露源码的
案例；该门槛不回溯阻塞已经满足上述条件的 binary release。

在上述 binary release 条件完成前，只能称为 0.1.0 design、implementation 或
RC，不能对外写成已发布。
