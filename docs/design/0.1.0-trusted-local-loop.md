# 0.1.0 Trusted Local Loop

> **状态：PARTIALLY IMPLEMENTED / 未达 RC / 未发布。**
> 目标版本：0.1.0。
> 最后更新：2026-08-06。
> 已发布基线：[0.0.22](../releases/0.0.22.md)；兼容验证继续覆盖 0.0.21 records。
> 产品边界：Free、local-first、BYOK；不增加付费、quota、托管执行或新的默认命令。

## 一句话定义

> **0.1.0 是一条可控、可恢复、可解释的单 Loop：用户在当前 workspace 中明确目标、检查和成本上限，Wukong 持续写、检查、审查和修复，最后给出可信结果、改动归因和安全的下一步。**

0.1.0 是稳定化版本，不是内部 schema 展示或功能堆叠版本。它冻结用户能依赖的
输入、Preflight、执行、终态与恢复语义，同时复用 0.0.14–0.0.22 已发布的 Resume、
Finish Line、durable lifecycle、Verification Criteria、evidence broker 和 Gate。

计划发布顺序：

```text
0.0.22
  → 完成 RC admission 必做项
  → 0.1.0-rc.1
  → 真实项目、六平台和 opt-in 用户验证
  → 0.1.0
```

当前开发分支已经具备 consolidated Preflight、部分 durable terminal、三态 Gate
结果、`STOPPED_BY_USER`、provider outcome unknown guard 和结果摘要。独立
provider-call/token cap、可信 no-check 合同、完整文件归因、升级/恢复矩阵和全部
真实发布证据仍未完成，因此当前不是 `0.1.0-rc.1`。

## 1. 版本决策

1. **稳定现有单 Loop。** `/loop` 继续复用 Goal engine，在用户确认的当前
   workspace 中执行。
2. **优先用户合同。** 用户不需要理解 schema、digest 或 record 才能输入、运行、
   判断结果或恢复。
3. **保留 fail-closed 不变量。** 只有当前 attempt 的必需 evidence 完整且新鲜时
   才能 PASS；无法证明完整性时只能 NEEDS_WORK、ERROR 或 lifecycle result。
4. **控制成本和改动。** 用户在运行前看到并确认 iteration、provider-call 和可选
   token 上限；运行后能区分已有改动与 Wukong 改动。
5. **不重新引入已取消架构。** isolated worktree、Candidate Gate、Safe Promote、
   target Final Gate、lease/fencing 和 Windows FFI 不属于 0.1.0。
6. **不收费。** 本地 BYOK Loop 不需要 Wukong 登录，不按 Loop 或用户自己的
   token 设置商业额度。
7. **把验证与宣传分开。** 六平台、真实项目、兼容升级和 cohort 是正式版证据；
   三个授权案例只阻断集中宣传，不阻断 binary correctness。

## 3. 冻结的用户流程

```text
Install or Upgrade
  → Configure and smoke-test an exact BYOK provider/model
  → Enter an editable Goal or import an editable Resume draft
  → Review one consolidated Preflight
      - Goal / Done when / Must not
      - required checks or explicit no-executable-check decision
      - workspace and pre-existing dirty paths
      - exact provider/model and outbound input summary
      - iteration, provider-call and optional token limits
  → Confirm local read, provider send, permission and check execution
  → Write → Check → Review → Fix
  → PASS / NEEDS_WORK / ERROR or STOPPED_BY_USER
  → Review decisive evidence, changed files, checks, usage and next action
  → Resume, Continue, Revise, End, Keep or Revert
```

每个终态必须回答：

1. 发生了什么；
2. 哪个 evidence 或运行条件决定了结果；
3. 哪些改动原本已存在，哪些由 Wukong 触碰；
4. 本次使用了多少 provider calls/tokens/retries，是否还有 budget；
5. 用户下一步可以安全地做什么。

## 4. RC admission：必须完成的 P0

### 4.1 Consolidated Preflight 与成本控制

Preflight 必须允许用户在任何写入、项目命令或 provider call 前查看并修改：

- Goal 原文、可选 `Done when`、`Must not`；
- required checks、selected criteria，或可信 no-check decision；
- current workspace、repo identity、pre-existing dirty paths；
- exact writer/reviewer model、provider origin、provider-visible input 摘要；
- permission mode、最大 iterations、writer/reviewer provider-call ceiling、可选
  token budget；
- 本地读取、provider transmission、permission 和 project-check execution 的
  审批顺序；
- 终态、保留改动和后续处置方式。

安全边界仍使用 distinct approvals；0.1.0 不追求一个“approve all”按钮。取消
Preflight 不创建 contract、trust grant 或 run，也不发送 provider request。

成本合同：

- provider-call ceiling 和 token budget 必须真实执行，不能只展示；
- 运行中显示 calls/tokens/retries 与 remaining budget；
- 达到上限形成 `NEEDS_WORK/budget_exhausted`，允许 same-contract Continue；
- 只有存在可靠 pricing source/version 时才显示金额，否则显示 `Cost unavailable`；
- 不建设 provider 价格数据库作为 0.1.0 前置条件。

### 4.2 No-check 合同

required checks 冻结为三类结果：

1. 有适用 checks 时必须完整执行；缺失、漂移或删除均不得 PASS；
2. 只有版本化 discovery/policy 判断该任务类型确实没有适用 executable checks 时，
   用户才能在 Preflight 显式确认 `No executable checks apply`；该 decision 进入
   Acceptance Contract，摘要醒目标注“本次没有执行项目命令”，并继续执行适用的
   builtin risk scan、静态 evidence 与 fresh reviewer；
3. source change 缺少本应存在的 checks 为 `NEEDS_WORK/checks_missing`；本应存在的
   check 因 tool、permission 或 runtime 不可用为 `ERROR`；已运行但失败为
   `NEEDS_WORK`。

通用 Finish Line warning acknowledgement 不能替代 no-check decision。删除或弱化
已冻结 check 必须创建 Revised Loop。

### 4.3 终态、结果与 TUI/headless 一致

Gate verdict 固定为：

| 终态 | 含义 | 默认下一步 |
|---|---|---|
| `PASS` | 当前 workspace 的完整且新鲜 attempt 满足所有冻结条件 | Review、Keep 或 End |
| `NEEDS_WORK` | attempt 完整结束，但仍有 blocker、失败 check、缺检查或预算耗尽 | Continue 或 Revise |
| `ERROR` | provider、tool、permission、record 或 runtime 阻止可信结论 | 修复环境后 Retry/Resume |

Lifecycle result `STOPPED_BY_USER` 不属于 Gate verdict：

- TUI Ctrl-C 或 `/loop pause` 保持可恢复 `PAUSED`；
- `/loop stop` 或 headless 在 verdict 前的显式中断为 `STOPPED_BY_USER`；
- Preflight cancel/reject 不创建 run；
- active Auto guard 拒绝为 `NEEDS_WORK/permission_required`；
- provider outcome unknown、checks missing、permission denial 和用户停止必须拥有不同
  reason、说明与 next action。

TUI、headless JSON、`/loop status` 和 Goal panel 必须从同一 durable terminal 与
continuation mapping 生成结果。`WRITE/CHECK/REVIEW` 在稳定共享 phase event 完成前
只能标成“当前活动提示”，不能作为 durable 阶段或恢复证据。

### 4.4 Workspace baseline 与文件归因

- Preflight 显示 tracked modified、staged、untracked、deleted paths 的有界摘要；
- 首次写入前记录 workspace/repo identity 和 baseline；
- Wukong 首次触碰路径时记录足以区分 pre-existing 与本次写入的 digest/state；
- 终态分别显示 pre-existing dirty、Wukong touched/added/deleted 和 attribution
  unknown，不把原有改动归因给 Wukong；
- 外部进程在运行期间修改同一路径时停止对应写入并要求重新确认；
- Wukong 不自动 stash、commit、reset、checkout、push、删除或回滚用户文件；
- Cancel/Stop 后改动留在 workspace，终态明确要求用户 Review、Keep 或 Revert。

0.1.0 不要求对 shell 内所有 descendants 建立完整 runtime attestation。执行 checks
仍需绑定 exact command、cwd/workspace、resolved direct shell 和 Gate approval；完整
shell binary content/PATH 前后 attestation 后移。

### 4.5 Durable lifecycle、恢复与兼容

- crash、终端关闭、进程被杀或系统重启后，可以恢复最后一个可证明的 active state；
- 恢复不得重复已确认的 provider request、check、reviewer、terminal 或 continuation；
- provider response 是否成功无法证明时持久化 `provider_outcome_unknown`，显示可能
  已产生调用/费用；用户确认前不提供盲目 Resume/Retry，provider 支持时复用相同
  idempotency key；
- append fault、损坏记录、跨 run 引用、digest conflict、重复 terminal、并发
  Continue 和 late write 均 fail closed；
- objective、criterion、constraint、check 或 provider origin 改变时创建 Revised
  Loop，不原地改写冻结合同；
- 0.0.22 config/provider/session/Goal/contract/criteria 可直接升级；0.0.21 records
  继续覆盖兼容读取；历史 PASS 只读保留，不为 legacy attempt 事后伪造新 evidence；
- 旧 active attempt 无法满足当前不变量时，明确结束为非 PASS，再由用户选择 Revised
  Loop；不自动授予 trust、permission 或 consent。

### 4.6 最小 Gate completeness/freshness

0.1.0 保留以下不变量，但不以新增多层 schema 作为用户功能：

- frozen Gate Plan 决定 expected producers：required checks 或 no-check decision、
  builtin risk scan、selected criteria/fresh reviewer 和 final workspace freshness；
- attempt terminal 前记录每类 expected/observed producer、缺失原因、workspace
  before/after 和 `complete | partial | inconclusive`；
- 只有同一 attempt 的 completeness=`complete` 且 evidence fresh 才能判定 PASS；
- `complete` 仍可得到 NEEDS_WORK 或 ERROR；partial/inconclusive、budget exhaustion、
  stop、interrupt、corruption 或 drift 永远不能 PASS；
- exact duplicate replay 幂等，conflicting duplicate、跨 attempt 或 late producer
  fail closed；
- 修复后完整重跑 frozen plan，不复用 stale PASS。

实现可以在现有 attempt/aggregate/snapshot/terminal record 上增加最小字段，或使用
一个最小内部 evidence summary；不要求 0.1.0 同时引入
`GateCoverageRecordV1`、`FinalFreshnessRecordedV1`、
`ProofAggregateRecordedV3`、`LoopEvidenceSnapshotCreatedV3`、
`GateAttemptCompletedV2` 的整套替换。若未来需要公开 evidence interchange、外部
attestation 或复杂并行 join，再单独设计版本化 schema。

### 4.7 BYOK consent、隐私与 Resume

- workspace read trust 与“发送给 exact BYOK provider”的 run-scoped consent 分离；
- secret、credential、session、日志、未经确认的 raw evidence 和不必要的绝对路径
  不进入 provider-visible broker input、Feedback 或普通日志；
- Wukong Web 不接收源码或本地 Gate evidence；`/feedback` 只提交用户预览确认的
  受控文本；
- `/login` 只连接可选账号；空模型目录仍成功，不改变 BYOK 默认 provider；
- Codex、Claude Code、Cursor、Kimi Code 和 Grok 只读取当前 workspace 下受支持的
  本地会话格式；导入只产生可编辑 Goal 草稿，不授予 checks、criteria、permission、
  trust 或 provider consent；
- 五来源共同覆盖损坏格式、symlink escape、workspace mismatch、外部路径、隐藏
  auth/system/terminal/memtrace 字段和空结果。

### 4.8 安装、跨平台与 release integrity

- macOS、Linux、Windows 的 x64/arm64 六个平台完成 fresh install、`--version`、
  首启、provider smoke、Resume、基本 Loop、停止/恢复和 checksum smoke；
- macOS/Linux 的 0.0.22 → 0.1.0 native upgrade 使用 download、verify、same-dir
  staging 和 atomic rename；Windows 明确退出后重新运行已校验 installer；
- 六平台共同覆盖 quoting、Unicode、timeout、cancel、process-tree cleanup 和
  contract restore；Windows 不能只验证交叉构建产物存在；
- tag、version、source full SHA、六个 ZIP、六个 SHA、installer、manifest、release
  notes 和公开下载必须属于同一 release identity；
- workflow 保持 third-party actions full-SHA、最小权限和
  `persist-credentials: false`；
- build/package 后从 ZIP smoke，生成 staging metadata/provenance 与 OIDC
  attestation，创建 draft，byte-verify exact assets 后再 publish；publish 不重建；
- 从公开 URL 重新验证 asset name/size/SHA/source run/attestation，再完成 fresh
  install 和 direct upgrade；失败不改变 public latest；
- OIDC provenance 不替代 macOS notarization 或 Windows SmartScreen 信任。

release manifest/provenance 可以延续当前 `release-provenance.json`，不要求为了
0.1.0 再定义新的公开 `ReleaseProvenanceV1` schema；必须证明的 release identity
字段和公开回读仍是硬门槛。

## 5. RC 期间必须完成的验证

### 5.1 真实项目与 Provider

- Node、Python、Rust、Go、monorepo 和至少一个 Windows repo 各完成
  blocker → fix → full rerun → PASS；
- 任务覆盖 bug、失败测试、多文件 feature、refactor、docs/config no-check、dirty
  workspace 和 tool missing；
- provider setup 覆盖 valid、invalid key、model not found、rate limit、timeout 和
  outcome unknown；
- API compatibility、migration/log security、frontend/design 和 monorepo package
  四类 criteria 完成固定 eval；
- adversarial fixture 覆盖恶意 Skill/workspace/stdout/Gate evidence、secret 和 prompt
  injection；seeded blocker false PASS 为 0；
- 同一 fresh fixture 连续至少三次保持 check 顺序、terminal 和 reason code 一致。

### 5.2 用户理解与 cohort

使用显式 opt-in、全分母 cohort；不通过账号表、下载量、D1、设备标识或 telemetry
推断：

- 25 名不同外部测试者全部进入分母，不替换失败者；
- 至少 20/25 在无维护者实时指导下完成 install/upgrade、provider smoke 和首个
  executable Preflight；已有 API Key 时中位数 ≤5 分钟、P90 ≤15 分钟；
- 至少 15/25 完成首个真实 Goal durable PASS；到达 terminal 的用户至少 80% 能
  解释结果、决定性 evidence、保留改动和 next action；
- 15 名 first-PASS 用户全部获得完整 14 天观察窗口；至少 7 名在第 1–14 天主动
  完成第二个不同 Goal PASS；
- ledger 只记录 consent、平台/项目类型、阶段时间、exit stage/reason、结果理解、
  repeat、cost/latency 接受度和反馈引用，不保存源码、repo/path、Goal、prompt、
  transcript、evidence 或 credential；正式版 90 天后删除 participant-level 数据。

上述 cohort 是正式 0.1.0 的产品证据，不是需要实现的新 telemetry 功能。三个授权、
可复现、source-safe 案例只属于 Product Hunt/集中宣传 gate。

### 5.3 RC 稳定窗口

- `0.1.0-rc.1` 后只接收 P0/P1 修复、兼容、性能、测试、文档和发布工程变更；
- RC 连续稳定至少 14 天；false PASS、pre-existing state loss、越界写入、privacy/
  consent violation、不可恢复 durable state、静默重复 provider request 或公开
  artifact/provenance mismatch 重算稳定期；
- 普通文案、非阻塞性能或兼容修复不自动重置窗口；
- 所有未完成用户保留非敏感 exit 分类，不能从分母删除。

## 6. P1：值得做但不阻塞 rc.1

- 将 activity hints 升级为 TUI/headless 共用的稳定 phase event；
- 优化 Goal panel、footer 和终态信息密度，不做大规模 TUI 重设计；
- 扩展更多真实项目、Resume/adversarial fixtures 和性能基线；
- 改进 onboarding、错误文案和 provider setup 归因；
- 公开现有 optional CLI telemetry 的 exact fields、endpoint、retention 和 opt-out，
  但不新增 event 或 metrics backend；
- 在真实 threat evidence 出现后重新评审完整 direct-shell content/PATH attestation、
  多层 coverage schema 或公开 evidence interchange。

任何 P1 若造成 false PASS、状态丢失、越界写入、隐私冲突或不可恢复升级，即升级为
release-blocking P0。

## 7. 明确不做

0.1.0 不包含：

- isolated worktree、Candidate Workspace/Gate、Safe Promote、lease/fencing、target
  Final Gate 或 Windows FFI；
- 多 Agent 并行 Loop、递归 Agent Tree、Detach、Local Supervisor 或 Remote Control；
- GitHub App、PR comment/status、PR Gate publish、Team policy、Audit log、SSO/SCIM；
- Hosted Terminal/Report、云端 Routine、源码/evidence 云同步；
- Wukong 托管模型推理、managed credits、Checkout、payment、subscription、quota、
  entitlement 或对 BYOK token 加价；
- 新的 Web/D1 产品 telemetry 后端、installation identity，或使用 telemetry 推断
  cohort；
- canonical JSON/SARIF 外部 evidence 导入、外部 evidence 自动参与 root PASS；
- `@openai/codex-security` 直接依赖、完整 security scan CLI、Workbench、Docker/
  seccomp 或完整 runtime sandbox；
- command recipe、动态 workflow graph、Skill marketplace 或新的默认顶层命令。

0.0.22 已存在的 `/swarm`、`/btw`、`/tasks` 和 subagent runtime 可以继续作为兼容
辅助执行面，但它们不能生成 root PASS、绕过 root Goal/Gate，或被宣传成 0.1.0
并行 Loop 产品能力。

## 8. 完成定义

### 可以切 `0.1.0-rc.1`

1. Preflight 可配置并真实执行 provider-call/token 上限；
2. no-check decision 与 source-change checks_missing 语义冻结；
3. 终态统一显示结果、决定性 evidence、文件归因、checks、usage、blocker 和 next；
4. crash/restart、provider outcome unknown、stop/pause/resume、duplicate terminal、
   corrupt record 和 concurrent Continue fail closed；
5. 0.0.22 直接升级与 0.0.21 record compatibility 自动化通过；
6. minimal completeness/freshness 保证 partial/inconclusive/stale 永不 PASS；
7. 六平台 RC assets、installer、manifest、release identity 和 public docs 候选一致；
8. P0 与 release-blocking P1 为 0。

### 可以发布 `0.1.0`

1. RC admission 条件持续满足；
2. 六平台公开 URL fresh install/upgrade、基本 Loop、恢复和 checksum 验收通过；
3. 五来源 Resume、真实项目、provider/error/adversarial 矩阵通过；
4. 25/20/15/7 cohort 与 14 天稳定窗口有可审计证据；
5. false PASS、pre-existing state loss、workspace 外写入、静默重复 provider
   request、privacy/consent violation 和不可恢复状态为 0；
6. package、tag、12 个 assets、SHA、installer、manifest、README、docs、Web、Today、
   Changelog、What's Changed 和公开 provenance 完全一致；
7. Free、local-first、BYOK、无 quota、无付费的公开口径一致；
8. 后续能力未进入实现、默认命令面或 release notes。

0.1.0 binary 发布后，集中宣传仍需三个授权案例和 live OAuth/Download/status/docs/
feedback/privacy 验收。0.2.0 或任何收费功能只能在 0.1.0 重复使用得到验证后重新评审。
