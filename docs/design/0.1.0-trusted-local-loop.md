# 0.1.0 Trusted Local Loop

> 状态：产品范围已确认；尚未批准实施，当前实施版本仍是 0.0.21。
> 目标窗口：最早 2026 年 11 月公开发布；日期取决于 0.0.20、0.0.21 与 RC 门槛，不是发布日期承诺。
> 最后更新：2026-07-29。
> 前置版本：[0.0.20 Reusable Verification Criteria](0.0.20-reusable-verification-skills.md) 与 [0.0.21 Isolated Loop Worktrees](0.0.21-isolated-loop-worktrees.md)。
> 产品边界：Free、local-first、BYOK；不设置 Wukong Loop/token quota，不在同一版本上线付费、Checkout 或托管模型。

## 一句话定义

> **0.1.0 是第一版可以向普通开发者稳定推荐的 Trusted Local Loop：从明确完成线开始，在隔离候选工作区中持续写、验、修，经安全 Promote 后只以真实目标 workspace 的最终 Gate 作为完成结论。**

0.1.0 不是一次大规模功能扩张。它把 0.0.19–0.0.21 已建立的合同收敛成一个稳定、可安装、可升级、可恢复、可解释的产品基线：

```text
Goal / Resume
  → Freeze Finish Line
  → Select reusable criteria
  → Create exact isolated candidate
  → Write → Check → Review → Fix
  → Candidate Gate
  → Confirm + Promote
  → Target Final Gate
  → Validate + Seal canonical evidence
  → PASS / NEEDS_WORK / ERROR
```

## 1. 为什么 0.1.0 在这里发布

0.1.0 的版本号表示“可信单 Loop 已稳定”，不是“功能最多”或“开始收费”。

在 0.1.0 之前继续做并行、后台监督或 Billing，会同时扩大执行面、权限面、恢复状态和产品承诺，使 false PASS、workspace 损坏和首次使用失败更难归因。正确顺序是：

1. 0.0.20 先让 reviewer evidence、BYOK provider consent 和 Verification Criteria 可控。
2. 0.0.21 再让单个写入 Loop 使用 exact snapshot、独占 worktree、显式 bootstrap 和安全 Promote。
3. 0.1.0 RC 不再增加大功能，只修兼容、恢复、安装、文档和真实项目问题。
4. 0.1.0 公开发布后，再依次决定 [0.1.1 Security Evidence Adapters](0.1.1-security-evidence-adapters.md) 与 0.2.0；外部 scanner integration 和 Pro 编排都不能偷渡进 RC。

## 3. 0.1.0 包含什么

### 3.1 明确、不可弱化的 Finish Line

- Loop 启动前确认 Goal、Done when、Must not 与必跑 checks。
- Acceptance Contract、Gate Plan、workspace identity、approval 和 criteria digest 可追溯。
- 外部 transcript、Resume 内容、模型输出和 Skill 文本不能自行获得命令执行、修改合同或跳过 Gate 的权力。
- 修改 objective、required check 或 blocking criterion 必须创建 Revised Loop。

### 3.2 受控且可复用的 Verification Criteria

- deterministic checks、risk scan 和 fresh-context reviewer 保持职责分离。
- 所有 reviewer attempt 使用 bounded、去密、attempt-scoped evidence broker。
- workspace read trust 与“发送给 exact BYOK provider”的 run-scoped consent 分离。
- 只读取用户本机已有、用户确认、digest-pinned 的 strict qualitative criteria sidecar。
- Skill 不能执行 command，不能覆盖 deterministic failure，也不能单独产生 PASS。

### 3.3 单 Loop 隔离与安全回写

- 写入型 Loop 绑定 exact source snapshot，在 Wukong 明确拥有的独立 Git worktree 中执行。
- dirty workspace 只纳入用户确认的 tracked diff 与有限 untracked regular files；不自动 stash、commit、reset、checkout 或 push。
- candidate 依赖通过显式 bootstrap plan 准备；不隐式复用 source workspace 的 secret、`.env`、`node_modules`、虚拟环境或生成目录。
- candidate Gate 通过只进入 `awaiting_promotion`，不能直接产生 terminal PASS。
- Promote 使用 target-global lease、source drift 检查和幂等 Apply。
- Apply 后必须在真实目标 workspace 重新运行完整 frozen Gate；只有该 Final Gate 能产生 PASS。
- worktree 是写入碰撞隔离，不宣传为完整 filesystem/network/process sandbox。

### 3.4 Durable lifecycle 与恢复

- attempt、run、terminal、continuation、Revised Loop、candidate、Promote 和 Final Gate 使用同一 lineage。
- crash/restart 不重复 provider request、bootstrap、Apply 或 terminal 写入。
- 无法证明 owner、snapshot、lease、workspace 或 evidence freshness 时 fail closed。
- 失败候选默认保留为可恢复状态；清理只处理本 run 可证明拥有的路径。
- TUI 与 headless 使用同一状态和 reason codes。

### 3.5 可比较的 Finding 与 Gate Evidence

- `findingId` 由 remote-independent repository identity、provider/rule 或 criterion identity、semantic anchor 与可选 instance key 派生；不得包含 attempt ID、绝对 cwd、worktree 路径或易漂移行号。
- 每次 Gate observation 产生独立 `occurrenceId`，绑定 attempt、source snapshot、producer/version、scope 与 evidence digest；同一 finding 在不同 attempt 不能复用 occurrence。
- canonical observation/evidence immutable；人工 `accepted | false_positive | fixed | unclear`、显示状态和 policy projection 单独保存，不能改写历史 observation 或 artifact seal。
- 本地 lifecycle 统一为 `new | persisting | reopened | resolved | unknown`。只有同一 producer/rule scope 在当前 attempt 中有完整、可验证 coverage 时，缺失 finding 才能成为 `resolved`。
- partial/unknown coverage、cancelled/error attempt、schema/version unknown、artifact/seal corrupt 或不可比较 scope 一律得到 `unknown`，不能支持 PASS 或自动关闭 blocker。
- final Gate completion 必须在 required checks、risk scan、selected criteria、fresh reviewer、Apply lineage、artifact hash 与 `TargetGateCompletionSealV1` 全部重读验证后，才 CAS 提交 terminal；completed attempt 或文件存在都不是成功。
- finding history、feedback 与 canonical evidence 只保存在本机 private state；默认不生成报告、不上传 Web。

### 3.6 稳定发行面

- macOS、Linux、Windows 的六平台 ZIP/SHA、native bundle、fresh install 和 upgrade 可复现。
- `curl | sh` 安装、`wukong upgrade`、`wukong --version`、首启、Provider 配置、Resume、Loop 和恢复路径一致。
- Codex、Claude Code、Cursor、Kimi Code、Grok 的 Resume 只导入本地内容为可编辑 objective 草稿。
- public README、docs、Web、release notes、manifest 与安装器在同一 commit/release identity 上对齐。
- GitHub Actions 使用 immutable full commit SHA；checkout 默认 `persist-credentials: false`，job/token 权限最小化。
- release tag、package version、commit/main ancestry、manifest、asset name/size/digest 和 public release identity 必须一致。
- verify/test/build/pack/smoke 先产生一批 immutable artifacts；publish job 只能下载并发布同一批已验证 artifacts，不能重新 build、使用 mutable tag 或以 `--clobber` 掩盖 mismatch。
- 支持的平台使用 OIDC provenance/attestation；installer/upgrade 必须从 public URL 验证 exact release asset digest，而不是只信 workflow 或本地输出。
- 0.1.0 RC 期间不再添加新的默认命令。

## 4. Free 产品合同

0.1.0 公开版永久免费包含：

- 单个前台 `/loop` 与 `wukong loop`。
- 本地 BYOK writer/reviewer，不要求 Wukong 登录。
- Cross-Agent Resume。
- Finish Line、deterministic checks、risk scan、fresh reviewer 和 reusable criteria。
- 单 Loop worktree 隔离、candidate review、Promote 与 target Final Gate。
- 本地 stable finding/occurrence identity、coverage-aware lifecycle 与 sealed canonical Gate evidence。
- 本地 durable state、恢复、取消和显式 continuation。
- 当前高级诊断入口；默认命令面仍以 Resume → Loop → Gate 为主。

明确规则：

- 不按 Loop 次数、轮次或 BYOK token 收费。
- 本地执行不能依赖 Wukong quota 服务。
- 可选账号登录不能变成本地 Loop 的准入条件。
- Wukong 没有模型时，登录和空模型目录仍应诚实成功，不影响 BYOK 默认路径。

## 5. 0.1.0 明确不做

- Bounded Parallel Loop、递归 Agent Tree 或公开 worker 数量承诺。
- Detach、Local Loop Supervisor、跨 repo exception view 或开机常驻。
- GitHub PR Gate publish、自动 comment/status、GitHub App 或组织 CI。
- Stripe、Checkout、Customer Portal、paid entitlement、年付或 Team 套餐。
- managed model、模型 credits、托管 reviewer 或 BYOK 加价。
- Hosted Terminal、Hosted Report、源码/evidence 云同步。
- Remote Control、手机控制、Slack Agent、云端 Routine 或 `/schedule`。
- telemetry 产品指标后端；产品验证使用显式 opt-in cohort、`/feedback`、访谈和可复现案例。
- 完整 filesystem/network/environment/process sandbox。
- Codex Security/Semgrep/CodeQL/Snyk 的执行或导入 adapter、generic SARIF provider、bulk/deep scan；这些只进入 0.1.1 或更后版本的独立批准。
- 新的默认 `/parallel`、`/agents`、`/worktree`、`/supervisor`、`/ship` 命令。

这些“不做”项不能通过 experimental flag、隐藏页面、占位 API 或营销文案提前变成公开承诺。

## 6. 发布前的真实用户门槛

由于当前不建设 telemetry 产品指标后端，0.1.0 使用显式 opt-in Beta cohort 验证。每条记录必须可回溯到用户授权的访谈、反馈或复现记录，不能用注册数、默认 Free rows、匿名安装 ping 或模型自评代替。

公开 0.1.0 前至少满足：

| 门槛 | 最低证据 |
|---|---:|
| 确认参与的外部测试者 | 25 |
| 在真实 repo 完成首个 Loop 的不同测试者 | 15 |
| 14 天内重复完成 Loop 的不同测试者 | 7 |
| 获得授权、可复现的 case studies | 3 |
| install/upgrade/resume/loop/gate/promote 已知 P0/P1 | 0 |
| false PASS、workspace damage、隐私误解未解决项 | 0 |
| RC 连续稳定期 | 14 天 |

“完成”必须是 target Final Gate 的真实 PASS；started、candidate PASS、abandoned、演示仓 smoke 或团队内部账号不计入外部完成用户。

## 7. 四类发布门槛

### 7.1 Contract / Security

- Acceptance、criteria、snapshot、candidate、Promote、Final Gate 和 terminal lineage 全链路可校验。
- finding/occurrence identity 不依赖 cwd/worktree/行号；immutable observation、mutable disposition、coverage scope 和 completion seal 可独立校验。
- secret、raw source、prompt、transcript、绝对路径和未经确认的 evidence 不进入 Web、feedback 或普通日志。
- stale approval、source drift、lease conflict、unknown owner 和 partial Apply 全部 fail closed。
- partial/unknown coverage、schema/version drift、corrupt artifact/seal、cancelled attempt 和无 owner `running` 状态不能被恢复或聚合成 PASS/resolved。
- permission、provider consent 和 budget 不能因 Resume、restart 或 Promote 扩大。

### 7.2 Automated Quality

- 相关 unit/integration/E2E、typecheck、lint、docs build 和 installer validator 通过。
- clean checkout 可以构建；tracked files、changeset、workspace manifest 和 Nix workspace 清单对齐。
- 六平台 bundle/native smoke、0.0.21 → 0.1.0 upgrade 和 0.1.0 fresh install 通过。
- fault-injection 覆盖 crash、cancel、provider failure、bootstrap failure、lease loss、source drift 和 partial Promote。
- 负向矩阵覆盖 completion-before-validation、manifest/evidence/seal 篡改 resume、required coverage 不完整、持久化前 redaction、SIGINT/SIGTERM late completion 与 Windows path/atomic replace。
- finding identity golden fixtures 覆盖跨 worktree/clone、文件移动/行号变化、同 rule 多 instance、reopened 与 coverage-incomplete unknown。

### 7.3 Real User Flow

- 全新用户能完成 install → provider → first Loop → candidate review → Promote → Final Gate。
- 有测试、无测试、dirty workspace、monorepo、多语言项目与至少一个 Windows repo 完成真实 E2E。
- Codex/Claude/Cursor/Kimi/Grok Resume 不自动获得验收权。
- 错误提示能说明下一步，不要求用户读内部 record 或日志才能恢复。

### 7.4 Release / Public Truth

- package version、tag、GitHub Release、12 个 assets、SHA、manifest、installer、README、docs、Web release page 和 What's Changed 一致。
- workflow actions full-SHA pinned、checkout credential persistence 关闭、release job 最小权限；tag/version/main ancestry validation 有失败测试。
- build-once/publish-exact artifact digest 与 OIDC provenance/attestation 可从 public package/release 验证。
- fresh install 与 upgrade 都从 public URL 验证，不只检查本地构建输出。
- 官网只宣传已通过验收的 0.1.0 能力，不出现 Pro、并行、Supervisor、Hosted 或 managed model 占位承诺。
- 发布后 health、版本 API、installer 和关键页面可访问；回滚路径已演练。

## 8. RC 与正式发布规则

1. 只有 0.0.20 和 0.0.21 的四类发布门槛完成后，才能切 `0.1.0-rc.1`。
2. RC 只接受 P0/P1 修复、兼容性、性能、文档和发布工程变更。
3. 任一 false PASS、workspace damage、隐私边界错误或不可恢复 Promote 都重置 14 天稳定期。
4. RC 不与 0.2.0 Pro Pilot、Checkout 或 public pricing 合并发布。
5. 正式版发布后先观察稳定性和重复使用，再依次决定是否批准 0.1.1 adapter 与 0.2.0 编排；二者都不是 0.1.0 release checklist。

## 9. 0.1.0 完成定义

只有同时满足以下条件，0.1.0 才算实现：

1. 0.0.19–0.0.21 合同在真实 release build 中完整连通。
2. target Final Gate 是唯一 terminal PASS 来源。
3. PASS terminal 只引用重读验证通过的 completion seal；crash/cancel/corrupt resume/partial coverage 不产生 false PASS。
4. finding/occurrence identity、coverage-aware lifecycle、immutable observation 与 mutable feedback 在跨 worktree/restart 中稳定。
5. 所有四类发布门槛与 opt-in cohort 门槛有可审计证据。
6. Free/BYOK/无 quota/无付费的产品、代码、Web 和文档口径一致。
7. 公开安装、升级、恢复和回滚验证 exact published artifact；release provenance 与 commit/tag/version/manifest 一致。
8. 所有已知 P0/P1 清零，RC 连续稳定 14 天。
9. 0.1.1/0.2.0 能力没有偷渡进默认命令面或公开承诺。

在此之前，文档只能写“规划”或“RC”，不能写“0.1.0 已实现”。
