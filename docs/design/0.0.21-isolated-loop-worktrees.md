## 一句话定义

> **让一个写入型 Loop 在绑定精确源码快照的独立 Git worktree 中修改和验证；候选结果只有经过显式 Promote、应用到目标 workspace 并重新通过最终 Gate，才能得到 terminal PASS。**

0.0.19 解决“怎样算完成”，0.0.20 解决“项目验收规则怎样复用”，0.0.21 解决“Agent 怎样把独立 worktree 作为正常写入目标，并在应用前检测 source drift”。这减少写入碰撞，但没有完整 sandbox 时不能承诺任意 shell 绝不会触碰用户 workspace 或其他系统路径。

本版先证明 **一个 Loop 的隔离执行与安全回写**，随后进入 [0.1.0 Trusted Local Loop](0.1.0-trusted-local-loop.md) 稳定化。多 Agent 并行与本机多 Loop 监督统一后移到 [0.2.0 Pro Reliable Autonomy](0.2.0-pro-reliable-autonomy.md)。

## 当前实施进度

- 新增默认关闭的 `isolated_loop_worktrees` experimental flag。
- `/loop --dry-run` 可只读生成 `SourceSnapshotDryRunV1`，不会创建 worktree、blob、run 或执行 candidate。
- 支持 clean、staged、unstaged 与用户显式选择的有限 untracked source projection。
- snapshot 绑定 policy/limits、Git repository identity、source workspace identity 与 repository-relative cwd。
- secret、generated、oversize、symlink、gitlink、path escape、portable case collision、unsupported index state、Git environment override 和仓库配置的外部 Git helper 均 fail closed。
- Headless 暂以隐藏的可重复 `--include-untracked` 提供选择入口；被 policy 排除的显式选择会阻断，不会静默丢弃。
- exact-byte sealer 在读取前后复核 approved snapshot，从 Git index blob 与 source worktree 分别读取冻结 postimage；rename 固定展开为 delete + add，drift、blocked snapshot、symlink/hardlink 与不安全父路径均阻断。
- 新增不可压缩、长度分帧的 `WKSMAT01` materialization container；manifest 分别冻结 index/worktree postimage，并绑定 Git index object ID、source snapshot 与 policy digest。
- 新增私有 `SnapshotBlobLeaseStore`：`0700/0600` 权限、不可枚举 raw fencing token、跨进程锁、CAS/journal、过期、单次 consume、精确 unlink 与 durable destroyed tombstone。

- materialization intent/record 额外绑定 exact Worktree Lease 与内部 candidate branch；record 已完成但 lease 尚未提交时，可重读 artifact、candidate path identity 与全部 immutable binding 后幂等完成。

- 新增 canonical `CandidateBootstrapPlanV1`/step contract：冻结 recipe/version、executable/runtime identity、私有 argv/env ref 及 digest、generated scopes、timeout、network/registry/permission/budget，并强制 lifecycle scripts 为 `deny`。
- 新增 canonical bootstrap budget/reservation/event contract：每个 step 在执行前预留 wall-clock/generated/output，budget 与 reservation 分别 CAS，event 链接前一 budget/reservation digest；`settled` 只释放可验证的未用额度，`retained_unknown` 保留完整预留。
- 新增 canonical bootstrap execution journal contract：强制 `prepared → started → observed/failed` 顺序，只有 exact fencing token 能追加；同 owner 可依据真实 generated-scope fingerprint reconciliation，存在 prepared/running step 时禁止 ownership adoption。
- 新增 trusted runtime identity：原生 executable 绑定 normalized realpath、device/inode/mode/size/content、runtime version 和父目录 identity；拒绝 symlink、hardlink、repo/candidate/generated root、PATH 间接解析及 inspect/spawn drift。常见 npm script shim 以 native Node + frozen npm package bundle 形成复合 identity，并在 probe、private staging、spawn 前后重验；其他未冻结的解释器 + script/shim 仍 fail closed。
- 新增 `0700/0600` Bootstrap 私有输入存储：exact argv/env/executable path 不进入公开 plan、journal 或日志，跨进程锁保护 stage/resume/use；销毁先 durable 写无 secret tombstone，再 exact-identity unlink，崩溃后可继续完成删除。
- 新增原子 `CandidateBootstrapStateStore`：budget、reservation、execution journal、事件链和当前 Worktree Lease/fencing binding 在同一 fsync 边界提交；重复 transition 幂等，竞争 prepare 只有一个成功，running/usage 无法证明时转为 `retained_unknown` 并禁止 ownership adoption。
- 新增并接入 confirmed `/loop` 的 POSIX `CandidateBootstrapExecutor`：只在 exact `bootstrapping` lease capability 内运行，durable `prepared + started` 后才使用 `shell:false` 和冻结 env spawn；执行前后重扫非 generated source projection，单独计量 generated scopes/output/wall-clock，超限、超时、取消、可执行文件漂移和未知进程组状态均 fail closed。

- 新增 canonical Candidate projection/change manifest/delta：在 bootstrap 完成、Writer 启动前持久化 source-content baseline，排除 plan 声明的 generated scopes；后续只把 Agent 造成的 create/update/delete/rename/mode 纳入 delta，用户 snapshot 中原有 staged/unstaged/untracked 内容不会被重复算作 Agent change。projection 拒绝 symlink、hardlink、unsafe node、越界容量和跨平台 path alias。
- 新增 capability-bound `CandidateDeltaStore`：baseline 与每个 `verifying` lease revision 的 delta seal 位于 source/candidate workspace 外的 `0700/0600` 私有 owner 目录，使用跨进程锁、原子写与 fsync；同一 revision 精确重试幂等，seal 后变更、record 篡改或 stale lease/fencing 均 fail closed。Gate `NEEDS_WORK → active → verifying` 会追加新 revision seal并保留旧轮证据，不会被首轮失败 seal 卡死。
- 新增 capability-bound deterministic Candidate Gate：source-approved Gate Plan 通过 shared Git common-dir identity 和 Worktree Lease 中的 exact gate-plan digest 重绑到 detached candidate；执行前先封存 exact CandidateDelta，Gate 前后复核冻结 check/review-policy 定义并运行 checks 与 builtin risk scan，执行后再次核对同一 delta seal。check 若改写可 Promote 内容、candidate/lease 漂移或 seal 不匹配均拒绝结论；结果携带 candidate/lease/candidateDelta/seal digest。该段尚不包含 brokered fresh reviewer、Promote 或 terminal seal。
- 新增 canonical `CandidateGateResultV1` 纯合同与校验：只记录 exact candidate、candidate delta、Gate attempt 和 `PASS/NEEDS_WORK/ERROR` outcome，并封存 result digest；deterministic Gate 不会自行生成完整 `PASS`，只有 durable brokered reviewer orchestration 可以提交该合同。
- 新增 Candidate brokered review plan 投影：只有 exact CandidateDelta 中存在 postimage 的路径会进入 Review Subject，原始 dirty snapshot 中未被 Agent 改动的路径不会泄漏到 reviewer；delete 与全部 create/update/rename/mode 以 digest-bound metadata evidence 表示，deterministic check stdout/stderr 和 risk evidence 继续交给现有 broker 做 secret/exclusion/size 处理。该受限输入现已由 Candidate fresh reviewer 使用。
- 新增 candidate-bound Review Subject Broker 生命周期：只在 exact `verifying` lease、active source-workspace trust/consent 与同一 delta seal 下构建 attempt-scoped broker；回调后重读 subject manifest、复核 trust 和 delta seal并销毁 broker，逃逸 broker 与 reviewer 期间的 candidate mutation 均 fail closed。provider/model origin lock、fresh verdict 与完整 Gate result 持久化已接默认关闭的 experimental `/loop` orchestration；experiment 关闭时保持原路径。
- 新增 durable `CandidateGateAttemptV1` 与私有 store：`prepared → deterministic_completed → reviewing → completed` 使用 CAS、event-first journal、fsync 和单步 journal-ahead recovery；attempt 精确绑定 verifying lease revision/digest、CandidateDelta seal、Gate Plan、deterministic result、Review Subject manifest、reviewer input、原始 provider payload digest 和结构化 verdict digest。deterministic blocker 不伪造 reviewer，invalid/inconclusive/provider failure 只能产生 `ERROR`。
- 新增 origin-locked Candidate fresh reviewer：provider/model 解析后按冻结 consent 逐请求锁定 exact origin、拒绝 redirect，仅安装 `ReadReviewSubject`、`SearchReviewSubjects`、`ReadGateEvidence` 三个 attempt-scoped broker 工具；模型调用前先 durable 提交 `reviewing`，调用后复核 consent、trust、manifest 和 delta。原始输出不持久化，只有 domain-separated digest；合法 PASS/NEEDS_WORK/INCONCLUSIVE 分别映射为 Candidate `PASS/NEEDS_WORK/ERROR`。
- 新增 Candidate Gate orchestration join：串联 deterministic Gate、broker plan、fresh reviewer 与完整 `CandidateGateResultV1`，重读验证 completed attempt 后才允许 `verifying → awaiting_promotion`；NEEDS_WORK 返回 `active`，ERROR 写入 exact `verifying → active` recovery transition。lease transition event 绑定 exact attempt ID 与 previous verifying lease digest，crash 后只有 journal evidence 可证明同一 join，candidate PASS 仍不会产生 root terminal PASS。
- 新增 canonical `IsolatedLoopCandidateBindingV1` 与 Goal record/replay：一个 run 只能绑定一个 exact candidate/Worktree Lease/source snapshot/bootstrap plan/Gate Plan/criteria selection，普通 snapshot 只暴露 candidate/lease/binding digest，不暴露路径或 raw fencing token。Gate attempt UUID 由 binding 与当前 verifying lease revision 确定派生，所以 NEEDS_WORK 后的新 revision 得到新 attempt，重启同一 revision 则精确重用。
- 新增 candidate preparer、iteration orchestration 与默认关闭的 Agent RPC/Node SDK/TUI/Headless 调用面：reserve 后、任何 candidate 文件写入前先提交 Goal binding；随后才 materialize，按 frozen plan 选择直接 activate 或 exact bootstrap，再运行受限 Writer、进入 verifying 并调用 Candidate Gate。Blob `sealed|confirmed` owner 与 `bootstrapping|active|verifying|awaiting_promotion` candidate root 可从私有 capability 文件恢复，恢复仍要求 exact owner、lease digest、fencing、expiry 和 identity。
- 冻结 Promote 第一层纯合同：`TargetStateFingerprintV1` 绑定 target workspace/Git common-dir、HEAD/branch/index、tracked/untracked/protected refs、source snapshot 与 promotable content；promotion consent 精确绑定 candidate delta、Candidate Gate result、target fingerprint 和 permission；`TargetPromotionLeaseV1` 以 canonical registry key、revision、owner process identity digest、fencing-token digest 和单调状态转换 fail closed。
- 新增用户级 `TargetPromotionLeaseStore`：registry 位于调用方提供的全局私有根而不是 session/candidate 内；每个 canonical target key 以真实跨进程锁、CAS revision、隐藏 raw fencing token、0600 capability、event-first hash journal 和 atomic state 推进。并发 acquire/adopt 只有一个 owner，released 后的新 acquisition 继续同一 revision/event chain 并轮换 token；journal 领先 state 一步可修复，旧 binding、错误 process identity、伪造 event 语义、tampered capability 或 chain divergence fail closed。
- 新增并接入 POSIX process liveness proof：绑定 PID、平台与 OS process start marker digest；只有进程明确不存在，或同 PID 的 start marker 已变化时才判旧 owner 已死亡。权限错误、probe timeout、不可用平台或跨平台读取只返回 `unknown`，不能触发 adoption。Target Promotion Lease 通过 crash-safe pending/event/capability 提交保持 state/ownerRun 不变并单调轮换 process identity 与 fencing token；runtime 可恢复 `acquired`、`applying` 与 `final_verifying`。
- Apply 恢复保留 created-by token provenance，同时维护 current fencing token 与单调 lineage；partial Apply 后只用 frozen source metadata 重建原 consent registry key，且必须再次匹配用户原始 proposal digest。prepared change 逐 path 比较真实 preimage/postimage：preimage 才执行、postimage 只追加 reconciled、其他状态进入 conflict/reconciliation，绝不从头盲目重放 patch。
- Final Gate 恢复不改写已经 durable 的 Apply head、evidence、result 或 completion seal；历史 artifact 保留产生它的 fencing token，新 owner 通过 Target Final Gate attempt lineage 建立当前 authority，producer 在 evidence 已落盘后不会重跑，historical seal 只在同一进程内经 lineage 重验后获得 terminal authorization。
- target lease 现持久化 exact promotion consent、candidate delta 与 Candidate Gate result digest，恢复后不能用同 candidate id 偷换用户未确认的 delta/Gate。
- 新增 `PromotionApplyJournalV1`、event-first `PromotionApplyJournalStore`、逐 change applier 与 Promote Apply orchestrator：整个 Apply callback 持有 target-global OS lock；每项 create/update/delete/rename/mode 都先 durable `prepared`、再核对真实 preimage、写入/fsync、核对 postimage 后追加 `applied`。crash 后若路径已等于 postimage 只追加 `reconciled`，外部 edit、symlink/unsafe parent、candidate byte drift 或中间状态追加 conflict/fail closed。所有 change 完成后重建 post-Apply 完整 target fingerprint，journal 标记 applied 后 lease 才进入 `final_verifying`。
- macOS/Linux Target Apply 使用 descriptor-rooted parent fd 与原生 atomic no-replace/exchange；final check 持有 preimage fd，mutation 后必须匹配同一 `(dev, ino)`，所以普通编辑器在最终检查后用同 bytes/mode atomic-save 也不会被静默删除或覆盖。deterministic transaction directory 现在包含 exact owner、identity、committed markers：identity 在 syscall 前持久化 preimage/stage `(dev, ino)` 与 change binding，committed 只在原子后验通过后落盘；backend 保留 receipt/quarantine，Apply journal 先 durable `applied/reconciled`，再写入绑定每个 artifact `(dev, ino)`、mode、size 与 content digest 的 cleanup manifest，把整个事务目录原子 no-replace 隔离到 cleanup namespace 后幂等删除。cleanup manifest 准备、目录隔离、部分 artifact 删除或 manifest 删除后的中断都可继续，manifest/artifact 漂移则 fail closed。prepared 状态没有 receipt，或目标虽同内容但 inode 不属于 receipt 时同样阻断；rename recovery 补齐 parent fsync，nested delete 的缺失 parent 按 absent reconciliation。zero-write capability probe 只证明 native primitive 可加载，目标 mount 是否支持 flags 由每次实际 no-replace/exchange syscall 证明，失败不回退。该边界不承诺隔离专门读取或伪造内部 artifact 的同 UID 恶意进程，也不是完整 process sandbox。
- 新增 target Final Gate 完整内部提交链：`TargetFinalGateEvidenceSnapshotV1` 将现有 Goal Gate 的 ordered checks、risk scan、criteria verdict、fresh reviewer 与 proof aggregate 重新绑定到 post-Apply target fingerprint、journal head 和 target fencing token；durable attempt store 使用 `prepared → evidence_recorded → completed` CAS/event-first journal，orchestrator 在 target-global `final_verifying` 锁内执行并可从 evidence/complete 边界恢复。
- 新增 `TargetGateCompletionSealV1` 与私有 artifact store：`promotion_apply_journal`、`final_gate_evidence_snapshot`、`final_gate_attempt_result` 三类 opaque artifact 必须恰好各一个且顺序固定；`0700/0600`、no-follow、regular-file/nlink、长度/hash、Gate coverage、target fingerprint、journal/fencing 与 attempt lineage 均重读验证并进入独立 completion digest。非 PASS seal 只能留证，不能成为 terminal PASS。
- 新增一次性、锁作用域内的 completion authorization 与幂等 terminal finalizer：Goal record 先持久化 exact completion seal，再写唯一 terminal；seal/run/contract/attempt/result/fingerprint/journal/fencing 任一 join 不一致均拒绝。terminal 已写而 target lease release 失败时，重试复用同一 terminal 并完成 release；record replay 必须先恢复 seal，孤立 terminal 不能恢复为 PASS。
- snapshot 固化本次生效 limits，candidate 复核不依赖调用方重建隐含配置；clean tracked bytes 如需 Git worktree conversion，或遇到 LFS pointer、symlink/gitlink、非 portable path、越界 root 与并发重复 claim，均 fail closed。
- targeted contract/CLI/store/materialization/recovery tests 与相关 typecheck/lint 已通过。

默认关闭的 experimental 产品链现已接通 Source Snapshot → optional exact-confirmed bootstrap → Candidate Writer → Candidate Gate → exact promotion challenge → Promote Apply → target Final Gate → completion seal → terminal join。TUI 可显式多选 eligible untracked 并用选择结果重新运行 dry-run；随后在创建 Goal/candidate 前展示只读 Source Snapshot 的 branch、base、tracked/untracked/exclusion 口径与 exact digest，以及 bootstrap steps、network policy、budget 与 plan digest，Cancel 保持零 Goal/run/worktree/source write。TUI 等待人类选择 `Promote` 时不持 target lease；选择 Keep/Esc 会暂停并保留 challenge。Headless 首次运行只输出 `loop.promotion_required`，必须恢复同一 session 并提交 `--promote-candidate <proposalDigest>` 才能 Apply；stream-json 使用独立 candidate/final Gate 事件。Promote 在 terminal 前抛错时，TUI/Headless 都会重新暂停 Goal 并保留 exact candidate/challenge。Candidate Gate `ERROR` 会先写 exact recovery transition再回 `active`，后续显式 rerun 使用新的 verifying revision/attempt，不会永久重读同一个 runtime error。

真实临时 Git 仓库 E2E 已覆盖：Candidate Writer 只修改 detached candidate、Candidate PASS 前后 source 保持干净、stale proposal digest 零写入、exact consent 后逐 change Apply、post-Apply target Final Gate、completion seal 与最终 PASS terminal。该 E2E 同时验证首次运行会初始化独立 Candidate 私有状态根，且 target Final Gate 计算结果会先持久化 exact Goal Gate audit 再构造 target evidence。

Target Final Gate fault coverage 已补 evidence 两侧的 durable boundary：producer 在 evidence 前取消时 attempt 只保留 `prepared` 且没有 evidence/result/terminal，后续可恢复同一 attempt；evidence 已 durable、result 尚未提交时，恢复不会再次调用 producer，而是从 exact evidence 完成同一 attempt。promotion Apply 也已接 cooperative `AbortSignal`：首个 write 前取消保持零写入；每个 change 的 durable `applied`/`reconciled` event 后再次检查 signal，取消时保留 `applying` 与 journal，retry 不重复已提交 change。durable error schema 只写固定 reason/status/digest；fresh reviewer exception 的任意 message/reasonCode 在 Candidate Gate attempt 前映射为固定 allowlist，secret sentinel 不进入持久化状态。Candidate Writer 泄露工具、Target Apply escaped authority 和独占锁已覆盖 late-write fencing；create/update/delete/rename/mode 五类 operation 均覆盖有 identity receipt 的 postimage 恢复，无 receipt 的同内容 postimage 会阻断。dead-owner recovery 还覆盖 Final Gate evidence/result 已提交、seal 已提交以及 terminal release 重试。POSIX process-level matrix 现覆盖：Source Snapshot sealer 四边界 SIGINT/SIGTERM 8/8 保持 source HEAD/index/staged/unstaged/untracked 逻辑状态不变；materializer 在 candidate record 已同步后的 2/2 会先重验 exact candidate record，再按 confirmed → materializing ancestry 回收 stranded source Blob，最后完成 worktree transition；Bootstrap `step_running` 2/2；Candidate Writer 在 temporary fsync、final-leaf check 与 atomic replace 两侧 6/6 分别保留完整旧 leaf 或完整新 leaf，崩溃遗留的私有 temporary 不进入 Candidate 搜索结果；Target Apply、Final Gate、completion seal 的 production-path 10 个 signal case，以及 synthetic target durable/terminal boundaries 10 个 case 也已通过，新增 outcome 已 durable、receipt 尚未清理的 SIGINT/SIGTERM 恢复。该证据完成 POSIX component-level hard-signal matrix，但不能外推为尚未实现 handle-relative backend 的 Windows termination 证据。

Worktree `creating`/`materializing`/`bootstrapping` 已实现无当前 holder runtime adoption：只有 PID + OS start marker 明确判 dead 才轮换 owner process identity 与 fencing；live/unknown 均 fail closed。materialization record 只可沿同状态 authenticated ownership ancestry 恢复，bootstrap state 只可在 journal `ready` 且无 reserved/running step 时重绑；未知运行步骤保留 attention，不盲目重跑。candidate materialization policy 已明确禁止 excluded-tracked overlay 和静默丢弃；任一 exclusion 阻断 sealing，只有显式批准的 selected-untracked 可进入镜像，决策与 limits 一并进入 policy digest。macOS/Linux candidate 文件工具的 descriptor-rooted backend 已有本地执行证据；Windows handle-relative/reparse-point/ACL/atomic replace 与 Target quarantine transaction 已实现并通过跨平台编译/纯布局测试，但 8 个原生 integration 和 19 个 forced-termination 等价用例尚未在真实 Windows runner 执行。macOS 本地四生态无依赖 dirty-workspace 完整 Loop harness 4/4 通过；dependencyful Node/Python/Rust 3/3 也完成 fixed registry bootstrap → Candidate → Promote → target Final PASS。Go 相同 harness 已实现，但本机到官方 proxy 的直连超时，且产品不能静默继承 ambient proxy，因此不计为通过；远端 job 必须四生态 4/4。仍无固定 SHA 的远端 CI、授权真实项目、三 OS E2E、六平台安装升级或固定五用户证据；当前 E2E 和 recovery 不等于 0.0.21 已可发布。

## 当前实现基线与问题

当前 subagent 直接继承父 Agent 的 `cwd`。现有 worktree 支持只用于识别 Git control directory 和 linked worktree，没有 `git worktree add/remove` 的受控生命周期。

这会产生以下问题：

1. 写 Agent 会直接修改用户当前 workspace，失败或取消后难以区分哪些文件属于本次尝试。
2. dirty workspace、外部 Resume 内容和 Agent 新修改混在一起，Gate evidence 很难证明精确来源。
3. 子 Agent 可以和父 Agent 或其他写 Agent覆盖同一文件。
4. crash 后无法证明某个残留目录是否由当前 run 创建，也无法安全清理。
5. 候选结果与最终应用没有独立状态，容易把“候选检查通过”误报成“用户 workspace 已完成”。
6. 自动 stash、reset、commit 或 branch 切换会改写用户已有 Git 状态，不适合作为隐式实现方式。

## 版本目标

1. 为单个写入型 Loop 创建独占 Git worktree 和候选 branch。
2. 支持 clean workspace，以及经用户确认纳入的 tracked diff 和有限 untracked files。
3. 不自动 stash、commit、reset、checkout 用户 branch 或改写 index。
4. 将 source snapshot、Acceptance Contract、Gate Plan、criteria selection、run 和 worktree lease 绑定。
5. writer、checks、risk scan 和 reviewer 都对同一个候选 worktree snapshot 工作。
6. 内置写工具只能写入候选 worktree；不能写父 workspace、其他 worktree 或 Git control directory。Bash/package script 仍受现有 permission/guard 和 source drift revalidation 约束，不宣传为强制 containment。
7. 候选 Gate 通过后进入 `awaiting_promotion`，不能直接 terminal PASS。
8. Promote 必须先取得目标 workspace identity 级的跨进程独占 lease，并在 lease 内重新验证 workspace、branch、index、HEAD 和 source snapshot。
9. Apply 后在目标 workspace 重新运行完整 frozen Gate。
10. crash/restart 能恢复 lease、候选状态和 Promote 决策，不重复创建或应用。
11. 失败 worktree 默认保留为可恢复状态；清理只能处理本 run 明确拥有的路径。
12. TUI 和 Headless 都能清楚区分 source、candidate、promoted 和 final Gate。
13. target Final Gate 先验证并 seal canonical evidence，再把 terminal record 作为最后提交点；crash/resume、取消和损坏 artifact 不能恢复出 false PASS。

## 0.0.19 / 0.0.20 强依赖

实施前必须满足：

1. 0.0.19 的 frozen Acceptance Contract、Gate Plan、workspace trust、approval CAS 和 source definition freshness 已稳定。
2. Gate attempt、terminal、continuation 和 Revised Loop 的 durable join 已通过真实 E2E。
3. 0.0.20 的 brokered reviewer、exact BYOK provider consent、criteria digest 和 evidence refs 已稳定。
4. 候选 worktree 与目标 workspace 必须复用同一套 deterministic check、risk scan 和 reviewer verdict 规则。
5. 任何旧合同、旧 PASS 或外部 transcript 都不能获得 worktree 创建、Promote 或 Apply 权限。

任一前置不成立时，0.0.21 只能生成只读 proposal，不能创建 worktree 或应用候选结果。

- untracked 文件必须逐项满足 regular-file、workspace-relative、大小上限和 secret policy，并由用户确认。

- 被排除文件如果是 Gate 的必要输入，返回 `snapshot_dependency_excluded`，不得静默使用父 workspace 内容。
- snapshot record 只保存路径投影、大小和 digest；raw patch、源码和 secret 不进入普通日志、feedback 或 Wukong Web。
- exact bytes 先写入本机私有、短生命周期的 `SnapshotBlobLeaseV1`；它是 materialization 输入，不是 durable contract/evidence。

Blob 规则：

- 位于 `<WUKONG_CODE_HOME>/runtime/isolated-loop/snapshot-blobs/<blobLeaseId>/`，使用不可预测 lease ID；POSIX 根目录/lease/event 目录固定 `0700`，文件固定 `0600`。Windows 私有 durable root 使用 current-user owner、present/non-null/protected DACL，ACE 只允许 `CURRENT_USER` + `LOCAL_SYSTEM` 的继承 full access；创建后在首个 private file write 前施加并重验 exact SDDL，复用时只读重验，路径必须 final-path exact、directory/non-reparse。Candidate/Target preflight 会区分 ACL primitive 与 handle backend 缺失，并在创建 Blob 前零写阻断。实际 ACL 与 NtCreateFile 调用仍须由真实 Windows runner 证明，纯合同测试不能替代。
- `0600/0700` 只能阻止其他 OS 用户，不能隔离同一 UID 下的任意 shell。0.0.21 只承诺 Wukong 不通过 prompt、工具、普通 records 或 API 暴露该 blob，不能把它描述成 OS sandbox。
- 只包含已确认 snapshot 所需的 exact tracked delta 与 selected untracked bytes。
- 只是 worktree materialization 的内部短生命周期传输载体；writer、reviewer、Skill 和用户 recipe 都不可访问，也不提供 0.0.20 Horizon 所说的通用 private scratch/artifact 能力。
- 不进入 prompt、review broker、普通 records、日志、feedback 或 Wukong Web。
- `privateBlobPathIdentity` 与 `fencingTokenDigest` 都是 domain-separated digest；public lease、日志和调用方永不获得真实 blob 路径或 raw fencing token。raw token 只存在于 store 内部 capability binding。
- 用户确认必须绑定 exact sealed `leaseDigest`，同时绑定 snapshot、manifest 和 policy digests；不能只确认裸 `contentDigest`。确认后 materialization 不再从 source workspace 动态补读。
- 每次状态改变都在跨进程锁内重新读取当前 record，校验 expected `casRevision`、`leaseDigest` 和 raw fencing token，再 durable append/fsync event 并以 CAS 单调推进。旧 owner 或旧 token 不能读取、消费、恢复或销毁新 lease。
- 允许的主路径是 `staging → sealed → confirmed → materializing → consumed → destroying → destroyed`。`staging/sealed/confirmed/materializing` 可在当前 owner 明确中止或 crash reconciliation 证明没有 live owner 后进入 `expired`/`corrupt`；用户明确 Cancel/拒绝时当前 owner 也可直接进入 `destroying`。`expired`/`corrupt` 只能经 `destroying` 进入 `destroyed`，所有路径都不能回退或复用。
- materialization 成功后先 durable 记录 `consumed`，再 durable 记录 `destroying`，关闭所有句柄，按已验证的 exact file identity unlink payload 并 fsync parent，最后写入 durable `destroyed` tombstone。只有 tombstone 成功后才允许 bootstrap、writer、reviewer、Skill 或用户 recipe 启动。
- Cancel、拒绝或过期同样走 `destroying → destroyed`。重复 destroy 必须幂等，且只能删除该 lease 已验证的 payload，不能递归清理未知文件。
- 这里的 destroy 只承诺关闭句柄、移除命名入口和持久化 tombstone；不宣称在 SSD、快照或 copy-on-write 文件系统上完成安全擦除。
- crash 后只有 blob file identity、owner、权限、link count、长度、digest、manifest、journal head 和 lease 全部有效时才可恢复；缺失或损坏时废弃 candidate，销毁残留并重新扫描，要求用户确认新 snapshot。

### 2. Snapshot materialization 必须确定

候选 worktree 不能只从 `baseCommit` 创建后直接开始写，否则 source workspace 中已确认的 staged/unstaged 和 untracked 内容会丢失。

snapshot exact bytes 使用 Wukong 自定义、不可压缩、长度分帧的容器，不使用 tar/zip 或通用 archive extractor：

```ts
interface SnapshotMaterializationImageV1 {
  readonly mode: number;
  readonly sizeBytes: number;
  readonly offsetBytes: number;
  readonly contentDigest: string;
  readonly imageDigest: string;
}

interface SnapshotMaterializationEntryV1 {
  readonly canonicalRelativePath: string;
  readonly selectedUntracked: boolean;
  readonly indexObjectId: string | null;
  readonly indexImage: SnapshotMaterializationImageV1 | null;
  readonly worktreeImage: SnapshotMaterializationImageV1 | null;
  readonly entryDigest: string;
}

interface SnapshotMaterializationManifestV1 {
  readonly schemaVersion: 1;
  readonly formatVersion: 1;
  readonly sourceSnapshotDigest: string;
  readonly snapshotPolicyDigest: string;
  readonly materializationPolicyDigest: string;
  readonly entries: readonly SnapshotMaterializationEntryV1[];
  readonly entryCount: number;
  readonly payloadSizeBytes: number;
  readonly manifestDigest: string;

```

Manifest/container 规则：

- container 固定 magic、format version、canonical manifest length、payload length 和 exact total length；尾随字节、截断、压缩、稀疏/重叠 offset 或非 canonical JSON 一律拒绝。
- entries 按 NFC canonical relative path 排序；拒绝空路径、绝对路径、`..`、反斜杠、NUL、`.git` control segment、Windows device/alternate-stream/尾随点空格、超长 path/segment、重复路径以及 Unicode NFC + lower-case 的 portable collision。
- `indexImage` 和 `worktreeImage` 分别是该路径在 source index 与 source worktree 的冻结 postimage；`null` 表示该 postimage 不存在。同一路径 staged+unstaged、delete/recreate 和 add/delete 不得折叠为单个 patch。
- `indexObjectId` 必须是 index postimage 的 exact Git blob OID；index postimage 不存在时必须为 `null`。它用于从冻结 bytes 重新计算 tracked projection，不能由路径或 worktree bytes 推断。
- 每个 image 只允许 regular file mode，绑定 exact size、payload offset 与 content digest；entry、manifest、container 和 lease 使用不同 domain 的 digest。
- parser 只返回已完整验证的只读 manifest 与受限 payload view；不得返回通用解包器、公开真实路径或可被 Agent 持久化的 blob handle。

物化顺序固定为：

1. 使用 sanitized Git environment 从 exact `baseCommit` 创建 detached、`--no-checkout` 的空闲 candidate worktree；不执行普通 checkout。
2. 在 claim lease 前重新验证 exact sealed lease、确认 digest、expiry、CAS、fencing、container、manifest 和 blob file identity，再进入 `materializing`。
3. 通过禁用 hooks、filters、external diff、textconv、fsmonitor、credential/helper 与 global/system config 的 Git plumbing 读取 exact base tree；P0 遇到 symlink、gitlink/submodule、LFS、sparse checkout 或任何 worktree conversion/filter 时 fail closed。
4. 以 candidate-root directory capability 为根，逐级 no-follow 创建目录；按 canonical path order 用同目录私有临时文件、fsync、fstat/digest、atomic rename 和 parent fsync 写入 base regular files及冻结 postimage，不能直接跟随或覆盖已有路径。
5. candidate index 按版本化的 `mirror_source_index_v1` policy 从 exact base tree 与 manifest postimage 构造；source index 永不修改。Promote 只应用到 target worktree，不隐式改写 target index。
6. 逐项复核 path、mode、size、file identity 和 content digest，再计算 candidate index/workspace digest，与 source snapshot 的预期投影比较。
7. 完全一致后依次 durable 提交 `consumed → destroying`、销毁 payload 并写入 `destroyed` tombstone；只有此后 Worktree Lease 才能进入 `bootstrapping`，若 frozen checks 不需要 bootstrap，可进入 `active`。

当前实现候选已完成第 1–7 步的 source materialization 部分，并在创建 worktree 前先持久化不可变 `SnapshotCandidateIntentV1`，成功复核后再写入 digest-chained `MaterializedSnapshotCandidateRecordV1`。intent 与 record 都绑定 exact Worktree Lease、内部 candidate branch、source/blob/manifest/policy；record 再绑定 candidate path identity、index digest、tracked delta 与 selected-untracked digest。两者仍不是 capability，不能单独授权 Agent 写入。

规则：

- snapshot blob sealed 后不再从 source workspace 动态补读文件。
- path case collision、rename/delete ambiguity、file type 改变或 source file digest 漂移都停止物化。
- materializer 不提供普通绝对路径写入；所有创建、验证与 rename 都相对于受信 candidate-root capability，并在每个边界拒绝 symlink、junction、hardlink、FIFO、device、目录交换与 file identity 漂移。
- 物化失败只清理本次仍为空闲且可证明归属的 worktree；有未知修改时保留并返回 blocker。
- candidate index 必须镜像 source index 的冻结 postimage；candidate worktree 必须镜像 source worktree 的冻结 postimage。该 policy 由版本化 materialization policy 固定，不能由模型选择。
- materialization policy/version/digest 必须进入 lease、candidate evidence 和 restart 校验。
- materialization 中途越过 `expiresAt` 不允许 sweeper 抢占 live owner；当前 owner 必须在 materialization deadline 内完成或明确中止。crash recovery 只有在证明旧 owner 已失效并提升 fencing token 后，才可将其标记 `expired`/`corrupt`，不能盲目重放。

- Preflight 必须根据 frozen checks、manifest、lockfile 和已知 runtime 先判断 candidate 是否具备可执行环境。

- executable 必须先解析为 exact absolute realpath，并冻结 file identity、regular-file mode、digest/version；拒绝 symlink/junction、candidate/source/Git common-dir/generated writable scope 内的 executable，以及 resolve 与 spawn 之间的 identity drift。启动只使用 exact executable + argv，不经过 login shell；sanitized PATH 只能包含已验证且位于受保护根之外的绝对目录。
- exact argv/env refs 只是 run/lease 内部恢复载体，使用当前用户私有权限并在 bootstrap settle/取消/过期后销毁；writer、reviewer、Skill 与用户 recipe 不可读取，不构成通用 private scratch/artifact。
- P0 内置 recipe 必须禁用 package lifecycle/install scripts、native build hooks 和任意 post-install command，并清除 ambient credential/provider/proxy 环境；确实需要这些行为的生态或 lockfile 返回 `candidate_bootstrap_unsupported`。
- Wukong 将 dependency、virtualenv、package cache 和 generated output 的配置目标限制在 candidate root 的声明 scopes，不能 copy、symlink 或主动读取 source workspace 的 ignored dependency directory。但这不是 OS sandbox；若受信 package manager 自身逃逸或绕过配置，只能由 permission/fingerprint 检测并阻断，不能宣传“任意依赖代码绝不会越界”。
- bootstrap 网络默认 deny；`explicit_once` 只允许用户确认的 registry endpoint digest 和 run-scoped credential names。没有 network sandbox 时 endpoint 配置是可审计约束而非强制网络隔离，无法接受该剩余风险时必须跳过隔离模式或 fail closed。
- 系统已安装的只读 runtime/compiler 可以使用，但其 identity/version 必须进入 bootstrap evidence。
- `.env`、credential 和 secret 文件仍不复制。check 必需的值只能通过逐项命名、run-scoped 的显式环境注入提供；值不写入 plan、日志或 evidence。没有合法输入时返回 blocker。
- generated bootstrap path 不进入 `CandidateDeltaV1`、Promote 或用户源码 diff；但 bootstrap plan、runtime、lockfile 和 generated-scope fingerprint 必须绑定 candidate Gate evidence。
- 每个 step 启动前通过 budget ledger CAS 预留 timeout、generated bytes 和 process output；未知/崩溃结果保留完整 reservation，只有可验证 actual usage 才 settle 未用额度。reservation 不足、超预算或 ledger/journal digest 不一致时停止。
- `prepared` 事件与 reservation 必须先 durable append/fsync，才允许 spawn；完成后记录 observed scope fingerprint 与 exit code。每个 event 校验当前 worktree fencing token。
- `createdByWorktreeFencingToken` 只是 immutable provenance；journal 当前可用 token 由最近一个有效 `ownership_adopted` event 决定，尚未 adoption 时才等于 created-by token。lease token 已提升后，除持有 registry lock 的 adoption append 外，旧 token 和新 token 都不能追加 step event。
- crash adoption 先在 lease registry 提升 token，再验证旧 journal head、generated scopes 和没有未知 in-flight step；成立时以新 token 追加 `ownership_adopted` event，显式链接旧 head、旧 token 与新 token，之后新 owner 才能从 next unapplied step 继续。若最后事件是未决 prepared/started、scope 漂移或旧 head 不完整，则 retain for attention，不能追加 adoption、重放该 step 或继续 bootstrap。
- bootstrap 失败、超预算、需要未批准网络/权限或没有受支持的确定方案时 fail closed，不得退回共享 source dependency。
- 目标 workspace final Gate 仍使用其真实环境重新执行；candidate bootstrap 成功不能替代 target final Gate。

### 5. Worktree isolation 不是完整 sandbox

0.0.21 只提供 Git/workspace 级碰撞隔离：

- 内置 Read/Write/Edit/Glob/Grep 使用 candidate-root capability。
- 普通 Agent/tool 对 workspace 外写、其他 lease 路径和 Git control directory 访问 fail closed。
- 只有内部 `GitWorktreeLifecycleCapability` 可以修改当前 lease 精确需要的 worktree inventory、candidate branch/ref 和 Git administrative metadata；它不能修改用户 source branch、source index 或远端。
- Bash、package script 和其子进程仍按用户当前 OS 权限运行。
- network、environment、credential inheritance 和任意子进程行为没有被完整隔离。
- 每次 Bash/check 前后、candidate Gate 前和 Promote 前都重算 source working tree、index、HEAD、受保护 refs 与已知 sibling lease fingerprint；Git common-dir 中由 exact lifecycle journal 解释的 candidate worktree/ref 变化属于预期变化，其他变化返回 `source_side_effect_detected` 并停止。
- fingerprint 只能发现已覆盖范围内已经发生的变化，不能证明任意系统路径没有副作用，也不能阻止逃逸进程稍后写入。
- “source unchanged” 只能表示最近一次受控 fingerprint 与冻结 snapshot 一致，不能作为 OS 级无副作用证明。
- UI 必须明确展示这条剩余风险，不能使用 “sandboxed” 或 “secure execution” 宣传。

完整 process-tree sandbox、Runtime Security 或 Prismor 集成不属于本版。

目标 lease 规则：

- `targetRegistryKey` 由 canonical target workspace + Git common-dir identities 计算，映射到所有 Wukong session 共用的当前用户私有 registry/lock 路径；不能放在 per-session store。
- acquire/adopt/release 必须持有该 registry key 的 cross-process file lock，并以 atomic CAS 更新 registry revision、owner identity 和单调递增 fencing token；同一目标任一时刻只能有一个 Wukong promotion owner。
- 所有 Apply journal append、change write、final Gate attempt 和 terminal join 都携带并重新校验 exact fencing token；旧 owner 即使进程恢复也不能在新 token 后继续写。
- 用户必须先在无锁状态审查 candidate diff/Gate，并确认 exact promotion challenge；等待人类输入期间不得持有 target lock。
- 取得锁后必须在锁内重建完整 `TargetStateFingerprintV1` 并重新执行全部 Apply eligibility；锁前的 freshness 结果不能直接复用。
- 若锁内 candidate、challenge、source 或 permission digest 与用户确认时不同，必须在任何 Apply 前释放锁并请求重新确认。
- 从第一项 Apply 之前一直持有到 Apply journal reconciliation、目标 final Gate 和 terminal join 完成；其他 candidate 只能保持 `awaiting_promotion` 并显示 target busy。
- 进程崩溃会释放 OS lock，但 durable lease 不自动视为完成；新 owner 必须在 target-global registry 中 CAS 提升 fencing token，并根据真实 target fingerprint 与 Apply journal reconcile 后才能继续。
- 外部编辑器、脚本或其他非 Wukong 进程不会遵守该锁；每项 change 仍需在写入前核对 expected preimage，final Gate 前仍需重验 target fingerprint。检测到漂移时进入 reconciliation，不宣传为通用 workspace write lock。

Promote 包含三个阶段：

1. **Review + exact consent（不持锁）**
   - 用户在 TUI 审查并确认 exact candidate/promotion challenge；Headless 也必须先提交 exact challenge；
   - consent 只绑定 candidate、source expectation、permission 和 target identity，不代表锁内 freshness 已成立。
2. **Target lock + Apply eligibility**
   - 已取得 exact target promotion lease，且 workspace identity、HEAD、branch、index 和 source snapshot 在锁内与冻结值一致；
   - candidate digest、lease 和 candidate Gate 必须 fresh；
   - challenge 必须与锁前确认的 digest 完全一致；
   - 任一漂移、冲突或权限变化都在修改目标 workspace 前停止。
3. **Apply + final Gate**
   - 只把 `materializedSourceDigest → candidateWorkspaceDigest` 的 Agent delta 应用到已经包含原始 dirty snapshot 的目标 workspace，禁止把 snapshot delta 重放第二次；
   - 使用确定、可审计的应用顺序和 `PromotionApplyJournalV1`，逐项记录 preimage/postimage digest；
   - 不执行隐式 stash、reset、force checkout、push 或 branch rewrite；
   - Apply 后对真实目标 workspace 重跑全部 frozen checks、risk scan、selected criteria 和唯一 fresh reviewer；
   - 只有 final Gate PASS 才能生成 terminal PASS。

```ts
  readonly candidateDeltaDigest: string;
  readonly promotionJournalId: string;
  readonly promotionJournalHeadDigest: string;
  readonly targetPromotionLeaseId: string;
  readonly targetFencingTokenDigest: string;
  readonly targetAfterFingerprintDigest: string;
  readonly finalGateAttemptId: string;
  readonly finalGateEvidenceSnapshotId: string;
  readonly finalGateEvidenceDigest: string;
  readonly requiredGateCoverageDigest: string;
  readonly finalGateAttemptResultDigest: string;
  readonly finalGateOutcome: 'PASS' | 'NEEDS_WORK' | 'ERROR';
  readonly orderedArtifacts: readonly CompletionArtifactRefV1[];
  readonly redactionPolicyVersion: string;
  readonly finalGateCompletedAt: string;
  readonly sealedAt: string;
  readonly completionSealDigest: string;
}
```

规则：

- `privateRef` 是 Wukong private store 分配的 opaque ref，不接受模型或用户提供的路径；三类 artifact 必须各恰好一个，不能缺失、重复或插入未知类型。
- artifact 必须是 private root 内的 bounded regular file；父级逐层 no-follow，拒绝 symlink/junction/hardlink、identity drift、root replacement、绝对路径和 `..`。
- raw path、raw fencing token、raw stdout/stderr、raw exception 和环境值不进入 seal；所有持久化 diagnostic 必须先经同一 redactor，再写 record/artifact 和计算 digest。
- `acceptanceContractDigest`、`gatePlanDigest`、`criteriaSelectionDigest` 与 `requiredGateCoverageDigest` 必须证明 frozen required checks、risk scan、selected criteria 和唯一 fresh reviewer 都已进入同一 final attempt；缺项、重复或 advisory-only 结果不能 seal PASS。
- `completionSealDigest` 使用独立 domain separator。完整 `NEEDS_WORK/ERROR` attempt 可以 seal 供恢复与解释，但只有重读验证通过的 `PASS` seal 才能加入 root PASS terminal。
- cancel、preflight 或 infrastructure error 没有完整 final Gate attempt 时沿用 0.0.19 的 non-PASS terminal，不能伪造 completion seal。

完成事务的固定顺序是：

```text
Apply journal = applied
  → write complete final Gate evidence
  → validate lineage + required coverage + artifact identity/hash
  → append GateAttemptCompleted
  → append TargetGateCompletionSealV1 and fsync
  → reopen and validate seal + every artifact
  → append LoopRunTerminal (the commit point)
```

crash 留下 evidence、completed attempt 或 seal 但没有 terminal 时都不算成功。resume 必须完整重读 schema、长度、digest、artifact、journal head、target fingerprint 和 fencing token，不能以“文件存在”或 `status=completed` 跳过。token/head/fingerprint 漂移时旧 seal 不可直接提交 terminal，必须重新 final Gate 或进入 reconciliation；幂等 terminal join 最多产生一个终态。

如果 Apply 后 final Gate 失败：

- run 返回 `NEEDS_WORK` 或 `ERROR`；
- 不自动 reset 或回滚用户 workspace；
- 记录已应用 candidate identity 和当前 workspace fingerprint；
- Continue 必须从当前真实 workspace 创建新 snapshot，不能复用旧 candidate PASS。

### 8. 清理必须可证明归属

- 只有 `createdByRunId`、lease marker、Git worktree inventory 和 canonical path 全部匹配时才允许释放。
- active、awaiting promotion、conflicted、lost 或含未集成修改的 worktree 默认保留。
- 不使用 broad glob、未解析环境变量或递归目录删除。
- 正常 released 只通过受控 Git worktree lifecycle 清理；失败时返回可操作路径，不偷偷强制删除。
- 用户显式 Retain 后，Wukong 不再自动清理；重新采用必须创建新的 lease assignment。

## 状态机

```text
preflight
  → snapshot_staging
  → snapshot_sealed
  → snapshot_confirmed
  → worktree_creating
  → materializing
  → snapshot_blob_consumed
  → bootstrap_preflight
  → bootstrapping | bootstrap_not_required
  → active
  → candidate_verifying
  → awaiting_promotion
  → promoting
  → final_verifying
  → completion_sealing
  → terminal_committing
  → PASS | NEEDS_WORK | ERROR
```

附加恢复状态：

```text
active/verifying + process lost
  → lost_recoverable
  → explicit resume | retain | release

snapshot_staging + process lost
  → destroy partial blob
  → re-scan and re-confirm

snapshot_sealed/materializing + process lost
  → validate blob lease + worktree journal
  → explicit resume | discard and re-confirm

bootstrapping + process lost
  → validate bootstrap plan + generated scopes
  → explicit resume from next unapplied step | retain for attention
```

任何状态都不能通过覆盖旧 record 回退；修复只追加新 record 和稳定 lineage。

## 稳定 reason codes

reason code 描述 phase、preflight 或 Gate 事件，本身不创建 Loop terminal，也不推导 continuation。`awaiting_promotion` 是 active run 的非终态 phase；只有用户拒绝、取消、超时策略触发或 0.0.19 terminal policy 明确收口时，才追加对应 terminal record。

| Reason code | 默认处理 | 含义 |
|---|---|---|
| `isolated_loop_not_git` | block isolated preflight | experimental isolation 已启用，但当前 workspace 不是受支持的 Git worktree；experiment 关闭时仍保持原 serial Loop |
| `source_snapshot_untrusted` | block preflight | source identity 或 trust 不成立 |
| `snapshot_dependency_excluded` | block preflight | 必要输入被 snapshot policy 排除 |
| `snapshot_selection_excluded` | block preflight | 用户显式选择的 untracked 文件被 snapshot policy 排除 |
| `snapshot_blob_missing_or_corrupt` | re-confirm snapshot | 私有 snapshot blob 无法恢复 |
| `snapshot_materialization_failed` | fail closed / retry proposal | candidate 内容无法精确复现已确认 snapshot |
| `candidate_bootstrap_unsupported` | block preflight | frozen checks 所需依赖无法用受支持的确定方案准备 |
| `candidate_environment_input_required` | attention / explicit input | check 需要未提供的 run-scoped 环境变量或 secret |
| `candidate_bootstrap_failed` | fail closed / retry proposal | 已确认 bootstrap 失败、超预算或违反权限/网络合同 |
| `candidate_bootstrap_reconciliation_required` | retain + attention | bootstrap journal、reservation、owner 或 generated scope 无法证明 |
| `worktree_create_failed` | fail closed / retry proposal | 创建候选 worktree 失败 |
| `worktree_identity_changed` | fail closed | lease 与真实 worktree identity 不一致 |
| `source_side_effect_detected` | pause + attention | shell/check 期间检测到 source 或 sibling lease 漂移 |
| `candidate_gate_failed` | continue current run | 候选未通过 Gate |
| `promotion_consent_required` | `awaiting_promotion` | 等待用户确认 exact candidate，非终态 |
| `promotion_target_busy` | `awaiting_promotion` + attention | 另一个 Wukong promotion owner 正在处理同一目标 workspace |
| `promotion_fencing_lost` | fail closed / attention | target-global registry 已产生更新 fencing token，旧 owner 失效 |
| `promotion_source_changed` | attention / revised source | 目标 workspace 已漂移 |
| `promotion_conflict` | attention | candidate 无法无冲突应用 |
| `promotion_reconciliation_required` | attention / fail closed | owner 丢失或外部写入后无法证明 Apply 状态 |
| `final_gate_failed` | continue or terminal by 0.0.19 policy | 应用后真实 workspace 未通过 Gate |
| `target_completion_seal_invalid` | attention / fail closed | completion seal 缺失、损坏、artifact 不完整或 lineage 不一致 |
| `worktree_lost_recoverable` | paused / explicit resume | 进程丢失但 lease/worktree 可恢复 |
| `worktree_cleanup_blocked` | retain + attention | 无法证明安全清理条件 |

### Integration

- clean、dirty、tracked diff、untracked file 的真实仓库流程。
- Node、Python、Rust、Go fixture 在空 candidate dependency 环境中完成显式 bootstrap；无受支持 lockfile、拒绝网络和缺少 secret/env 时均 fail closed。
- package lifecycle/native build hook fixture 在 P0 bootstrap 被拒绝；ambient provider/credential/proxy env 不进入 child process，registry consent 与 endpoint digest 固定。
- staged/unstaged/untracked snapshot 在 Promote 时不重复应用、不丢失，index 语义符合固定 materialization policy。
- 内置写工具路径中，Promote 前 source workspace、branch、HEAD 和 index 保持不变。
- Git common-dir 只出现 lifecycle journal 允许的 candidate worktree/ref 变化，source branch/ref 和 sibling lease 不变。
- adversarial Bash 写 source/sibling worktree 时被 fingerprint revalidation 阻断；文档不据此宣称任意外部路径零副作用。
- source drift、重叠 patch、rename/delete、mode change 和 path traversal 停止在 Apply 前。
- candidate Gate PASS → Promote → target final Gate PASS。
- 合法 PASS seal 可幂等 join；损坏 seal、fencing token 提升或 target fingerprint 漂移必须重新 final Gate 或进入 attention。
- 两个独立 Wukong 进程对同一 target 并发 Promote 时只有一个获得 lease；第二个保持 awaiting/attention，不能交错 Apply。
- 持锁期间外部编辑器修改目标文件时，下一项 preimage recheck 或 final fingerprint 必须阻断并进入 reconciliation。
- candidate PASS 但 target seeded blocker 存在时 false PASS 为 0。
- kill/restart 不重复创建 worktree、不重复 Apply。
- 失败/取消 worktree保留，安全释放不删除用户目录。

### Cross-platform

- macOS、Linux、Windows 的 Git worktree、Unicode、长路径、文件模式和进程终止。
- Windows drive-relative/UNC/device/ADS/尾随点空格、atomic replace、fresh/reused artifact root 与 manifest/seal retry。
- 支持的最低 Git 版本有明确检查和错误。

### Privacy / adversarial

- 日志、records、feedback 和 provider broker manifest 不包含 raw patch、secret、home path 或 session transcript。
- synthetic secret 覆盖 stdout/stderr、exception、URL userinfo/query、Authorization 和 env assignment；record、seal、stream-json、日志、feedback、crash payload 与 tombstone 均在持久化前去密。
- 恶意 symlink、`.git` indirection、worktree marker spoof、path case collision 和 repository identity drift。
- completion artifact 覆盖 absolute/`..`/反斜杠/NUL/case-NFC collision、symlink/junction/hardlink、parent swap 与 artifact-root replacement。
- Cancel、permission denial、consent refusal 时零 Apply；内置写工具不会修改目标 workspace，任意 shell 的 OS 级副作用不在 worktree 保证内。
- SIGINT/SIGTERM 注入 sealer、materializer、bootstrap、writer、Apply、final Gate、completion seal 和 terminal 前；late callback 不能补写 PASS，无 owner 的 active state 不能按 completed 恢复。

## 完成定义

0.0.21 只有在以下条件全部成立时才算实现：

1. 一个写入型 Loop 能在独占 candidate worktree 中完成。
2. source snapshot 和所有 Gate evidence 可追溯且 fresh。
3. Candidate 依赖只能经确认的 bootstrap plan/budget/journal 准备；缺环境或无法禁用安装脚本时 fail closed，不复用 source ignored dependency。
4. Promote 前内置写工具不修改用户 workspace；每次 shell/check 后重验 source fingerprint，检测到漂移即阻断，但不宣称完整 OS containment。
5. candidate PASS 永远不能直接成为 root PASS。
6. target-global fencing lease、完整 fingerprint 和逐 change journal 能阻止双进程交错 Apply；source drift 或冲突在 eligibility/change boundary 阻断。
7. Apply journal 不会重复用户原有 dirty snapshot；只有目标 workspace final Gate 能产生 terminal PASS。
8. PASS 只在 completion seal 与所有 canonical artifact 被重读验证后提交；corrupt resume、取消、late write 和 Windows path 不能产生 false PASS。
9. durable error 在持久化前去密，private artifact 不可经 symlink/path escape 落入 source、candidate 或 Git common-dir。
10. crash/restart 不重复未知 bootstrap step 或盲目重放 Apply，无法 reconcile 时进入 attention。
11. worktree/bootstrap isolation 没有被描述成完整 sandbox。
12. 没有新增 Wukong 云端依赖、telemetry、支付或默认命令。
13. 四类发布门槛都有真实 evidence。
