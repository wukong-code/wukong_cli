## 目标与客户假设

用一个真实团队的重复验收任务，验证 Wukong 是否能减少需求遗漏、人工验收和返工，
以及客户是否愿意为明确交付的接入、配置和工作流支持付款。

首批客户假设是小型开发团队或软件外包公司中的技术/交付负责人。先聚焦一个技术栈
和场景，例如网站项目的发布前验收；访谈后选定，不能预先宣称此客户群有付费需求。
个人开发者 Pro、完整团队平台和 Enterprise 不是首轮试点范围。

用户路径：

```text
已有需求 / GitHub Issue
  → 验收草案与检查映射
  → 用户确认并冻结
  → 在本地或客户控制的 CI 执行
  → 检查 / 独立 review / 必要修复与重跑
  → 当前 commit 的 Gate 与未覆盖项
  → 预览、授权发布交付摘要
  → 下一次真实交付再次使用
```

## 候选范围与现有能力复用

| 候选项 | 最小形态 | 复用 | 验收意图 |
|---|---|---|---|
| 需求到验收映射 | 从用户提供的需求或一个 Issue 生成草案，用户确认条件、检查、约束与未覆盖项 | Goal、Done when、Preflight、冻结合同 | 原需求可追溯；模型生成的 Spec 不自动批准；验收条件变更重新确认 |
| 最小 GitHub PR Gate | 把真实 attempt 的结论与脱敏摘要写到用户授权的一个 PR/commit | 检查引擎、独立 reviewer、Gate completeness/freshness | 只绑定当前 exact commit；失败、缺失、过期、部分执行和纯确定性检查不冒充完整 Gate PASS |
| 交付摘要 | 展示需求覆盖、运行过的检查、review 结论、未覆盖项和下一步 | 本地 durable state 与 evidence identity | 本地可预览；发布字段经去密；接收者能判断验收范围，不能宣传无 bug 保证 |
| 实际仓库接入 | 人工整理可执行检查、确认模型配置、陪跑一次交付 | 现有 CLI、BYOK、Loop、恢复与上限 | 约定服务范围可完成；后续真实任务可以重复使用 |
| 真实演示与案例 | 演示失败、修复、重跑和至少一个非 PASS 结果 | 0.1.2 上手路径与真实任务输出 | 获得展示授权、脱敏；耗时和收益来自记录，不由动画或预测生成 |

默认复用 GitHub Issue/PR 的任务管理和原项目检查，不另建通用 Spec/Plan/Kanban 平台。
新生成的测试必须可审查；writer 不得自行降低用户确认的验收条件来取得 PASS。

## 执行与发布边界

- 首版优先显式本地启动或客户控制的 CI；不建设 Wukong 托管执行集群。
- GitHub 发布是新的网络写入能力，与本地 Loop 分离。发布目标、字段、权限与授权
  方式必须在技术设计中确定；已发布的本地 CLI 不默认获得发布权限。
- 外部 Issue、PR、评论和代码是不可信输入，不继承外部 transcript 的权限或完成声明。
- PR 新提交后旧结果必须标为过期。结果只能描述已验证的 exact commit；状态写入与
  摘要写入部分失败必须可见、可幂等恢复，不能留下误导的成功结论。
- 不在带有生产密钥的环境中默认执行不可信 PR。fork PR、执行隔离、凭据注入与
  人工审批策略是开工前技术设计的必答项，不能凭 BYOK 或 local-first 宣称已有 sandbox。
- 默认不上传源码、prompt、transcript、raw evidence、绝对路径或 provider 凭据。
  允许发布的摘要必须在本地去密、预览，并绑定用户授权的 exact target。
- 不恢复 `/report`、Hosted Report、历史报告上传、旧 SaaS quota 或失效 Promote 设计。
- Free 本地 Loop、Resume、Gate、BYOK reviewer 与基础验证持续完整可用，账号、
  GitHub、收款或 entitlement 服务故障均不能阻断它们。

## Founding Team 收费实验

先出售**按次接入与验收陪跑服务**：一个仓库、一个技术栈、一次真实交付任务，
约定支持工时与交付物后单独报价。使用现有 CLI，人工整理用户确认的完成条件、
接通原项目检查、陪跑有界修复与复验、交付人工摘要及未覆盖项。首单不承诺新 PR
Gate、自动摘要发布、必定 PASS 或没有缺陷；自动化技术候选从反复出现的卡点中选择。

同一团队在下一次真实交付主动复购后，再测试 **$199/团队/月、最多 5 人** 的固定
范围月度验收支持。该价格未验证，不是当前公开套餐或软件订阅；接入次数与支持
工时须约定。首单和月度服务的合同、报价、收款方式、取消/退款条款均需先确认。

模型 API 费用由客户 BYOK 承担。记录接入、支持、基础设施和支付处理成本；大量
定制交付单独报价，不能靠无限人工支持维持低价月订阅。

Pro $12/月、Team $29/人/月与 Enterprise 仅为后续待验证假设；不同时建设四个套餐。
服务付款说明有人买服务，只有标准工作流被反复购买、独立使用和续费，才能支持
软件订阅方向。账本区分一次性接入费、月度服务费和未来软件订阅收入。

## 首轮 30 天实验顺序

时间窗口从实际实验启动算起，不是已安排的日历任务或收入预测。

| 阶段 | 工作 | 可核对输出 |
|---|---|---|
| 第 1 周 | 面向一个客户群访谈、拿真实任务、了解当前替代流程并提出按次报价 | 目标买方、仓库/任务授权、具体卡点、一次服务范围/工时与报价反馈；访谈目标 10 个团队，不计收入 |
| 第 2 周 | 服务条件确认后，用当前能力交付首单；新增功能未完成时诚实说明 | 用户确认的验收条件、执行证据、人工摘要与未覆盖项、实际付款/退款、人工工时及客户反馈 |
| 第 3 周 | 把多次出现的卡点整理成候选技术设计，再确认实施范围 | 最小 PR 接入、检查映射或交付摘要设计；只补能解释购买理由的缺口 |
| 第 4 周 | 验证第二次主动购买，复盘交付成本；有复购再提出固定范围月度服务报价 | 区分按次复购、月度服务与退款记录，核对重复交付、支持工时和收益；未收款不写成收入 |

演示和官网表达可以同步准备，不能先用等待名单、页面完成或 Star 替代客户验证。
30 天内可观察付款和重复使用；续费必须跨实际账期继续观察。

## 分开的验收与决策门槛

**技术版本验收**：先批准具体设计，再按 minor 矩阵验证代码。范围至少覆盖需求变更
确认、exact-commit/stale/partial/failed/未执行检查、GitHub 权限与部分写入失败、
去密与取消、CI 不可信输入/凭据边界、恢复兼容以及六平台发布。代码验收通过不等同
商业试点成功；没有付款也不能放宽 Gate 或隐私底线。

**服务试点验证目标**：3 个非关联团队实际付款，每队至少完成 2 次真实交付。仅支持
项目、朋友付款、免费试用或口头意向不算工作流需求证据；记录每个买方购买的具体
价值以及退款原因。未达目标时调整客户/场景/报价，不自动扩功能。

**0.3.0 产品化评审门槛**：至少 2 个试点团队进入月度服务后的下一实际账期并续费，
同一工作流反复被使用，扣除接入、支持与基础设施等成本后的交付毛利为正。
第二笔按次订单只计复购，不计月度续费。继续核对客户是否
能独立使用；服务续费本身不证明标准软件订阅成立。具体自助订阅阈值、权益和完整
Billing/entitlement 设计在 0.3.0 另行批准。

收入和使用证据来自经同意的客户记录与收款账本，不新增匿名行为采集；商业记录
不放入公开仓库。可公开案例与完整运营证据分开留存。

策略、适用回归与发布矩阵。该清单是候选规格的未决项，不是 TODO 自动执行任务。
