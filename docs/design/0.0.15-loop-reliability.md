## 实现状态（2026-07-20）

核心实现已落地：CLI 使用 `0600` 原子 JSON 记录持久化 `requestId → goalId/sessionId/workspace`，completion 网络失败进入带退避的本地 outbox，CLI/TUI 启动、session resume、today/doctor 和下一次 Loop 前会 fail-open 重试；headless/TUI 的完成、用户取消和 Goal 创建失败都能生成独立 lifecycle。重启后可以 Resume、End as cancelled 或 View details，Resume 会重新读取 workspace、Git、checks 和 policy。preflight 已前置到 quota start 之前，首次 TUI 与终态卡片已经收敛。

Web `/complete` 已兼容旧 payload，并支持 cancelled、幂等重试、冲突 409、跨用户隔离；历史 lifecycle 区分 active、stale、completed、cancelled 和 abandoned。真实 Node/Python/Rust/Go、无 checks、缺失工具和 Cross-Agent Resume → editable Loop fixture E2E 已覆盖。

完整 test/typecheck/lint/bundle 与本机 darwin-arm64 native smoke 已通过；全量并发测试中的 10 个资源竞争超时，已按失败文件单 worker 重跑并 80/80 通过。0.0.14 → 0.0.15 的 upgrade pinning contract 和显式版本 fresh installer 已通过。

真实六平台 release assets 与 checksum 已发布；隔离环境中的 0.0.14 → 0.0.15 自动升级和 0.0.15 fresh installer 均完成 SHA-256 校验并运行为 0.0.15。正式 manifest、公告、官网、下载页、D1 migration 与 live health 已同步验证。

## 1. 版本结论

0.0.14 已经完成 `Resume → Loop → Gate` 的主要入口，但“可以开始”不等于“可以可靠结束”。0.0.15 不继续扩张命令面，而是把一次 Loop 从启动、执行、终止、重启恢复到服务端记账做成可靠闭环。

本版本只回答三个问题：

1. 用户启动的 Loop 是否一定会进入明确终态。
2. CLI 崩溃、断网、重启或用户取消后，是否可以恢复或正确结束记账。
3. 新用户是否能在不理解 verify/scan/proof 内部结构的情况下完成第一次 Loop。

主路径保持不变：

```text
Install / Upgrade
        ↓
Provider + workspace preflight
        ↓
Resume a task / Start a Loop
        ↓
Write → Check → Review → Fix
        ↓
PASS / NEEDS_WORK / ERROR
        ↓
Durable completion + optional repeat
```

## 2. 可靠性问题

TUI completion tracking 若只依赖进程内状态，CLI 重启或 session 恢复可能丢失
`requestId → goalId` 映射。应通过 durable tracking 与幂等 outbox 恢复明确终态；
启动记录本身不能证明任务完成，也不能替代 Gate evidence。

## 3. 版本目标

### 3.1 P0：每个已计费 Loop 都有终态

- 已登录用户的 Loop run 在本地持久化，不依赖 TUI 内存 `Map`。
- 正常完成、达到最大轮次、runtime error、用户取消和长期失联都能被区分。
- completion 上报失败不会改变本地 Gate 结论，但会进入可重试 outbox。
- 同一个 `requestId` 的 start/complete 可以安全重试，不重复计数。
- preflight 没有通过时不创建服务端 run，也不消耗额度。

### 3.2 P0：第一次 Loop 有可执行的下一步

- 初次进入 TUI 只突出 `Continue a task`、`Start a Loop`、`Configure model`。
- 启动 Loop 前检查 provider、model、workspace、objective 和项目 checks。
- 没有 checks、工具缺失、检查失败和模型不可用使用不同原因，不再统一显示为验证失败。
- 默认结果只显示 Gate、主要原因和下一步；高级诊断折叠展示。

### 3.3 P0：重启后可恢复

- 活跃 Loop 与 Goal/session 一起恢复。
- 恢复后重新读取 workspace、Git、checks 和 review policy，旧结论不能直接复用。
- Cross-Agent Resume 创建的 Loop 使用同一恢复机制。
- 如果用户选择不恢复，旧 run 结束为 `cancelled` 或 `abandoned`，不能永久停在 `started`。

### 3.4 P1：建立可信激活指标

- 区分安装、首次启动、Loop 启动、第一轮执行、终态和重复使用。
- 不上传源码、diff、prompt、transcript、API key 或机器指纹。
- 安装/匿名使用指标提供明确 disclosure 和 opt-out。
- 登录后的 quota/accounting 事件与匿名产品指标分开定义。

## 4. 非目标

0.0.15 明确不做：

- Stripe Checkout、customer portal 或正式 Pro 收费。
- GitHub PR comment、status check 或 merge gate。
- Team rules、audit log、retention 或 private runner。
- Hosted Report、报告上传、公共分享或报告列表。
- `/schedule` 云端例程。
- 新增更多外部 Agent 来源。
- 扩张 Role Profiles / 变身系统。
- 把 verify、scan、proof 重新升级为三个普通用户产品。
- Managed model、credits 或第三方模型 API 转售。

## 5. Loop 生命周期 Contract

### 5.1 生命周期与结果分离

服务端 run lifecycle 与用户可见 outcome 必须分开，避免把取消误写成代码失败：

```ts
type LoopRunStatus = 'started' | 'completed' | 'cancelled' | 'abandoned';
type LoopOutcome = 'PASS' | 'NEEDS_WORK' | 'ERROR';
```

约束：

| status | outcome | 含义 |
|---|---|---|
| `started` | `null` | 已通过 preflight 并开始真实执行 |
| `completed` | `PASS` | Gate 通过 |
| `completed` | `NEEDS_WORK` | 有可修复 blocker、达到轮次上限或证据不足 |
| `completed` | `ERROR` | runtime/provider/check infrastructure 无法完成判定 |
| `cancelled` | `null` | 用户明确取消 |
| `abandoned` | `null` | 客户端长期未回报，不能证明任何代码结论 |

`cancelled` 和 `abandoned` 不得计入 PASS/NEEDS_WORK/ERROR 比例。

### 5.2 允许的状态迁移

```text
started ──→ completed(PASS)
        ├─→ completed(NEEDS_WORK)
        ├─→ completed(ERROR)
        ├─→ cancelled
        └─→ abandoned
```

终态不可被另一个终态覆盖。相同 payload 的幂等重试返回成功；冲突 payload 返回稳定错误并保留第一个终态。

### 5.3 什么时间创建 run

顺序固定为：

1. 校验 objective 和参数。
2. 确认 provider/model 可解析。
3. 确认 workspace 可读，且没有冲突的 active Goal。
4. 完成 checks discovery，并生成 preflight summary。
5. 调用 `/api/v1/loops/start`。
6. 持久化本地 tracking record。
7. 创建 Goal 并发送第一轮输入。

第 1–4 步失败不占额度。第 5 步成功但第 6–7 步失败时，客户端必须把 run 标记为 `cancelled` 或写入 outbox，不能静默遗留。

## 6. 本地持久化与 Completion Outbox

### 6.1 本地记录

建议目录：

```text
~/.wukong/usage/loop-runs/<request-id>.json
```

最小结构：

```ts
interface LocalLoopRunRecord {
  version: 1;
  requestId: string;
  goalId?: string;
  sessionId?: string;
  workspace: string;
  startedAt: string;
  state: 'active' | 'pending_terminal' | 'synced';
  terminal?: {
    status: 'completed' | 'cancelled';
    outcome?: 'PASS' | 'NEEDS_WORK' | 'ERROR';
    iterations?: number;
    finishedAt: string;
  };
  retry: {
    attempts: number;
    nextAttemptAt?: string;
    lastErrorCode?: string;
  };
}
```

安全边界：

- 文件权限 `0600`，目录权限遵循现有 Wukong home。
- 不保存 objective、prompt、transcript、diff、finding 内容或 token。
- workspace 只用于本机恢复，不上传到 metrics。
- 使用临时文件 + atomic rename，避免崩溃留下半个 JSON。

### 6.2 Outbox flush

以下时机尝试 flush：

- CLI/TUI 启动后，不阻塞首屏。
- 用户执行 `wukong today`、`wukong doctor` 或开始新 Loop 前。
- Goal 到达终态后立即尝试。
- session resume 后发现 pending terminal record 时。

重试使用有上限的指数退避。HTTP 401 停止自动重试并提示重新登录；409 冲突记录为诊断事件；网络失败保持 pending。outbox 永远不能把本地 PASS 改成失败。

### 6.3 活跃 Loop 恢复

启动时发现 active record：

```text
Active Loop found
  Resume Loop
  End as cancelled
  View details
```

恢复前必须重新读取当前 workspace。若 Goal record 不存在、workspace 不可达或 session 已删除，则提示原因并允许结束为 cancelled；不能伪造一次完成结果。

## 7. Server API 与数据模型

### 7.1 `/api/v1/loops/start`

保持现有接口并强化：

- `requestId` 对同一 user 幂等。
- 重试返回原 run 和当前 quota，不重复创建记录。
- 新 run 开始时，可将该用户超过阈值的旧 `started` run 视为 stale，用于 metrics 排除；是否写回 `abandoned` 由明确 reconciliation 逻辑完成。
- 返回 server run id、quota、最大迭代和 start timestamp。

### 7.2 `/api/v1/loops/complete`

兼容旧客户端的 `{ requestId, outcome, iterations }`，0.0.15 扩展为：

```ts
interface CompleteLoopRequest {
  requestId: string;
  status?: 'completed' | 'cancelled';
  outcome?: 'PASS' | 'NEEDS_WORK' | 'ERROR';
  iterations?: number;
}
```

- 旧 payload 默认 `status = completed`。
- completed 必须带合法 outcome 和 iterations。
- cancelled 不带 outcome。
- 只能结束当前用户自己的 run。
- 同 payload 重试返回 200；冲突终态返回 409。

### 7.3 Stale run

- `started` 超过 24 小时不再计入 active/completion funnel 分母。
- metrics 单独返回 `staleStarted`，不能把它伪装成 ERROR。
- 通过 migration/backfill 将发布前明显陈旧的 started rows 标记或统计为 abandoned。
- 不为这一项单独引入 Hosted Report 或新的通用 job 系统。

## 8. Preflight 与首次成功 UX

### 8.1 Preflight 输出

默认保持短：

```text
Ready to start Loop
Model    GLM-5.2
Checks   pnpm test, pnpm typecheck
Limit    up to 5 iterations
```

只在阻塞时解释：

```text
Loop not started
Reason   No model is configured
Next     Run wukong provider
```

### 8.2 没有项目检查

没有 checks 不是“测试失败”。默认结果为：

```text
Gate: NEEDS_WORK
Reason: No project checks configured
Next: Add checks with .wukong/checks.json
```

0.0.15 不默认允许 reviewer-only 结果变成 PASS。高级 review-only mode 可以后续单独设计，避免把低证据结论包装成已验证。

### 8.3 最终结果卡

默认只显示：

```text
Gate        NEEDS_WORK
Iterations  3
Blocker     Tests still fail in auth/session.test.ts
Next        Continue Loop after fixing the failing fixture
```

详细 check、scan、review findings 保留在 transcript 展开区和显式诊断命令中。

## 9. 指标与隐私

### 9.1 历史事件兼容记录

以下记录 0.0.15 当时的事件，不代表当前允许发送的字段或新增采集授权。
当前最小传输契约以 [CLI telemetry](../operations/cli-telemetry.md) 为准。

历史事件：

```text
install_success
first_run
device_login_started
device_login_terminal
resume_selected
loop_started
loop_first_iteration
loop_terminal
loop_repeat_started_7d
loop_repeat_completed_7d
```

`loop_repeat_started_7d` 只表示 7 天内再次开始；`loop_repeat_completed_7d` 仅在用户于后续 UTC 日期完成另一次 `PASS` 或 `NEEDS_WORK` Loop 时发送。两者不得混为留存。

服务端运营指标与研究计划在私有仓库维护；下节保留历史数据边界，
不得据此扩大当前 telemetry 的出站字段。当前契约见
[CLI telemetry](../operations/cli-telemetry.md)。

### 9.2 数据边界

允许：

- CLI version。
- OS family 和 CPU architecture。
- event name、timestamp、匿名 install id 或登录 user id 二选一。
- Loop outcome、iterations、failure category。

禁止：

- 文件路径、仓库名、Git remote。
- prompt、objective、transcript、diff、源码。
- API key、provider endpoint、session content。
- 可组合成机器指纹的硬件/网络细节。

匿名 install telemetry 必须在 installer/docs 明示，并支持 `WUKONG_TELEMETRY=0`。关闭匿名 telemetry 不影响本地 Loop；登录用户的 quota/accounting 仍按服务契约执行。

CLI 同时兼容旧的 `WUKONG_DISABLE_TELEMETRY=1`；新文档统一推荐更直接的 `WUKONG_TELEMETRY=0`。

## 10. 兼容策略

- 0.0.14 Goal/session records 继续可读。
- 找不到 0.0.15 tracking record 时不猜测旧 Loop outcome。
- 旧客户端 completion payload 继续有效。
- Guest trial 文件格式继续兼容；Guest 不创建服务端 run。
- `verify-pass`、`scan-clean`、`judge-pass` 继续映射到 `proof-pass`，本版本不删除。

## 11. 实施顺序

### Phase A：冻结 Contract

1. 冻结 lifecycle/outcome、API 兼容和本地 record schema。
2. 写 restart、offline、cancel、duplicate-complete 的 contract tests。

1. 把进程内 tracking 改为 durable store。
2. 接入 headless 和 TUI Goal 的所有终态。
3. 实现 outbox flush 与 retry 分类。

### Phase C：Preflight 与结果 UX

1. preflight 前置到 quota start 之前。
2. 简化首次入口与最终结果卡。
3. 无 checks、工具缺失、provider failure 文案分层。

1. 扩展 D1 lifecycle schema 和 API。
2. Dashboard 只展示真实终态和 stale 提示，不恢复 Reports。

## 12. 测试矩阵

### 12.1 CLI 单元与集成

- start 成功后本地 record 原子写入。
- Goal 创建失败会产生 cancelled outbox。
- PASS/NEEDS_WORK/ERROR 映射正确。
- Ctrl+C 和 `/loop stop` 映射为 cancelled。
- completion 超时后 pending，后续启动重试成功。
- 401、409、5xx 和网络失败行为稳定。
- 重启后 active Goal 可以恢复；丢失 Goal 不伪造 outcome。
- 旧 Goal、Guest trial 和旧 completion payload 兼容。

### 12.2 真实项目 E2E

- Node monorepo。
- Python 项目。
- Rust workspace。
- Go module。
- 无 tests/checks 的空项目。
- 缺失本地工具。
- 从 Codex、Claude Code、Cursor resume 后启动 Loop。

每类至少覆盖 PASS、NEEDS_WORK 和 infrastructure ERROR 中适用的路径。

### 12.3 Web/API

- start/complete 幂等。
- 跨用户 requestId 不可访问。
- cancelled/abandoned 不进入 code outcome 统计。
- stale started 不污染 completion rate。
- Dashboard 空状态和真实终态一致。
- telemetry payload 拒绝禁止字段和超大 payload。

### 12.4 Release

- 全量 test、typecheck、lint、bundle smoke。
- macOS arm64 native SEA build/smoke。
- 六平台 GitHub Actions assets。
- 0.0.14 → 0.0.15 `wukong upgrade` E2E。
- fresh installer、SHA-256、latest manifest 和公告 live 验证。

## 13. 发布门槛

代码发布门槛：

- 自动化证明所有已 tracking run 最终可同步或保留在可重试 outbox。
- crash/restart/offline/cancel 不会永久丢失 requestId。
- preflight 失败不消耗服务端额度。
- production metrics 能区分 terminal、cancelled、abandoned 和 stale。
- 三仓文档和 Web 文案不把支付、PR 或 Team 写成已上线。
