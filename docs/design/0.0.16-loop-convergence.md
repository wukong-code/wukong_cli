# 0.0.16 Loop Convergence 设计

> 状态：功能实现完成，发布验证中（尚未发布）
> 目标版本：`0.0.16`
> 最后更新：2026-07-21
> 一句话：**Stop repeating. Converge safely.**
> 商业边界：继续免费/BYOK；支付、GitHub PR 写入、Team、managed reviewer 和云端 `/schedule` 不进入本版本

## 1. 版本结论

0.0.15 已经让 Loop 在崩溃、断网、重启和取消后可靠进入终态。0.0.16 不继续增加普通用户命令，而是解决下一层问题：**Loop 运行了多轮以后，是否真的在向固定目标收敛，而不是重复修改、重复审查或不断提高通过标准。**

本版本把一次 Loop 从“反复执行直到上限”升级为“围绕固定验收合同、有历史记忆、能识别无进展并切换策略的收敛循环”。

主路径保持不变：

```text
Resume / Start Loop
        ↓
Freeze objective + acceptance contract
        ↓
Apply permission + capability ceiling
        ↓
Write → Check → Review
  ↑                ↓
  └── prior blockers + stable keys
                   ↓
        repeated blocker fingerprint
                   ↓
      one read-only strategist attempt
                   ↓
        PASS / NEEDS_WORK / ERROR
```

普通用户仍然只需要理解三个结果：

- `PASS`：固定目标和 Gate 均满足。
- `NEEDS_WORK`：仍有具体 blocker、达到轮次上限或 Loop 没有进展。
- `ERROR`：provider、reviewer 或检查基础设施无法完成判定。

- [相同 gap fingerprint 的无进展检测](https://github.com/xai-org/grok-build/blob/ba76b0a683fa52e4e60685017b85905451be17bc/crates/codegen/xai-grok-shell/src/session/goal_tracker.rs#L16-L30)。
- [只读、fail-open strategist](https://github.com/xai-org/grok-build/blob/ba76b0a683fa52e4e60685017b85905451be17bc/crates/codegen/xai-grok-shell/src/session/goal_strategist.rs#L1-L20)。
- [Agent 与 Persona 的输入输出契约](https://github.com/xai-org/grok-build/blob/ba76b0a683fa52e4e60685017b85905451be17bc/crates/codegen/xai-grok-pager/docs/user-guide/16-subagents.md#L94-L135)。

Wukong 的取舍：

- 保留现有 `Resume → Loop → Gate` 产品语义。
- 不把 Grok 的定时任务 `/loop` 语义带入 Wukong；定时巡检继续使用 scheduler，未来云端例程仍叫 `/schedule`。
- 默认只运行一个 fresh-context reviewer，不默认并行三个 reviewer。
- strategist 只在确认重复 blocker 后运行一次，不进入每轮固定成本。
- 不引入 Grok 的 Rust crate 切分、完整插件市场、远程 session 或 managed configuration。
- 只借鉴公开的行为和协议思想；若后续直接移植 Apache-2.0 源码，必须单独保留许可证与归属说明。

## 3. 版本目标

### 3.1 P0：冻结 Loop 验收合同

- 保留用户 objective 原文，任何派生计划都不能缩小或覆盖它。
- Loop 在第一次写入前生成一次有限、可编号的 acceptance criteria。
- 合同进入 agent record，重启、resume 和 compaction 后保持一致。
- writer、reviewer 和 strategist 都不能在执行期间修改合同。
- 用户显式修改目标时必须开始新 Loop 或显式 replace，不能静默改写当前合同。

### 3.2 P0：Reviewer 记住上轮 blocker

- 每轮 reviewer 都接收上一轮 blocker 及其稳定 key。
- 复审首先判断旧 blocker 是 `resolved`、`still_open` 还是 `replaced_by`。
- 新 blocker 只有在证明真实缺陷或未满足 objective/acceptance criterion 时才能阻断。
- 新的风格偏好、非约定扩展或 reviewer 自己提高的标准只能是 `important` / `note`，不能制造 `NEEDS_WORK`。

### 3.3 P0：识别无进展并切换策略

- harness 为每轮 blocking set 生成稳定 fingerprint。
- 同一 blocker fingerprint 连续出现两次时，不立即继续盲目迭代。
- 有剩余轮次时启动一次 read-only strategist，给 writer 一条结构化替代路径。
- strategist 后 blocker 仍保持相同，则以 `NEEDS_WORK/no_progress` 暂停。
- 最大轮次仍是硬上限；strategist 不绕过 quota，也不偷偷增加用户配置的轮数。

### 3.4 P0：Reviewer model 有真实回退

- 显式 `--review-model` 无法解析、鉴权失败或启动失败时，自动回退当前 writer model 一次。
- 用户取消不触发回退。
- invalid structured output 与 model unavailable 分开处理。
- 回退必须记录在本地诊断和隐私受限事件中，不能静默伪装成指定模型成功。

### 3.5 P0：Permission Mode v2 与分身权限上限

- `manual`、`auto`、`yolo` 必须有稳定且不重叠的语义；`auto` 不能比 `yolo` 更宽松。
- `auto` 是“不提问的受限自主模式”：只自动执行明确位于 workspace 能力边界内、且未命中高风险规则的操作；需要额外授权时暂停，而不是静默放行。
- `yolo` 是显式危险的 approval bypass；它仍不能绕过用户 `deny`、安全 hook、Plan guard、Role/Agent Profile 工具上限或只读分身边界。
- Headless `-p/--prompt` 默认使用新的受限 `auto`，不能因为无交互界面就获得 unrestricted 权限；危险 headless 执行必须显式 `--yolo --yes`。
- `--yes` 不再等价于启用 YOLO；它只确认已经显式选择的危险操作。旧 `--auto-approve` 进入带警告的兼容期。
- reviewer、planner、strategist 和只读 explore 分身永远保持只读；父 Agent 的 Auto/YOLO、Role 或自定义工具不能为它们扩权。
- 子 Agent 只能继承“已注册但仍被自身 profile 明确允许”的工具；未知或未分类的 MCP/custom tool 默认不进入只读分身。

### 3.6 P1：Cross-Agent Resume 更快进入 Loop

- Welcome/TUI 在后台只检查当前 workspace 最近的未完成外部 session。
- 每个来源最多读取 50 条、默认只看最近 30 天。
- 建议只显示一条，不把首屏变成 session dashboard。
- 选中后仍先只读恢复上下文，再由用户确认或编辑目标后启动 Loop。
- 用户可关闭外部 session suggestion；关闭后欢迎页不扫描对应目录，显式 `/resume <source>` 仍可使用。

### 3.7 P1：Role Profile 增加最小任务契约

- 在现有 prompt、model、tools、verify profile 之上增加可选 `inputs`、`outputs` 和 `capabilityMode`。
- capability 只能收窄基础 profile 权限，不能通过 Role 扩权。
- 内置 planner、reviewer、strategist 使用明确的输入输出 schema。
- 旧 Role 文件继续有效；不增加 Agent modal、persona 市场或自动角色编排。

### 3.8 P1：收敛后台任务状态

- footer 用一条紧凑计数汇总后台命令与 subagent；不再为每个后台任务重复占用状态行。
- transcript 不重复写入“仍有 N 个任务运行”类状态消息。
- checks、reviewer 和 strategist 继续使用各自现有结果语义；详细后台任务仍通过 `/tasks` 查看。
- 窄终端、无颜色和 screen reader 模式保持线性可读。

### 3.9 P1：Session picker 支持有限内容搜索

- 标题、来源、session id 和最后用户请求继续即时过滤。
- 输入至少两个字符并短暂 debounce 后，可搜索最近 Wukong/外部 session 的本地 prompt 摘要。
- 0.0.16 不引入新的 native SQLite/FTS 依赖；只扫描有界的最近 session 与有界字节。
- 搜索内容不上传、不进入 telemetry，也不把 synthetic/system prompt 当用户内容。

## 4. 非目标

0.0.16 明确不做：

- Stripe Checkout、customer portal、正式 Pro entitlement。
- GitHub PR comment/status、GitHub App 或 CI merge gate。
- 默认多 reviewer、投票 quorum 或 managed reviewer credits。
- 改变 Wukong `/loop` 为定时 prompt scheduler。
- 云端 `/schedule`、远程 session、Hosted Report 或公共分享。
- Agent/Persona 双系统、角色市场、团队角色同步。
- OS 级 sandbox、容器隔离或把策略检查宣传为不可绕过的安全边界。
- 自动修改 `.wukong/review-policy.md`、Role、Skill 或 acceptance contract。
- 上传 objective、acceptance criteria、blocker、finding、文件路径、diff 或 transcript。

## 5. Loop Acceptance Contract

### 5.1 数据结构

```ts
interface LoopAcceptanceCriterion {
  readonly id: string;
  readonly text: string;
  readonly source: 'objective' | 'completion_criterion' | 'derived'; // derived 为后续兼容预留
}

interface LoopVerificationStep {
  readonly id: string;
  readonly kind: 'project_check' | 'review';
  readonly description: string;
  readonly blocking: boolean;
}

interface LoopContract {
  readonly schemaVersion: 1;
  readonly goalId: string;
  readonly objective: string;
  readonly completionCriterion?: string;
  readonly acceptanceCriteria: readonly LoopAcceptanceCriterion[];
  readonly verificationPlan: readonly LoopVerificationStep[];
  readonly source: 'user' | 'planner' | 'fallback'; // planner 为后续兼容预留
  readonly createdAt: number;
}
```

约束：

- `objective` 必须与 `goal.create` 中的用户目标完全一致。
- 0.0.16 的合同只包含用户 objective 和可选的显式 `completionCriterion`，因此实际为 1–2 条稳定 criteria；`derived` 与 `planner` source 只为后续兼容预留，本版不会由模型自动生成验收标准。
- 不让 planner 拥有或改写合同，避免额外模型调用、隐藏成本和模型自行提高门槛。内置 planner Role 仍是只读任务角色，但不参与合同创建。
- 新 Loop 在创建时以 `source = user` 冻结合同；旧 Goal 第一次进入 Gate 时创建 `source = fallback` 的最小合同，不消耗额外 Loop quota，也不丢失原目标。

### 5.2 持久化

新增 append-only agent record：

```ts
type GoalConvergenceRecord =
  | { type: 'goal.contract.create'; contract: LoopContract }
  | { type: 'goal.review.record'; attempt: LoopReviewAttempt }
  | { type: 'goal.strategy.record'; attempt: LoopStrategyAttempt };
```

规则：

- `goal.contract.create` 对同一 `goalId` 只允许一次。
- restore 必须按 record 顺序重建合同、review history 和 strategy 状态。
- compaction 可以压缩自然语言上下文，但不能丢弃结构化合同和最后 blocker 状态。
- 旧 Goal 没有合同：第一次进入 0.0.16 Gate 时从原 objective/completion criterion 创建兼容合同。

## 6. Prior Gaps 与 Anti-ratchet

### 6.1 Review attempt

```ts
interface LoopReviewBlocker {
  readonly key: string;
  readonly findingId: string;
  readonly criterionId?: string;
  readonly category: 'correctness' | 'security' | 'test' | 'performance' | 'maintainability';
  readonly file?: string;
  readonly summary: string;
  readonly evidence: string;
  readonly nextAction: string;
}

interface LoopReviewAttempt {
  readonly schemaVersion: 1;
  readonly iteration: number;
  readonly status: 'PASS' | 'NEEDS_WORK' | 'ERROR';
  readonly blockers: readonly LoopReviewBlocker[];
  readonly blockerKeys: readonly string[];
  readonly blockerFingerprint?: string;
  readonly workspaceFingerprint: string;
  readonly model: string;
  readonly usedModelFallback: boolean;
  readonly priorBlockerDispositions: readonly {
    readonly key: string;
    readonly status: 'resolved' | 'still_open' | 'replaced_by';
    readonly replacedBy?: string;
  }[];
}

interface LoopStrategyAttempt {
  readonly schemaVersion: 1;
  readonly triggeredAtIteration: number;
  readonly blockerFingerprint: string;
  readonly status: 'advised' | 'failed';
  readonly diagnosis?: string;
  readonly recommendedApproach?: string;
  readonly risks?: readonly string[];
  readonly model?: string;
  readonly usedModelFallback: boolean;
}
```

`LoopReviewAttempt` 只保存继续收敛必需的 blocking findings，不复制 important/note、raw model response 或完整 transcript。`LoopStrategyAttempt` 的建议也只保存在本地 agent record，用于 restart/resume 后继续当前 Goal。服务端只接收允许的计数和 outcome。

### 6.2 Stable blocker key

不能直接信任模型生成的 finding id 作为 stall 判断。harness 生成稳定 key：

```text
deterministic check:
  check:<normalized-command-id>:<status>

review finding:
  review:<criterion-id-or-objective>:<category>:<normalized-relative-file-or-none>
```

然后对排序、去重后的 blocking keys 计算 fingerprint。

安全规则：

- 不把 summary 自然语言直接放进 key，避免措辞变化绕过检测。
- 不使用绝对路径。
- line number 只用于展示，不进入 key，避免普通代码位移制造新 blocker。
- 一个宽泛 key 下若 evidence 明显变化，reviewer 可以用 `replaced_by` 说明，但必须保留关联关系。

### 6.3 Reviewer prompt contract

复审顺序固定为：

1. 阅读用户 objective 和冻结合同。
2. 对每个 prior blocker 给出 `resolved` / `still_open` / `replaced_by`。
3. 读取当前 workspace、deterministic checks 和 policy。
4. 只在发现真实缺陷或未满足固定标准时增加 blocking finding。
5. 所有 prior blocker 已解决且固定标准满足时返回 PASS。

Reviewer 不得因为个人偏好、更多测试覆盖想象、额外重构或未约定扩展提高通过门槛。

## 7. Stall Detection 与 Strategist

### 7.1 状态机

```text
NEEDS_WORK fingerprint=A
          ↓ next review
NEEDS_WORK fingerprint=A
          ↓
strategistAttempted=false and iterations remain
          ↓
run one strategist → inject recommendation
          ↓ next review
fingerprint changed  ──→ continue normal Loop
fingerprint still A ──→ NEEDS_WORK/no_progress + pause
```

规则：

- 重复阈值固定为连续两次相同 blocking fingerprint。
- strategist 每个 Goal 最多成功或失败尝试一次。
- strategist 使用 fresh context、read-only profile，并读取合同、prior blockers、当前 workspace 与 check evidence；不复制完整 worker transcript。
- strategist 只返回 `diagnosis`、`recommendedApproach`、`risks`，不能修改合同、policy、Role 或 workspace。
- strategist 失败是 fail-open：记录失败；若仍有轮次，继续普通 Loop；没有轮次则返回原有 `max_iterations`。
- strategist 不额外增加 quota 或 `maxIterations`。
- strategist 后相同 fingerprint 再出现时，终态仍是现有 `NEEDS_WORK`，reason code 为 `no_progress`，不是新增第四种 Gate 状态。

### 7.2 用户文案

默认结果保持短：

```text
Gate      NEEDS_WORK
Reason    Same blocker remained after a strategy change
Blocker   auth-session-test
Next      Review the blocker or resume with a different approach
```

高级详情才显示 fingerprint、策略模型、fallback 和 review history。

## 8. Model Fallback 与错误语义

| 情况 | 行为 | 结果 |
|---|---|---|
| 显式 reviewer model 无法解析/鉴权/启动 | 回退当前 writer model 一次 | 继续 Gate，并记录 fallback |
| reviewer 返回 invalid JSON | 同一有效模型重试一次 | 再失败为 `ERROR/reviewer_invalid_output` |
| fallback model 也失败 | 不再重试 | `ERROR/reviewer_unavailable` |
| 用户取消 reviewer | 不回退 | cancelled，不伪造 Gate |
| deterministic check 命令真实失败 | reviewer 不可覆盖 | `NEEDS_WORK/check_failed` |
| check 工具/运行环境不可用 | reviewer 不可覆盖 | `ERROR/check_unavailable` |
| strategist 失败 | fail-open | 继续或按现有上限结束 |

TUI 常驻 footer 不显示模型细节；只在 fallback 发生时增加一条可展开提示。

## 9. Permission Mode v2

### 9.1 三种模式的用户合同

0.0.16 保留现有 wire 名称，重新冻结用户可理解的行为：

| 模式 | 是否允许向用户提问 | 自动执行边界 | 遇到边界外操作 |
|---|---|---|---|
| `manual` | 允许 | 现有默认允许的只读操作与 workspace 内普通写入 | 询问用户 |
| `auto` | 不允许 | workspace/additional dirs 内、profile 已允许、且未命中高风险规则的操作 | 阻断并暂停当前 Loop |
| `yolo` | 允许 | 跳过普通 approval；可执行 profile 已允许的操作 | 仅硬性 deny/capability ceiling 能阻断 |

共同规则：

- PreToolUse block、安全 hook、用户显式 `deny`、Plan mode guard 和 Agent Profile/Role 工具上限始终先于模式决策。
- `auto` 不得绕过用户 `ask`、敏感文件、Git control path、workspace 外写入或高风险 Bash/MCP/custom tool；在无 UI 的路径上，这些 `ask` 必须转成稳定的 block/pause，而不是默认批准。
- `yolo` 只跳过 approval，不增加工具，也不改变 read-only profile；UI 必须持续显示危险状态。
- 当前风险判断是应用层 policy/guard，不是 OS sandbox。文案不得使用“完全隔离”“绝对安全”或“不可绕过”。

### 9.2 CLI 与兼容行为

```text
wukong                         # manual
wukong --auto                  # autonomous + guarded
wukong --yolo                  # interactive + unrestricted approvals
wukong -p "fix the tests"      # headless safe auto
wukong -p "fix the tests" --yolo --yes
                               # explicit headless unrestricted run
```

- `--auto` 与 `--yolo` 继续互斥，避免一个枚举同时表达两套相反策略。
- `-y` 继续作为 `--yolo` 的短参数。
- `--yes` 从“YOLO 隐藏别名”改为危险 headless 执行的确认信号；单独传入不能改变 permission mode。
- 旧 `--auto-approve` 在 0.0.16 仍映射到 `--yolo`，但必须输出一次 deprecation + danger warning；后续版本再删除。
- `default_permission_mode = "auto"` 继续可读取，但升级后使用新的受限 Auto 语义；这是安全收紧，不迁移为 YOLO。
- resume 旧 session 时，命令行显式模式覆盖恢复值；未显式指定时沿用 record 中的模式并展示实际边界。

### 9.3 Auto 阻断与 Loop 结果

Auto 至少阻断：

- workspace/additional dirs 外的写入、移动和删除。
- `.git` control path、credential、SSH key、token、`.env` 等敏感目标的读写。
- `rm -rf`、`git reset --hard`、`git clean -f`、远程脚本管道执行和已识别的网络上传。
- capability 未分类或声明 mutating/network/credential access 的 MCP/custom tool。

阻断不伪装成检查失败：

```text
Gate      NEEDS_WORK
Reason    Permission required
Action    Review the blocked action or restart explicitly with YOLO
```

内部 reason code 为 `permission_required`；若风险分类器自身不可用，则 fail-closed 为 `ERROR/permission_policy_unavailable`。命令正文、路径和 tool arguments 只保存在本地 transcript，不进入 telemetry。

### 9.4 分身权限继承

子 Agent 的有效能力必须取交集：

```text
base profile
  ∩ child profile
  ∩ parent enabled tools
  ∩ active Role/tool policy
  ∩ permission mode ceiling
```

- `reviewer`、`planner`、`strategist` 和只读 `explore` 强制 `read-only`；即使父 Agent 是 YOLO，也不能获得 Bash、Write、Edit 或可变更外部状态的 MCP/custom tool。
- `coder` 可继承父 Agent 的 mode，但仍受自己的 profile、workspace 边界和用户 hard deny 约束。
- `inheritUserTools` 只能继承注册信息，不能绕过 child profile 直接激活工具。
- 未声明 capability metadata 的 custom/MCP tool 对只读分身默认拒绝；0.0.16 不靠工具名称猜测副作用。
- Agent/AgentSwarm 结果与 `/tasks` 详情显示实际 profile、permission mode 和 capability summary，不显示 tool arguments。

## 10. Cross-Agent Resume 激活与边界

### 10.1 扫描限制

- 当前 workspace suggestion：每个来源最多 50 条、30 天、标题最多 200 字符。
- 显式 picker 仍允许查看全部 workspace，但保持每来源 500 个候选文件和现有 head/tail byte cap。
- suggestion 扫描在后台运行，不阻塞首屏。
- realpath/symlink containment、损坏 JSONL 隔离和 synthetic prompt 过滤保持现有规则。

### 10.2 首屏行为

只有找到当前 workspace 的近期外部 session 时显示：

```text
Continue recent task from Codex
```

不显示来源统计、总 session 数或多个卡片。用户进入后仍使用统一 picker，并经过：

```text
read-only context import → inspect current workspace → edit/confirm objective → start Loop
```

配置：

```toml
[resume]
foreign_suggestions = true
```

关闭后 welcome 不访问 Codex、Claude Code、Cursor session 目录；显式 `/resume codex|claude|cursor` 不受影响。

## 11. Role Contract

现有 Role 文件增加可选字段：

```yaml
name: reviewer
capabilityMode: read-only
inputs:
  - name: loop_contract
    type: json
    required: true
  - name: prior_blockers
    type: json
    required: false
outputs:
  - name: verdict
    schema: reviewer-verdict-v1
    required: true
```

`capabilityMode`：

| 模式 | 能力 |
|---|---|
| `read-only` | Read/Glob/Grep/ReadMediaFile；不能 Bash、编辑或安装 |
| `read-write` | 可读写文件；命令仍遵守 session permission |
| `execute` | 可执行命令；不自动获得文件写权限 |
| `all` | 仅在基础 profile 已允许时可用，Role 本身不能扩权 |

兼容：

- 旧 `tools` allowlist 继续有效。
- 同时存在时取 `capabilityMode ∩ tools ∩ base profile`。
- 未声明 inputs/outputs 时保持 0.0.15 行为。
- 内置 reviewer 与 strategist 固定 `read-only`；planner 固定 `read-only`。

## 12. TUI Task Plane

统一状态行示例：

```text
◎ 3 tasks
```

要求：

- footer 只保留一条后台任务计数，不重复展示每个 command/subagent 名称。
- 状态变化原位更新，不向 transcript 追加“仍有 N 个任务运行”。
- `/tasks` 保留完整后台任务列表、状态、耗时和取消入口。
- checks、reviewer 和 strategist 不伪装成已接入统一 task registry；它们继续使用现有 Loop/Gate 状态。
- 0.0.16 不重写整套任务调度协议；统一 task id/display contract 留到有真实需求的后续版本。

## 13. Session 内容搜索

0.0.16 使用有界扫描，不增加 SQLite/native 依赖：

- 只搜索最近 100 个 session。
- 每个 session 最多读取 128 KiB 的用户 prompt 摘要输入。
- 至少输入 2 个字符，debounce 250ms。
- 当前 workspace 优先，随后按更新时间排序。
- 搜索 worker 可取消；新 query 到来时旧扫描不能覆盖结果。
- 只索引用户内容，不索引 tool output、system prompt、环境块或外部网页正文。
- 匹配结果只显示一行脱敏摘要。

如果真实 session 数和延迟证明有必要，再在后续版本设计持久化 FTS；0.0.16 不为尚未出现的规模问题增加 native 依赖。

## 14. 指标与隐私

0.0.16 新增的允许事件：

```text
loop_contract_created
loop_blocker_repeated
loop_strategist_started
loop_strategist_terminal
loop_unstuck_after_strategy
loop_no_progress
review_model_fallback
permission_mode_selected
auto_action_blocked
yolo_session_started
subagent_capability_ceiling_applied
resume_suggestion_shown
resume_suggestion_selected
```

允许字段：

- CLI version。
- contract source 和 criteria count。
- iteration、blocker count、是否重复、是否 fallback。
- strategist outcome 和最终 Gate outcome。
- permission mode、阻断类别、工具能力类别和分身 profile 类别；不含命令、参数、路径或自定义工具名。
- suggestion source 类别和是否选择。

禁止字段：

- objective、criterion 文本、blocker key/fingerprint、finding 内容。
- session id、原生外部 id、workspace、文件路径、仓库名。
- diff、源码、prompt、transcript、policy、Role 内容或 model API key。

0.0.16 用这些指标回答：

1. 多少 Loop 因相同 blocker 卡住。
2. strategist 是否真的让 blocker 集合改变或最终通过。
3. reviewer model fallback 是否降低 ERROR，而不是隐藏配置问题。
4. Auto 的风险阻断是否导致用户安全恢复、显式升级为 YOLO 或直接放弃。
5. reviewer/strategist 的 capability ceiling 是否真实阻止父 Agent 扩权。
6. Resume suggestion 是否提高 `resume → loop_started → loop_terminal` 转化。

## 15. 兼容策略

| 旧输入/状态 | 0.0.16 行为 | 是否改写旧数据 |
|---|---|---|
| 0.0.15 及更早 Goal/session record | 正常恢复；第一次进入新 Gate 时生成 fallback contract，不伪造旧 review history | 否，只追加新 contract record |
| 早期 `goal.strategy.record` 的 `afterIteration/outcome/advice` | 读取时归一化为 `triggeredAtIteration/status/recommendedApproach` | 否 |
| 现有 `LoopResult`、CLI exit code、`/loops/complete` payload | 三态和 wire contract 不变；convergence metadata 仅本地可选 | 否 |
| 0.0.15 durable run、completion outbox、lifecycle reconciliation | 行为保持并纳入全量回归 | 否 |
| 旧 Role 文件 | 继续有效；缺少 inputs/outputs/capabilityMode 时采用旧行为，但新增字段只能收窄权限 | 否 |
| 旧 `manual|auto|yolo` permission record 与 `default_permission_mode` | 继续读取；`auto` 使用新的受限语义，不迁移成 YOLO | 否 |
| 单独 `--yes` | 不选择 permission mode；若与 `--yolo` 同用，只承担危险 headless 确认 | 不适用 |
| `--auto-approve` | 一个兼容版本内映射到 YOLO，并输出弃用与危险警告 | 不适用 |
| Headless `-p` | 默认使用受限 Auto；只有显式 `--yolo --yes` 才跳过普通 approval | 不适用 |
| 裸 `/resume` | 仍只显示 Wukong；不恢复 `/resume wukong` | 不适用 |
| `/loop` | 仍是 iterate-until-verified，不接受周期 scheduler 语义 | 不适用 |
| `verify`、`scan`、`proof` | 继续作为 Loop 内部层和高级诊断 | 不适用 |

## 16. 实施顺序

### Phase A：冻结 Convergence Contract

1. 增加 `LoopContract`、review attempt、strategy attempt schema。
2. 增加 append-only agent records 与 restore/compaction contract。
3. 增加旧 Goal fallback contract 兼容。
4. 冻结 reviewer prior gaps 和 stable blocker key 规则。

### Phase B：Reviewer Anti-ratchet

1. 把合同和 prior blockers 注入 fresh reviewer。
2. 扩展 verdict schema 的 `criterionId` 和 prior blocker disposition。
3. 由 harness 生成 blocker key/fingerprint。
4. 覆盖新 blocker 合法性、旧 blocker resolved/still-open 和 workspace freshness。

### Phase C：Stall 与 Model Fallback

1. 连续重复 fingerprint 检测。
2. 实现内置 read-only strategist profile 与严格输出 schema。
3. strategist 一次性触发、fail-open 和 `no_progress` 终态。
4. reviewer 显式 model → current writer model 回退与诊断。

### Phase D：Permission Mode v2 与 Subagent Ceiling

1. 重排 permission policy：hard deny/profile ceiling → mode decision → ask/default allow；Auto 不再先于敏感路径和用户 ask 规则放行。
2. 为 Auto 增加 workspace boundary、敏感目标、高风险命令和 MCP/custom capability block。
3. 修正 Headless `-p`、`--yes`、`--auto-approve`、resume override 和配置兼容。
4. 修正 subagent custom-tool 继承：只注册、不绕过 child profile 激活；内置 reviewer/planner/strategist 强制只读。
5. TUI/footer、Agent/AgentSwarm 和 `/tasks` 展示实际 permission/capability，YOLO 使用持续危险提示。

### Phase E：Resume 与 Role Contract

1. 增加近期 suggestion 的 30 天/50 条边界和 opt-out。
2. Welcome 显示单条 Continue suggestion。
3. Role schema 增加 inputs/outputs/capabilityMode。
4. 内置 planner/reviewer/strategist 使用新契约。

### Phase F：TUI、搜索与指标

1. 统一 task status line 和完成 chip。
2. 实现有界 session 内容搜索与取消。
3. 增加隐私受限 convergence metrics。
4. 同步中英文 README、用户指南、CHANGELOG、release notes、公告和 Web 文案。

## 17. 测试矩阵

### 17.1 Contract 与恢复

- 用户 objective 原文不能被 derived criteria 缩小。
- contract 对同一 Goal 只创建一次。
- restart/resume/compaction 后 contract 和 prior blockers 不变。
- 旧 Goal 生成 fallback contract，不伪造历史。
- writer/reviewer/strategist 无法修改 contract record。

### 17.2 Anti-ratchet 与 Stall

- prior blocker 已解决时不会再次出现。
- reviewer 不能用新风格偏好制造 blocking finding。
- 同一 blocker 不同措辞生成相同 key。
- 同一问题的措辞或行号变化不会错误制造新 blocker；文件路径仍属于 finding 身份的一部分。
- 两轮相同 fingerprint 触发一次 strategist。
- strategist 后 fingerprint 改变时继续；仍相同则 `NEEDS_WORK/no_progress`。
- strategist 不超过 maxIterations 或服务端 quota。

### 17.3 Model 与错误语义

- 显式 reviewer model 不存在时回退 writer model 一次。
- fallback 成功时 Gate 正常结束且诊断可见。
- 两个 model 都失败时返回 ERROR，不返回 NEEDS_WORK。
- cancellation 不触发 fallback。
- invalid output 与 unavailable/error 分开计数。

### 17.4 Permission Mode 与分身权限

- Auto 不调用 `AskUserQuestion`，workspace 内普通操作可继续；workspace 外写入、敏感目标、高风险 Bash 和未分类 MCP/custom tool 被阻断。
- Auto 的用户 `ask` 规则在交互与 headless 路径都转成阻断；活动 Loop 记录 `NEEDS_WORK/permission_required` 并暂停，绝不弹问答或静默 approve。
- YOLO 可跳过普通 approval，但不能绕过用户 `deny`、PreToolUse block、Plan guard、profile allowlist 或只读 capability。
- `--yes` 单独使用不启用 YOLO；`-p --yolo` 缺少 `--yes` 时在任何工具执行前失败。
- 旧 `--auto-approve` 显示弃用和危险警告；旧 permission records/config 可恢复。
- 父 Agent 为 Auto/YOLO 且启用自定义工具时，reviewer/planner/strategist 仍不能看到或调用未被 child profile 明确允许的工具。
- coder 分身只继承合法交集；Agent/AgentSwarm 输出的实际 capability 与运行时一致。

### 17.5 Resume、Role 与 TUI

- 近期 suggestion 遵守当前 workspace、30 天和 50 条限制。
- opt-out 后 welcome 不访问外部 session 目录。
- 显式 `/resume <source>` 在 opt-out 后仍可用。
- Role capability 与 tools/base profile 取交集，不能扩权。
- task line 在 40/80/120 列宽下稳定，对 screen reader 可读。
- session 搜索有界、可取消、过滤 synthetic/system 内容。

### 17.6 真实 E2E

- Node、Python、Rust、Go 项目各覆盖一次 prior blocker → fix → PASS。
- reviewer 重复 blocker → strategist → unblock。
- reviewer 重复 blocker → strategist → no progress。
- 指定无效 reviewer model → fallback → PASS/NEEDS_WORK。
- TUI/Headless 分别覆盖 Manual、Auto、YOLO；Auto 风险阻断可恢复，显式 YOLO 可继续。
- Auto/YOLO 父 Agent → reviewer/strategist 的真实工具调用证明只读 ceiling 不可绕过。
- Codex、Claude Code、Cursor suggestion → resume → edit objective → Loop terminal。
- 0.0.15 → 0.0.16 Goal/session 和 native upgrade。

## 18. 发布门槛

- 固定合同、prior gaps、fingerprint、strategist 和 fallback 均有 contract tests。
- 至少三个真实仓库证明 reviewer 不会在每轮抬高门槛。
- 同 blocker doom loop 能在最大轮次前进入 strategist 或 `no_progress`。
- strategist 失败不会把正常 Loop 错误升级为 ERROR，也不能扩权或修改 workspace。
- Auto 不再先于敏感路径、用户 ask 和风险规则批准；YOLO 不能为只读分身扩权，且 custom/MCP tool 有 fail-closed capability 测试。
- `wukong -p`、`--auto`、`--yolo`、`--yes`、`--auto-approve` 和旧 permission record/config 的 CLI 兼容矩阵通过。
- 0.0.15 durable lifecycle、completion outbox 和 completion API 全部回归通过。
- Session suggestion/search 的扫描量、延迟、取消和隐私边界有自动化测试。
- 全量 test、typecheck、lint、bundle、native smoke 和六平台 release assets 通过。
- 中英文 README、ROADMAP、TODO、用户指南、CHANGELOG、release notes、公告和 Web 文案同步。
- 官网不得把 multi-reviewer、PR Gate、支付、Team 或云端 Loop 写成 0.0.16 已上线能力。

## 19. 商业判断

0.0.16 继续免费/BYOK。它不是新的收费层，而是让免费用户更容易完成第一次 Loop、减少模型空转并形成重复使用。长期的 Role / Specialist / Managed Gate 与商业分层见 [Wukong 能力体系与商业化原则](../business/WUKONG_CAPABILITY_MODEL.md)；本版只建设 acceptance、Role contract、分身权限上限和可靠运行地基，不实现付费 Custom Specialist 或 Managed Gate。

商业价值链：

```text
固定完成标准
  → 更少重复轮次
  → 更高 Loop terminal rate
  → 更多 7-day repeat users
  → 0.1.0 Trusted Local Loop 稳定发布
  → 0.2.0 Reliable Autonomy 邀请制验证
```

默认单 reviewer 和 strategist 属于完整免费 Loop。未来只有在真实高风险 PR 用户证明需要更高决策置信度后，才把多 reviewer quorum 设计为可选 `Deep Gate`；它不能在 0.0.16 中成为人为额度墙。

2026-07-20 曾把 0.1.0 的首个付费假设定义为 PR Gate publish；该方案现已[归档](historical-pro-pr-gate-billing.md)。2026-07-25 起，0.1.0 继续 Free/BYOK，只发布 Trusted Local Loop；付费只在 0.2.0 Reliable Autonomy 候选中验证，PR Gate 不再是唯一购买理由。
