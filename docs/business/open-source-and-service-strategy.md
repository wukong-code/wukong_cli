# 本地 CLI 开源与服务收费路线

> 更新：2026-10-23。
> 状态：产品方向已确认；本次仅更新文档，开源发布与服务实验均未执行。
> 方向索引：[ROADMAP](../../ROADMAP.md)。服务候选：[0.1.3 交付验收试点](../design/0.1.3-delivery-acceptance-pilot.md)。
> 不改变 0.1.2 已批准功能范围；开源发布方案、最终许可证、服务合同与收款路径仍需另行确认。

## 已确认方向与当前状态

开源完整、可独立使用的本地 CLI，以可检查和可自行构建的产品获得真实采用；官网
后端继续私有。收入先来自具体仓库的接入与验收陪跑服务，再由重复购买决定持续
服务和未来团队产品。开源发布、产品功能验收与商业验证分别记录，不相互替代。

2026-10-23 核对时，`wukong-code` 是公开分发/文档仓，但其 `LICENSE.md` 仍为专有
许可；`wukong_cli` 与 `wukong_web` 仍为私有仓库。CLI 根 LICENSE 保留所有权利，
根与 CLI package 的 license 字段为 `UNLICENSED`，部分内部包标为 `MIT`。
本次没有修改这些文件或仓库可见性，不能把方向确认表述为已经开源。

后续迁移状态：三个仓库已转入 `wukong-code` 组织，本地远程与仓库链接已更新。
迁移组织不改变上述许可与源码可见性，也不代表已完成开源发布。

## 开源与私有的边界

| 范围 | 确认的方向 | 可核对边界 |
|---|---|---|
| 本地 CLI 核心 | 开源 | CLI/TUI、Resume、Loop、Gate、Provider 接入、恢复与运行上限，以及构建和运行所需的内部依赖、测试与文档 |
| 本地 server / browser UI | 属于本地产品；保留时随所需源码开放 | `wukong_cli/apps/wukong-web` 与 `packages/server` 不是官网后端；依赖边界随发布方案核对，不能留下必须连接私有服务才能跑通的核心流程 |
| 官网与运营后端 | 保持私有 | `wukong_web` 的账号/device auth、反馈、运营接口、数据库及部署配置；公开网页和隐私说明不等于后端源码开源 |
| 客户与经营记录 | 私有留存 | 合同、收款/退款、客户仓库与任务、支持成本和未获展示授权的证据不进入开源发布内容 |
| 未来团队产品 | 需求验证后独立评审 | 不预先承诺现有免费核心转为收费；新协作能力的范围与许可另立设计 |

开源版本须能从公开源码完成构建，并在自带模型 API Key、无 Wukong 账号和无官网
后端支持时跑通 Resume → Loop → Gate。Gate 规则、必需依赖或可运行样例不能被
留在私有仓库而使公开版本无法独立工作。模型请求仍发送给用户选择的 provider。

## 开源发布的后续决策

优先评估 Apache-2.0，尚未选定最终许可证。先核对自有代码权属、第三方源文件与
原始许可，解释根许可证、package 字段与第三方 notice 的差异，保留必须的原始声明；
本次不通过修改 README 重新许可代码，也不将所有内部包机械替换成同一许可证。

公开源码放入哪个仓库、采用完整历史还是经核对的发布快照、首次公开版本与迁移
方式，由后续发布方案确定。应明确公开文件清单与 source revision，区分可发布内容
和私有运营历史，再执行实际公开；本次不直接将整个私有仓库改为 public。

完成开源发布至少要有：公开可获取的完整所需源码、正确的 LICENSE/notice、
可重复的外部构建与无账号核心流程，以及源码与分发资产的可追溯关系。官网、README
和安装页只有在这些事实成立后才改称“已开源”。这不要求先完成全部 0.2.0 瘦身。

## 服务收费路径

首批买方假设是使用 AI 开发、反复交付项目的小型开发团队或软件外包公司的技术/
交付负责人。先选一个技术栈和近期真实交付任务；该客户群的付费需求尚未验证。

| 阶段 | 卖什么 | 收费与决策边界 |
|---|---|---|
| 首单按次服务 | 一个仓库、一次真实交付任务：整理用户确认的完成条件、跑通原项目检查、陪跑有界修复与复验、人工整理结果与未覆盖项 | 按明确范围单独报价，约定支持工时和交付物；未收款不记为已收服务费，未交付不记为已交付，不承诺必定 PASS 或没有缺陷 |
| 重复购买 | 同一团队在下一次真实交付主动再次购买同一服务 | 记录第二个任务、购买理由、实际付款、退款及支持成本；第一单免费体验不算付费验证 |
| 持续验收服务 | 已出现重复需求后的固定范围月度接入/验收支持 | 才测试 `$199/团队/月、最多 5 人`；这是未验证报价，不是公开套餐或软件订阅，支持次数/工时必须约定 |
| 团队产品化 | 将多个付费团队反复购买、可独立使用的同一工作流产品化 | 归 0.3.0；另验收团队边界、Billing/entitlement、权限与隐私，不能直接把服务订单计成 SaaS 订阅 |

模型费用由客户 BYOK 承担。账本分开记录一次性接入/陪跑费、月度服务费与未来软件
订阅收入，并扣除接入、支持、基础设施与支付处理成本；大量定制交付单独报价。
首单与月度服务均须先确认范围、合同、报价、取消/退款条款及可用收款路径。

首轮可以使用当前 CLI 加人工配置、人工验收摘要交付。自动 PR Gate、自动需求映射、
摘要发布与新团队能力仍为 0.1.3 候选，未完成时不作为已有权益出售。客户发现和
现有能力服务验证可与开源准备、0.1.2 并行，不等待新 binary、开源正式发布或完整重构。

## 分开的证据与门槛

- 开源采用：外部用户实际构建/运行、在真实任务主动再次使用、明确反馈。Star、fork、
  下载量不证明任务价值、付费需求或收入。
- 0.1.3 服务试点目标：3 个非关联团队实际付款，每队至少 2 次真实交付；未达时
  复盘客户、场景、报价与服务成本，不自动扩功能。数字不是收入预测或实施授权。
- 0.3.0 产品化评审：同一工作流被反复购买；至少 2 个团队进入月度服务后跨下一实际
  账期续费，重复使用归因明确、交付毛利为正。第二笔按次订单只计复购，不冒充月度
  续费；服务续费也不证明标准软件订阅成立。
- 公开自助订阅：另行确认产品可独立使用、权益、完整 Billing 与权限/隐私/故障恢复。
  Free 本地 Loop、Resume、Gate、BYOK reviewer 与基础验证持续完整，不查收费 entitlement。

公开文案必须区分“计划开源 / 已开源”“服务报价 / 已收款”“服务复购 / 月度续费 /
软件订阅”。官网后端私有不改变已声明的数据边界，也不意味着可以上传客户源码。
